# Adversarial review: issue 10 / persistent-bash-pty-session

**Evidence re-run.** I re-ran `tests/test_session.py` on the patched target (`$PDCA_TARGET`) with the gate venv's Python: 35 passed in 10.7 s. That matches C4/T3. The red leg (gate-logs/C4-verify.log) is 35/35 `ModuleNotFoundError: nl_shell.session`. That is the expected red for a brand-new module, but it only proves the module didn't exist before. It does not prove that each test would catch a broken version of the behaviour it names. The tests do drive the production path: the real `Session`, real bash, and `os.openpty()` standing in for the terminal. I found no copy of the logic inside the tests.

I tried to break the fix with probe scripts (in the scratch dir, against the target's `src/`). Results:

- NEEDS-HUMAN [human] — **Typed-ahead input becomes part of the next confirmed command.** `src/nl_shell/session.py:517-524` forwards terminal bytes to the PTY while a command runs. If the command doesn't read them, readline picks them up at the next prompt. Then `run()` pastes the next confirmed command after them (`session.py:454`), and `_drain_pty()` at `session.py:434` can't stop this because it only drains output. Concrete case: during `run("sleep 2", terminal=t)`, write `echo INJECTED; ` (no Enter) to the terminal. The next `run("true")` returns output `'INJECTED\n'`, so bash ran `echo INJECTED; true`. A 200 KB paste gave status 127 on the next `true`. This breaks the Goal's "sends a confirmed command byte-for-byte" and spec §5.1 ("exactly the confirmed bytes"). #78's gate will confirm one string while bash runs another. Fixing it needs a decision §5.3 doesn't currently allow: clear readline's line before the paste (e.g. a kill-line byte), or stop forwarding when no process is reading. That's why I tagged this [human] rather than [impl]. No test covers typeahead.
- NEEDS-HUMAN [human] — **A typed-ahead Enter, or any syntax error or comment-only command, degrades the session.** For a line that doesn't parse, PS0 never runs, but `__nls_done` still bumps `__nls_seq` (`session.py:80`, `session.py:85`). So a `D n+1` arrives with no `S`, and `pty_protocol.py:221-222` degrades the session. Reproduced: `run("fi")` and `run("# just a comment")` both raise `SessionDegraded: control record 'D' arrived out of order (without a start record)`. So does pressing Enter during a forwarded `sleep 2` (the *next* `run("true")` raises). An unclosed quote (`echo 'abc`) degrades after the 1 s back-at-a-prompt rule. All of these fail closed, and the behaviour comes from the spec's reference rcfile (v1.md:62). But in practice an ordinary typo forces a restart, and that loses `cd`/`export` state. The brief and the tests don't mention it. A human should decide whether that's acceptable for M0, or whether to treat "D n+1 without S" as "didn't parse, not run" (a spec change).
- NEEDS-HUMAN [human] — **Capture stops for good at the first forwarded byte**, including the Ctrl-C in vector 10 (`session.py:520-522`, `_Capture.stop` at `session.py:207-211`). The brief's Scope says capture pauses only on the alternate screen. Spec §6.2 makes capture a MAY, so this is allowed. Still, an interrupted or interactive command reaches #62 (failure classes) and #11 (state block) with only partial output, flagged by `input_forwarded`. That's a product trade-off the human should confirm, not a bug.
- **Known limit, confirmed:** `run("sleep 2 & wait")` degrades with "no done record after the shell returned to a prompt" (`session.py:594-608`). The brief accepts this for `read`/`wait`. I'm listing it so the sign-off sees that ordinary `cmd & wait` hits it too, not just `read`.

Attempted and could not break:
- Prompt or user-`PROMPT_COMMAND` output leaking into captured output. 150 runs of `echo hi` with a custom PS1 and a printing user `PROMPT_COMMAND`, under 3 busy CPU loops: 0 bad.
- A forwarded paste larger than the PTY buffer hanging the loop: no hang, `run()` returned on time.
- Faking records through a `PATH` that contains a newline (`P` is the only snapshot field not passed through `tr`). An injected `J`/`H`/`F`/`E` either repeats a record type (`pty_protocol.py:234-235`) or lands in IDLE. Both degrade, so this fails closed.
- `$(sleep 2)` falsely tripping the back-at-a-prompt rule: correctly excluded by the child-process-group check (`session.py:617-626`).
- Vectors 4/5 (printed fake records) and the `\r`-is-malformed rule (`pty_protocol.py:98-101`): they hold.

Verdict: I couldn't refute the red→green evidence or the spec vectors as tested. The first finding is a real gap between the Goal's "byte-for-byte" claim and what the code does. The reviewer's pass doesn't cover it, because no test forwards input that isn't a full line.
