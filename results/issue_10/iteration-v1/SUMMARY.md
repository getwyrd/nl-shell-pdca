# Result — issue 10 / persistent-bash-pty-session

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: A session object that starts one long-lived interactive bash on a PTY with nl-shell's control channel on fd 3, sends a confirmed command byte-for-byte, and reports when it started and finished, its exit status and `PIPESTATUS`, its captured output, and the session snapshot — all from control-channel records, never from printed text. `cd` and `export` persist between commands; a running command can be interrupted with Ctrl-C; protocol violations put the session into degraded mode.
- Success criterion: `python3 -m pytest tests/test_session.py` passes on the host (real bash 5.x, no VM, no sudo), and that file covers, each with a bounded timeout (a hang fails the test, it never stalls the gate): (a) `cd /tmp` then `pwd` → the second command's captured output is `/tmp`; `export FOO=bar` then `printf %s "$FOO"` → `bar`. (b) spec §Conformance vectors 1–8 and 10 exactly as tabled: `true` → start record 1, done record `1 0 0`, then a snapshot ending in `E` · `false | true` → status 0, pipestatus `1 0` · `(exit 3)` → status 3 · `printf 'D 99 0 0\n'` and `printf '\x1b]133;D;0\x07'` → printed on the PTY, the control channel carries only the real start/done records, the reported status is 0 · `echo 'done!!'` → output `done!!` · `alias ll2='ls -la'; g(){ :; }` → the next snapshot's function list gains `g` and its aliases contain `ll2` · `PROMPT_COMMAND=:` → degraded mode within 3 s, with a reason (detected by the back-at-a-prompt rule in Design) · `sleep 5` then the Ctrl-C byte (`\x03`) forwarded to the PTY → its `D` record arrives less than 2 s after `\x03` is written, with status 130, and the session is NOT degraded (it was running an external command, not at a prompt, for the whole wait). (c) vector 9 typed raw: `exec 3>&-` → degraded mode (control channel closed). (d) vector 12: a command containing `ESC [201~`, `ESC`, or another C0 control except TAB/LF is refused by the session without writing anything to the PTY. (e) vector 11 with `TERM` set: output between `ESC [?1049h` and `ESC [?1049l` (and `ESC [?47h`/`l`) is mirrored but not captured, and capture resumes after it (drive it with `printf` of those sequences around a marker word, so the test doesn't depend on `less`). (f) a command with no output, a multi-line command, a here-doc, and a background job (`sleep 1 &`) each produce exactly one start/done pair; the background job's `D` has status 0, the session is not degraded, and after `sleep 3 &` the next snapshot's `J` is still `0` (`J` counts *stopped* jobs, and a running background job is not stopped) while the session stays usable for the next command. (g) a snapshot carries the v1 fields `T`, `B`, `X`, `P`, `J`, `H`, `V` besides `F`/`L`, the first snapshot is kept as the baseline, and changing `PS0` puts the session in degraded mode (`H` differs); so does appending an array element, `PROMPT_COMMAND+=(':')` (H is computed over every element, see Design). (h) a `~/.bashrc` in the test's temporary HOME that sets an alias and its own `PROMPT_COMMAND` → the alias is in the first snapshot and the user's `PROMPT_COMMAND` still runs, after nl-shell's hook; a `~/.bashrc` containing `bind 'set enable-bracketed-paste off'` and `set -o vi` → a two-line command still arrives byte-for-byte and gives exactly one start/done pair. (i) bash writes no history: `HISTFILE` is unset in the session. (j) control-channel wiring: inside the session `[ -p /dev/fd/3 ]` is true (fd 3 is a FIFO, not the PTY), every record read in tests (a)–(i) ends in `\n` with no `\r`, and a record containing `\r` fed to the record parser is malformed (→ degraded). (k) terminal ownership with an `os.openpty()` pair as the "real" terminal: its termios attributes are equal before and after a forwarded run; after resizing it to 40×100 and delivering `SIGWINCH`, `stty size` in the session prints `40 100`; a sentinel byte string forwarded while `cat > /dev/null` runs does not appear in the captured output, in the result object, or in any attribute of the session object (checked by scanning `vars()` recursively for the sentinel).
- Repo + branch target: eduralph/nl-shell @ main
- Scope (one logical fix) / out of scope: One session unit (new module(s) under `src/nl_shell/`) implementing pty-protocol v1 §1–§6: start `bash --noprofile --rcfile <rcfile> -i` on a PTY via ptyprocess with a pipe's write end as fd 3 in the child (§1.1); the rcfile as the spec's reference (§1.3), with two fixes stated in Design (`\\n` inside `PS0`, and `H` over every `PROMPT_COMMAND` element) plus the v1 snapshot records `T`, `B`, `X`, `P`, `J`, `H`, `V` (§3) and `bind 'set enable-bracketed-paste on'` (the spec's first open question — force it so `~/.bashrc` can't turn bracketed paste off); parse records (§2), enforce the S → D → snapshot → E order and enter degraded mode on every §4.2 trigger, with a reason, and offer a restart (a method that starts a fresh session; the REPL message is #78's); send a command as one bracketed paste + CR and refuse forbidden bytes (§5); terminal ownership (§6): a forwarding loop that, between send and done record, puts a given real terminal in raw mode, forwards its input bytes to the PTY master unchanged and keeps none of them, copies PTY output to the terminal, captures output for the caller except on the alternate screen (§6.2), copies the window size on `SIGWINCH` (§6.3), and restores the terminal afterwards. Unknown record types are ignored (spec §Versioning). Add `ptyprocess` to `pyproject.toml` `dependencies`. Update `.oss-scanner/threat_model.md` §How to exercise it (the issue asks for this): how the session tests run and that they need only bash. / out of scope: wiring into the REPL or `cli.py` (#78); the policy gate and its fd-3 / control-character rejection (#12 — the session's own refusal in (d) is defence in depth, not the gate); sudo passthrough and the per-session `SUDO_PROMPT` (#13, ADR-0015); history write-back to `~/.bash_history` (§7 — #17); taint labels and the state block (#11); a rendering filter for mirrored output (OSC 52 etc. — not owned by this issue, see Open questions); the architecture doc 05 code-layout table (one docs pass after the batch).

### Advisory — adversary

# Adversarial review: issue 10 / persistent-bash-pty-session

**Evidence re-run.** I re-ran `tests/test_session.py` on the patched target (`$PDCA_TARGET`) with the gate venv's Python: 35 passed in 10.7 s. That matches C4/T3. The red leg (gate-logs/C4-verify.log) is 35/35 `ModuleNotFoundError: nl_shell.session`. That is the expected red for a brand-new module, but it only proves the module didn't exist before. It does not prove that each test would catch a broken version of the behaviour it names. The tests do drive the production path: the real `Session`, real bash, and `os.openpty()` standing in for the terminal. I found no copy of the logic inside the tests.

I tried to break the fix with probe scripts (in the scratch dir, against the target's `src/`). Results:

- NEEDS-HUMAN [human] — **Typed-ahead input becomes part of the next confirmed command.** `src/nl_shell/session.py:517-524` forwards terminal bytes to the PTY while a command runs. If the command doesn't read them, readline picks them up at the next prompt. Then `run()` pastes the next confirmed command after them (`session.py:454`), and `_drain_pty()` at `session.py:434` can't stop this because it only drains output. Concrete case: during `run("sleep 2", terminal=t)`, write `echo INJECTED; ` (no Enter) to the terminal. The next `run("true")` returns output `'INJECTED\n'`, so bash ran `echo INJECTED; true`. A 200 KB paste gave status 127 on the next `true`. This breaks the Goal's "sends a confirmed command byte-for-byte" and spec §5.1 ("exactly the confirmed bytes"). #78's gate will confirm one string while bash runs another. Fixing it needs a decision §5.3 doesn't currently allow: clear readline's line before the paste (e.g. a kill-line byte), or stop forwarding when no process is reading. That's why I tagged this [human] rather than [impl]. No test covers typeahead.
- NEEDS-HUMAN [human] — **A typed-ahead Enter, or any syntax error or comment-only command, degrades the session.** For a line that doesn't parse, PS0 never runs, but `__nls_done` still bumps `__nls_seq` (`session.py:80`, `session.py:85`). So a `D n+1` arrives with no `S`, and `pty_protocol.py:221-222` degrades the session. Reproduced: `run("fi")` and `run("# just a comment")` both raise `SessionDegraded: control record 'D' arrived out of order (without a start record)`. So does pressing Enter during a forwarded `sleep 2` (the *next* `run("true")` raises). An unclosed quote (`echo 'abc`) degrades after the 1 s back-at-a-prompt rule. All of these fail closed, and the behaviour comes from the spec's reference rcfile (v1.md:62). But in practice an ordinary typo forces a restart, and that loses `cd`/`export` state. The brief and the tests don't mention it. A human should decide whether that's acceptable for M0, or whether to treat "D n+1 without S" as "didn't parse, not run" (a spec change).
- NEEDS-HUMAN [human] — **Capture stops for good at the first forwarded byte**, including the Ctrl-C in vector 10 (`session.py:520-522`, `_Capture.stop` at `session.py:207-211`). The brief's Scope says capture pauses only on the alternate screen. Spec §6.2 makes capture a MAY, so this is allowed. Still, an interrupted or interactive command reaches #62 (failure classes) and #11 (state block) with only partial output, flagged by `input_forwarded`. That's a product trade-off the human should confirm, not a bug.
- **Known limit, confirmed:** `run("sleep 2 & wait")` degrades with "no done record after the shell returned to a prompt" (`session.py:594-608`). The brief accepts this for `read`/`wait`. I'm listing it so the sign-off sees that ordinary `cmd & wait` hits it too, not just `read`.

Attempted and could not break:
- Prompt or user-`PROMPT_COMMAND` output leaking into captured output. 150 runs of `echo hi` with a custom PS1 and a printing user `PROMPT_COMMAND`, under 3 busy CPU loops: 0 bad.
- A forwarded paste larger than the PTY buffer hanging the loop: no hang, `run()` returned on time.
- Faking records through a `PATH` that contains a newline (`P` is the only snapshot field not passed through `tr`). An injected `J`/`H`/`F`/`E` either repeats a record type (`pty_protocol.py:234-235`) or lands in IDLE. Both degrade, so this fails closed.
- `$(sleep 2)` falsely tripping the back-at-a-prompt rule: correctly excluded by the child-process-group check (`session.py:617-626`).
- Vectors 4/5 (printed fake records) and the `\r`-is-malformed rule (`pty_protocol.py:98-101`): they hold.

Verdict: I couldn't refute the red→green evidence or the spec vectors as tested. The first finding is a real gap between the Goal's "byte-for-byte" claim and what the code does. The reviewer's pass doesn't cover it, because no test forwards input that isn't a full line.

### Advisory — security-review

# Security review — issue 10 / persistent-bash-pty-session

Attacker-reachable inputs this diff touches: **command output** (threat model item 1: the PTY stream that `session.py` mirrors and captures) and **session state** (item 4: functions, variables and hooks set by `~/.bashrc`, raw `\cmd` input or a confirmed `source`, which the rcfile hooks report as the snapshot). The control channel itself is trusted by the threat model, and writing to the inherited fd 3 from code running as the user is a listed known gap, so I don't raise it.

Checked with no finding:
- Forged records in output (vectors 4 and 5). Start, done and status come only from the fd-3 pipe (`session.py:497-516`), and the tests cover this.
- Forbidden bytes in a command. `check_command` runs before any write (`session.py:427`, `pty_protocol.py:122-138`). Test (d) covers ESC, paste-end, CR, BEL and NUL.
- Forwarded input being kept. `_forward` holds the bytes only in a local variable (`session.py:632-641`), capture stops on the first forwarded byte, and test (k) scans the session and result objects for a sentinel string.
- History. `HISTFILE` is unset, and test (i) checks it.
- The rcfile temp dir. `mkdtemp` makes it mode 0700, and it is removed once bash has read it.

Findings:

- NEEDS-HUMAN [impl] — **Medium** (threat model: "the session doesn't enter degraded mode when its hooks were changed"; it becomes **High** once #12's gate relies on `F`/`L`, because a session change then goes undetected by the gate). `target/src/nl_shell/session.py:100` and `target/src/nl_shell/pty_protocol.py:277`. **Input:** session state set by a confirmed `source` of a repository script (item 4). **What goes wrong:** `H` is a checksum of `declare -p PROMPT_COMMAND PS0` only. The code that actually runs at every prompt is outside it: the function `__nls_done` (`session.py:82`), `__nls_ret`, and the variable `__nls_user_pc`, which is `eval`'d at every prompt (`session.py:105`). A sourced script can redefine `__nls_done` to print well-formed but false `D`/`F`/`L` records (for example, an `L` that hides a newly added `alias ls='rm -rf ~'`), or put any code in `__nls_user_pc`. `PROMPT_COMMAND` and `PS0` keep the same text, so `H` matches the baseline and the session never degrades. `F` lists only function names, so a redefined `__nls_done` doesn't change it either. **Reproducer** (probed on host bash 5.3.9): with `PS0` set, `h1=$(declare -p PROMPT_COMMAND PS0|cksum); __nls_done(){ echo fake; }; __nls_user_pc='touch /tmp/x'; h2=$(declare -p PROMPT_COMMAND PS0|cksum)` gives `h1 == h2`. **Suggested fix:** in the rcfile, after the definitions, add `readonly -f __nls_done __nls_ret` and `readonly __nls_user_pc`. Probed: redefining a readonly function fails with "readonly function". Also consider adding `declare -f __nls_done __nls_ret; declare -p __nls_user_pc` to the `H` input. **Test gap:** `test_changed_hooks_degrade` (`tests/test_session.py:361`) only tries `PS0='x'` and `PROMPT_COMMAND+=(':')`. Add cases for `__nls_done(){ :; }` and `__nls_user_pc=:` that expect either degraded mode or a refused redefinition.

- NEEDS-HUMAN [human] — **Medium, possibly High** (same ratings as above). `target/src/nl_shell/session.py:82-106` (and the comment at `target/src/nl_shell/session.py:67-68`, which says `builtin`/`command` keep the hooks safe from user functions). **Input:** session state from a confirmed `source` (item 4). **What goes wrong:** bash lets a function be named `builtin` or `command`. Probed: after `builtin(){ echo "shadowed builtin: $*"; }`, `builtin printf "hi\n"` runs the function. Once such a function exists, every snapshot record is produced by attacker code: `F` (via `builtin compgen`), `L`, `T`, `B`, `H` and `V`. So the snapshot can hide the function itself and report the baseline `H`. `readonly -f` can't stop this, because there is nothing to mark readonly before the function is defined. This is a limit of reporting state from inside bash, which spec `pty-protocol/v1` §3 and ADR-0014 don't address. A human should decide whether to accept it as a known gap in the threat model (the in-shell snapshot trusts that `source`'d code didn't shadow `builtin`/`command`) or to require a different design, for example having the gate class `source`/`.` of untrusted files as session-altering and always confirmed, which ADR-0013 may already do.

- NEEDS-HUMAN [human] — **High once wired in** (threat model: "output writes the clipboard"; "What must hold: output rendering is filtered everywhere"). `target/src/nl_shell/session.py:494` and `:503`. **Input:** command output (item 1), for example `cat` of a repository file containing `\e]52;c;<base64>\a` (an OSC 52 clipboard write) or `\e[8m` (concealed text, so the user's screen hides what the capture and later the model's state block contain). **What goes wrong:** `_write_all(mirror_out, chunk)` copies PTY bytes to the real terminal with no filter. The brief puts the rendering filter out of scope, and nothing calls `run(terminal=...)` outside tests yet, so this can't be reached today. The open question in the brief says no issue owns the filter. A human should make sure one is filed and that it blocks #78, which makes the mirror user-facing.

- Unrated note (the threat model's scale has no resource-exhaustion row; not a NEEDS-HUMAN item). `target/src/nl_shell/session.py:198` and `:203` (`_Capture.data`), plus `_OutputSplitter._since_start`. Captured output grows without limit for the whole command. With `timeout=None`, a confirmed `cat` of a multi-gigabyte file from a cloned repository, or `yes`, grows nl-shell's memory until the user presses Ctrl-C or the process is OOM-killed (killed by the kernel for running out of memory). The state block only needs truncated output, so a capture cap (keep the last N KiB) would be enough. This can wait for #78/#11.

The gates passed: C4 red→green and T3 suite green (`gate-logs/C4-verify.log`, `T3-suite.log`). None of the findings above is something those gates test for.

A pipe never turns `\n` into `\r\n`. Only a tty line discipline (ONLCR) does that. So in the probe, fd 3 was most likely the PTY slave, or the probe read the PTY stream, not the pipe.
