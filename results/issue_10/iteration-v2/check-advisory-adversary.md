# Adversarial review — issue 10 / persistent-bash-pty-session (iteration 2)

The red→green evidence holds up. The iteration-1 hook-tamper fix does not: one command forges exit statuses and hides itself from the snapshot without degrading the session.

- **NEEDS-HUMAN [human] — making the hooks read-only does not stop a sourced script from forging records. A function named `builtin` hijacks every call inside the hook.** `src/nl_shell/session.py:114-115` marks `__nls_done`, `__nls_ret` and `__nls_user_pc` read-only. But every record the hook writes (`session.py:94-108`) goes through `builtin printf …` and `command tr/cksum`. In bash's default (non-POSIX) mode, a user function named `builtin` or `command` runs in place of the real one. Being read-only doesn't protect the callers from that. Run end to end against the patched `Session` (host bash 5.3.9, the real rcfile), one confirmed command did all of this:
  `builtin(){ if [[ $1 == printf && $2 == 'F %s\n' ]]; then command printf 'F %s\n' "${3//builtin /}" >&3; elif [[ $1 == printf && $2 == 'D %s %s %s\n' ]]; then command printf 'D %s 0 0\n' "$3" >&3; else command builtin "$@"; fi; }`
  Results: the session stays **not degraded**. `H` stays equal to the baseline (`1324652430 1556`, because `H` hashes the read-only functions, which never changed). `F` leaves out `builtin`. After that, `false` reports status `0`, pipestatus `(0,)`, and `(exit 7)` reports status `0`. This is exactly the threat the carry-forward named ("redefine the hook to write false `D`/`F`/`L` records while PROMPT_COMMAND and PS0 keep their text"), reached through a different name. The brief says exit codes on the control channel are *trusted*, and #12's gate will rely on `F`/`L`, so this breaks a trusted input. `test_replaced_done_hook_cannot_hide_state` (`tests/test_session.py:369`) only tries redefining `__nls_done` itself, so it passes. I tagged this `[human]`, not `[impl]`: inside bash there may be no full fix, because every defence (`unset -f`, `set -o posix`, `enable`) is itself a builtin a function can shadow. A human needs to decide whether to accept it as a known limit of in-band hooks (and record it in the threat model), or require a mitigation. Partial mitigations:
  - have the hook check `declare -F builtin command printf tr cksum` and write a poison record if any exists (that check can also be shadowed);
  - compare `F` with the baseline outside bash (useless once `F` is forged).
  At minimum, add a test that defines `builtin(){ …; }` and `command(){ …; }` and expects degraded mode, or a documented xfail.

- **Not refuted — the oversized-number fix.** `pty_protocol.py:41-45` limits numeric fields to 18 digits, and `_handle` (`pty_protocol.py:206-211`) now catches `ValueError` as well, so a 5000-digit `D` record degrades the session instead of raising. `test_oversized_numeric_field_degrades` (`tests/test_session.py:414`) tests both the tracker and a live session. Small point, not a defect: `\d` also matches non-ASCII digits (e.g. `S ٣`). `int()` accepts those, so nothing crashes, but `[0-9]` would match §2 more exactly.
- **Not refuted — tampering through the non-read-only state variables** (`__nls_seq`, `__nls_started`, `__nls_ps0`, `__nls_once`, `session.py:84-87`). Changing them only knocks the `S`/`D` sequence numbers out of step, and `_sequence` (`pty_protocol.py:225-239`) then degrades. That fails closed.

What I tried to refute and couldn't: the C4 evidence, the bounded-number parse, and the sequence-variable tampering. What I did refute: the claim that read-only hooks stop forged records (the `builtin`/`command` shadowing above).
