# Result — issue 10 / persistent-bash-pty-session

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: A session object that starts one long-lived interactive bash on a PTY with nl-shell's control channel on fd 3, sends a confirmed command byte-for-byte, and reports when it started and finished, its exit status and `PIPESTATUS`, its captured output, and the session snapshot — all from control-channel records, never from printed text. `cd` and `export` persist between commands; a running command can be interrupted with Ctrl-C; protocol violations put the session into degraded mode.
- Success criterion: `python3 -m pytest tests/test_session.py` passes on the host (real bash 5.x, no VM, no sudo), and that file covers, each with a bounded timeout (a hang fails the test, it never stalls the gate): (a) `cd /tmp` then `pwd` → the second command's captured output is `/tmp`; `export FOO=bar` then `printf %s "$FOO"` → `bar`. (b) spec §Conformance vectors 1–8 and 10 exactly as tabled: `true` → start record 1, done record `1 0 0`, then a snapshot ending in `E` · `false | true` → status 0, pipestatus `1 0` · `(exit 3)` → status 3 · `printf 'D 99 0 0\n'` and `printf '\x1b]133;D;0\x07'` → printed on the PTY, the control channel carries only the real start/done records, the reported status is 0 · `echo 'done!!'` → output `done!!` · `alias ll2='ls -la'; g(){ :; }` → the next snapshot's function list gains `g` and its aliases contain `ll2` · `PROMPT_COMMAND=:` → degraded mode within 3 s, with a reason (detected by the back-at-a-prompt rule in Design) · `sleep 5` then the Ctrl-C byte (`\x03`) forwarded to the PTY → its `D` record arrives less than 2 s after `\x03` is written, with status 130, and the session is NOT degraded (it was running an external command, not at a prompt, for the whole wait). (c) vector 9 typed raw: `exec 3>&-` → degraded mode (control channel closed). (d) vector 12: a command containing `ESC [201~`, `ESC`, or another C0 control except TAB/LF is refused by the session without writing anything to the PTY. (e) vector 11 with `TERM` set: output between `ESC [?1049h` and `ESC [?1049l` (and `ESC [?47h`/`l`) is mirrored but not captured, and capture resumes after it (drive it with `printf` of those sequences around a marker word, so the test doesn't depend on `less`). (f) a command with no output, a multi-line command, a here-doc, and a background job (`sleep 1 &`) each produce exactly one start/done pair; the background job's `D` has status 0, the session is not degraded, and after `sleep 3 &` the next snapshot's `J` is still `0` (`J` counts *stopped* jobs, and a running background job is not stopped) while the session stays usable for the next command. (g) a snapshot carries the v1 fields `T`, `B`, `X`, `P`, `J`, `H`, `V` besides `F`/`L`, the first snapshot is kept as the baseline, and changing `PS0` puts the session in degraded mode (`H` differs); so does appending an array element, `PROMPT_COMMAND+=(':')` (H is computed over every element, see Design). (h) a `~/.bashrc` in the test's temporary HOME that sets an alias and its own `PROMPT_COMMAND` → the alias is in the first snapshot and the user's `PROMPT_COMMAND` still runs, after nl-shell's hook; a `~/.bashrc` containing `bind 'set enable-bracketed-paste off'` and `set -o vi` → a two-line command still arrives byte-for-byte and gives exactly one start/done pair. (i) bash writes no history: `HISTFILE` is unset in the session. (j) control-channel wiring: inside the session `[ -p /dev/fd/3 ]` is true (fd 3 is a FIFO, not the PTY), every record read in tests (a)–(i) ends in `\n` with no `\r`, and a record containing `\r` fed to the record parser is malformed (→ degraded). (k) terminal ownership with an `os.openpty()` pair as the "real" terminal: its termios attributes are equal before and after a forwarded run; after resizing it to 40×100 and delivering `SIGWINCH`, `stty size` in the session prints `40 100`; a sentinel byte string forwarded while `cat > /dev/null` runs does not appear in the captured output, in the result object, or in any attribute of the session object (checked by scanning `vars()` recursively for the sentinel).
- Repo + branch target: eduralph/nl-shell @ main
- Scope (one logical fix) / out of scope: One session unit (new module(s) under `src/nl_shell/`) implementing pty-protocol v1 §1–§6: start `bash --noprofile --rcfile <rcfile> -i` on a PTY via ptyprocess with a pipe's write end as fd 3 in the child (§1.1); the rcfile as the spec's reference (§1.3), with two fixes stated in Design (`\\n` inside `PS0`, and `H` over every `PROMPT_COMMAND` element) plus the v1 snapshot records `T`, `B`, `X`, `P`, `J`, `H`, `V` (§3) and `bind 'set enable-bracketed-paste on'` (the spec's first open question — force it so `~/.bashrc` can't turn bracketed paste off); parse records (§2), enforce the S → D → snapshot → E order and enter degraded mode on every §4.2 trigger, with a reason, and offer a restart (a method that starts a fresh session; the REPL message is #78's); send a command as one bracketed paste + CR and refuse forbidden bytes (§5); terminal ownership (§6): a forwarding loop that, between send and done record, puts a given real terminal in raw mode, forwards its input bytes to the PTY master unchanged and keeps none of them, copies PTY output to the terminal, captures output for the caller except on the alternate screen (§6.2), copies the window size on `SIGWINCH` (§6.3), and restores the terminal afterwards. # Adversarial review: issue 10 / persistent-bash-pty-session (iteration 3)

Toolchain was available (host bash 5.3.9, ptyprocess from the system Python). I re-ran attacks against the patched code at `target/src` with `python3 -I`. pytest is not installed in the system Python, so I could not re-run the test file myself. For red→green I relied on `gate-logs/C4-verify.log`: 46 of 46 tests fail before the fix (a real `ModuleNotFoundError` inside each test, not a collection error) and all pass after it. That proof looks sound.

The round-2 items are fixed:
- `P` is now encoded (`session.py:105`).
- The control channel is drained before sending (`session.py:506`).
- Records after `E` are drained (`session.py:586`).
- Alternate-screen modes are tracked one by one (`session.py:250-260`).
- Capture is bounded (`session.py:219-226`, `311-313`).

Two attacks still break the core claim that the snapshot and status can't be forged:

- NEEDS-HUMAN [human] — **A function named `builtin` takes over the hook. The round-1 fix (readonly hooks + `builtin`/`command` prefixes) does not hold.** `session.py:78-79` says the hooks "call `builtin` / `command`, so a user alias or function named `printf` or `tr` doesn't change them". But bash lets a user define a *function* named `builtin` (or `command`), and function lookup comes before builtins. Every `builtin compgen`, `builtin alias -p`, `builtin declare` and `builtin printf` in `__nls_done` (`session.py:98-112`) then calls the user's function. `H` (`session.py:108-109`) still matches, because the readonly hook text is unchanged and the takeover lives in a different function. The `H` check (`pty_protocol.py:287`) never notices. **Reproducer (probed, host bash 5.3.9):** `run("builtin() { case $1 in compgen) command builtin \"$@\" | command grep -v -x -e builtin -e evil ;; alias) command builtin \"$@\" | command grep -v '^alias ls=' ;; *) command builtin \"$@\" ;; esac; }\nevil() { :; }; alias ls='echo pwned'")` gives `degraded=False`, `'evil' not in snapshot.functions`, `'builtin' not in snapshot.functions`, no `ls=` in `snapshot.aliases`, and `hooks_sum == baseline.hooks_sum`. The next command's `type ls` prints "ls is aliased to `echo pwned'". This is the same threat as the round-1 finding (a sourced repository script hides an alias or function from the #12 gate), reached by a different route. There is no plain in-band fix: anything the hook calls to check for the takeover (`declare -F`, `unset -f`, `set -o posix`) can itself be shadowed by a function, except special builtins in POSIX mode. A human needs to decide whether v1's in-shell snapshot is meant to resist a hostile sourced script at all, and if so, how. At minimum, the comment at `session.py:78-79` overstates what the code guarantees, and no test covers a function named `builtin` or `command`.

- NEEDS-HUMAN [human] — **A command can forge its own done record and snapshot by writing to fd 3, and `run()` returns the forgery as a success.** The command inherits fd 3 (vector 9 depends on this). After the real `S 1`, the tracker accepts the first `D 1` it sees (`pty_protocol.py:232-238`) and the next `E`. `run()` then drains only what is already in the pipe (`session.py:586`) and returns (`session.py:602-613`). **Reproducer (probed):** `run("printf '<D 1 0 0 + full snapshot with the baseline F/X/P/H/V values + E>' >&3; export LD_PRELOAD=/x.so; sleep 0.5; false")` returns `status 0` (the real status is 1), `snapshot.vars_sum == baseline.vars_sum` (hides `LD_PRELOAD`), and `degraded=False`. The real `D 1` is caught only on the *next* `run()` ("control record 'D' arrived out of order"). The pre-send drain at `session.py:506` does stop the next command from going out. But the caller (#62 failure classes, the #12 gate reading `result.snapshot` / `session.snapshot`) has already acted on a false status and snapshot. Worse: if the forging command then blocks on the tty (e.g. `read`) rather than exiting, no stray record is waiting at the next `run()`, so the next confirmed command is pasted into the still-running script's stdin. The brief's goal ("all from control-channel records, never from printed text") holds only for PTY text, not for fd-3 writes. Fixing this needs a protocol-level decision (for example, keep fd 3 away from the command, or authenticate records), so it is a spec/architecture question.

Attacks that did not refute the fix:

- `session.py:647-656` (`_drain_pty` collects chunks with no size or time limit): I tried to make it spin forever with a background `yes &` flooding the PTY. It did not hang. Each drain returned after about 40 KB and memory stayed under 26 MB. The next `run("echo hi", timeout=0.5)` timed out and degraded the session, and with `timeout=3` it took about 2.5 s. That is fail-closed, so it is not a refutation, only a latency note.
- Alternate-screen tracking (`session.py:250-260`): mismatched resets (`?1047h` closed by `?1049l`, or `?1049h` closed by `?47l`) leave capture paused. That loses output but never captures alternate-screen text. Not a leak.
- Tampering with `__nls_seq`, `__nls_ps0` or `__nls_once` gives a sequence mismatch or a missing `S`, and the session degrades (`pty_protocol.py:226-239`). Not exploitable.
- Newlines or `\x1e` in `PATH`, aliases or traps can no longer inject records: every free-text field goes through `tr` (`session.py:100-105`).

### Advisory — security-review

# Security review — issue 10 / persistent-bash-pty-session (iteration 3)

**Attacker-reachable inputs this diff touches:** command output on the PTY (threat model item 1: captured, mirrored, split on alternate-screen switches) and session state (item 4: aliases, functions, `PATH`, hooks set by `~/.bashrc`, raw `\cmd` or a confirmed `source`), which the rcfile's hooks report as the `F`/`L`/`T`/`B`/`X`/`P`/`J`/`H`/`V` snapshot. The control channel itself is trusted, but its *contents* are written by shell code that session state can reach.

Severity uses the threat model's scale. Like earlier rounds, snapshot findings are rated **Medium now, High once #12's gate reads the snapshot** ("a session change (alias, function, hook) goes undetected by the gate").

- NEEDS-HUMAN [human] — **Medium now / High with #12.** `src/nl_shell/session.py:93-116` (the `__nls_done` hook) and `session.py:118`. **Input:** session state from a confirmed `source` or raw `\cmd` (item 4). **What goes wrong:** every snapshot record is written through `builtin …` and `command …`, but bash looks up a *function* named `builtin` or `command` before the real builtin, at call time. Turning off `expand_aliases` while the hook is defined has no effect on that. `readonly -f __nls_done __nls_ret` stops the hook from being redefined, but not the names it calls. A function `builtin` can filter what `compgen -A function` and `alias -p` return, which hides itself from `F` and hides any new alias from `L`. `PROMPT_COMMAND`/`PS0` keep their text, so `H` still matches and the session never degrades. **Reproducer** (run against the patched tree, host bash 5.3.9): `run("alias ls='echo PWNED'\nbuiltin() { if [[ $1 == compgen ]]; then command builtin compgen \"${@:2}\" | grep -vx -e builtin; elif [[ $1 == alias ]]; then :; else command builtin \"$@\"; fi; }")` → snapshot `F` = `('__nls_done','__nls_ret','command_not_found_handle')` (same as the baseline), `L` = `()`, `H` same as the baseline, `degraded=False`. Then `run("ls")` prints `PWNED`. `enable -f <lib.so> printf` (a loadable builtin that replaces `printf`) belongs to the same class; I didn't probe it. **Why [human]:** this is the same "in-shell code reports on itself" problem the last two rounds patched one hole at a time (readonly hooks, encoded `P`). Any check written in bash can be shadowed by bash code that ran earlier. Someone has to decide whether ADR-0013/pty-protocol v1 should treat a snapshot as trustworthy after a confirmed `source`, or whether to add a structural defence. Options: degrade whenever a function exists whose name matches a builtin or keyword the hook calls (checked in POSIX mode, where special builtins like `unset` beat functions), or accept the limit and document it under Known gaps. **Test gap:** `test_changed_hooks_degrade` (around `tests/test_session.py:420`) only tries `__nls_user_pc`. It has no case that shadows `builtin`/`command`.

- NEEDS-HUMAN [impl] — **Medium now / High with #12.** `src/nl_shell/session.py:100-111` (`command tr`, `command cksum`). **Input:** session state (item 4). **What goes wrong:** `command` skips functions but still uses bash's command hash table. `hash -p /path/fake cksum` (or `BASH_CMDS[cksum]=…`, or `tr`) swaps the program that computes `H`/`V` or encodes `L`/`T`/`B`/`P`. Neither the hash table nor `BASH_CMDS` appears in any snapshot field. **Reproducer** (probed, patched tree): write a script `fakecksum` that does `cat >/dev/null; echo '<baseline H>'`, then `run("hash -p $PWD/fakecksum cksum; PROMPT_COMMAND='__nls_done; __nls_started=1; echo HIJACK'")` → `H` equals the baseline, `degraded=False`, and the next `run("echo hi")` succeeds with the changed `PROMPT_COMMAND` in place. **Suggested fix:** don't call external programs from the hook. Bash can do the newline-to-`\x1e` change itself (`${var//$'\n'/$'\x1e'}`). Or call them by absolute path, which skips both `PATH` and the hash table. Add a test that does `hash -p` on `cksum` and on `tr`, and expects degraded mode or an unchanged honest snapshot.

- NEEDS-HUMAN [human] — **Medium / High with #12; reasoned, not probed.** `src/nl_shell/session.py:108-111` and `src/nl_shell/pty_protocol.py:287`. **Input:** session state (item 4). **What goes wrong:** `H` and `V` are `cksum` values: CRC-32 (a 32-bit checksum built to catch accidental errors, not tampering) plus a byte count. CRC-32 is linear, so a script can pick a new `PROMPT_COMMAND` or `LD_PRELOAD` of the same length, with 4 filler bytes chosen to give the same CRC. `H` then matches the baseline and the change goes unnoticed. The spec asks for `cksum` (`docs/design/specs/pty-protocol/v1.md:94`), so this is a spec choice, not a builder slip. A fix would send the raw `declare -p` text (encoded like `L`) for nl-shell to compare, or use a real hash. That needs a spec decision. I didn't build a collision, so this finding is unconfirmed.

Checked with no finding:
- **Forwarded input is never kept** (`_forward`, `session.py:719-728`): the bytes live only in a local variable, and capture stops before the PTY can echo them.
- **Forged records on the PTY:** start, done and status come only from fd 3.
- **Newline injection through `P`:** fixed. `P` is encoded, and `run()` now drains the control channel and degrades before sending (`session.py:502-508`).
- **Out-of-range numbers:** they are bounded by `_NUM`, and `ValueError` is caught and degrades the session (`pty_protocol.py:41,209`).
- **Alternate screen:** capture resumes only after the matching reset (`session.py:250-260`).
- **Captured output** is capped at `MAX_OUTPUT`, and so is the buffer before the line is accepted.
- **`check_command`:** it refuses `ESC`, other C0 controls and `ESC [201~` before anything is written.
- **Background-job flood:** `run("yes … &")` followed by `run("true", timeout=2)` returned in 0.05 s, with no hang and no memory growth.
- **Not raised:** the unfiltered mirror (OSC 52 and similar) is out of scope by the brief and flagged under its Open questions. Children inheriting fd 3 is a Known gap.
