# Plan review: issue #10 / persistent-bash-pty-session

- NEEDS-HUMAN — **The probe's `S 1\r\n` result points to a wiring defect, and the brief tells Do to work around it.** Brief, Design: "The start record arrived as `S 1\r\n`, not `S 1\n`: the record parser must handle that". fd 3 is supposed to be a pipe (spec `pty-protocol/v1.md:35`, `:42-43`), and the reference rcfile writes `printf "S %s\n" … >&3` (`v1.md:59`). A pipe never turns `\n` into `\r\n`. Only a tty line discipline (ONLCR) does that. So in the probe, fd 3 was most likely the PTY slave, or the probe read the PTY stream, not the pipe. That would also cast doubt on the probe's vector-4 result. If the parser accepts `\r\n`, it hides the one property the spec exists for (printed text can't forge records). It also conflicts with §Conventions ("`\n`-terminated") and §4.2 ("malformed → degraded"). Fix the brief: drop the "must handle that" instruction, and require Do to assert that fd 3 in the child is a FIFO (e.g. `[ -p /dev/fd/3 ]` or `stat` in a test), and that a `\r` in a record is malformed.

- NEEDS-HUMAN — **Vector 8 needs a "back at a prompt" signal, and the brief doesn't say where it comes from.** Success (b): "`PROMPT_COMMAND=:` → degraded mode at the next prompt, with a reason". Spec §4.2 trigger: "no `D` arrives after the shell is back at a prompt" (`v1.md:106`). After `PROMPT_COMMAND=:`, the session sees `S 1` and then nothing. Without a second signal, that looks the same as a long-running `sleep 5` (vector 10). The brief forbids parsing the PTY stream ("Never parse the PTY stream for them"), and it gives no other mechanism. One option is the PTY's foreground process group (`os.tcgetpgrp(master) == bash pid` means bash is back at readline). Another is a timeout, but a timeout would wrongly degrade every slow command. Do will have to invent this rule in the critical path. The brief should name the mechanism and add a test that a long command (vector 10) does **not** trigger degraded mode.

- NEEDS-HUMAN — **One adversarial row from the thread is missing.** The thread's sharpened done-when (notes.json): "adversarial rows: output that prints a marker, a command with no output, **a background job**, a here-doc, multi-line input." Brief (f) covers no-output, multi-line and here-doc, but has no background-job test. It matters here: a background job inherits fd 3, so it can keep the pipe open (vector 9's "control channel closed" depends on EOF). Its `[1]+ Done` notice also appears at a later prompt. Add a test such as `sleep 1 &` → exactly one S/D pair, status 0, and then `J` in the snapshot.

- NEEDS-HUMAN — **The thread declares dependencies that the brief doesn't record.** notes.json: "**Depends on** #65 (PTY protocol) and #19." The brief has no `Depends on` line, and there is no `dependency-state.json` in the bundle. In content, both look satisfied on `main`: the spec exists with `tracking-issue: "#65"` (`v1.md:7`), and ADR-0014 answers #19 (`0014-pty-session-protocol.md:69-70`). However, the spec is `status: draft` / `stability: unstable` (`v1.md:4-6`), and the ADR is `Proposed`. The brief should either declare #65 or explicitly record why it is treated as met (the M0-builds-against-Proposed rule, #95). As written, the thread and the brief disagree. The thread's other instruction ("completion … from OSC 133 markers") is correctly overridden by ADR-0014, and the brief's Alternatives section covers that.

- NEEDS-HUMAN — **(g)/(h) rely on `H`, but `H` misses `PROMPT_COMMAND` array elements (bash ≥ 5.1).** Spec §3: `H` is "a `cksum` of `$PROMPT_COMMAND` and `$PS0`" (`v1.md:94`), and the rcfile saves `__nls_user_pc=$PROMPT_COMMAND` (`v1.md:56`). On the target bash 5.3.9, `PROMPT_COMMAND` can be an array, and `$PROMPT_COMMAND` expands only element 0. Two consequences:
  1. A command like `PROMPT_COMMAND+=('evil')` adds a hook without changing `H`. The threat model rates this High: "a session change (… hook) goes undetected" (`.oss-scanner/threat_model.md:192`).
  2. A user `~/.bashrc` that sets an array keeps its extra elements running, but `__nls_user_pc` drops them.

  The brief says to follow the spec "as written", so this is a spec hole, not a brief deviation. Still, (g)/(h) as phrased will pass while this bypass stays open. Decide whether to compute `H` over `"${PROMPT_COMMAND[@]}"` (a spec note via build-notes), or to record it as a known gap.

- NEEDS-HUMAN — **Several parts of the scope have no test in the success criterion.** Scope requires: copying the window size on `SIGWINCH` (§6.3), restoring the terminal after raw mode, a restart method, and "forwarded input bytes are never stored, logged or included in captured output" (Design). Criteria (a)–(i) test none of these. The last one matters most, because it is the property #13's sudo password depends on. Two options:
  - Add red→green checks, e.g. forward a sentinel byte string while `cat` is not reading it, then assert the sentinel is absent from captured output and from the session object's state; resize the openpty and `stty size` sees it; termios attrs are equal before and after the run.
  - Or move these items out of scope.

  The brief's own Open question already considers splitting terminal ownership into a separate slice. Untested scope is where that split pays off.

- NEEDS-HUMAN — **Scope also settles one of the spec's open questions.** "Force `bind 'set enable-bracketed-paste on'`" answers spec Open question 1 (`v1.md:170-171`: "probably force … ; to verify"). That is a reasonable call, but it is a protocol decision made inside an implementation bundle, and no criterion verifies it. Examples of a check: a `~/.bashrc` with `bind 'set enable-bracketed-paste off'` or `set -o vi`, and then vector 6 or a multi-line command still arrives byte-for-byte. Without such a check, it is unverified extra surface.

- NEEDS-HUMAN — **Vector 10's success criterion is vague.** "finishes well under 5 s with status 130". "Well under" isn't a threshold a gate can check. State a bound, e.g. `D` arrives < 2 s after `\x03` is written, inside the per-test timeout.
