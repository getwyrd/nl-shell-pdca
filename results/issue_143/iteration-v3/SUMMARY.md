**Findings**

- NEEDS-HUMAN [impl] — `tests/test_backend.py:493-503`: the hidden-character vectors test only one point inside each range, so narrowing the predicate in `src/nl_shell/render.py:39-47` would not turn the suite red. Three examples:

  - Dropping `0x2029` from `LINE_AND_PARAGRAPH_SEPARATORS` still passes. U+2029 is category Zp, not Cf, so nothing else catches it, and a terminal that breaks the line there would show an unprefixed line inside the framed proposal.
  - Cutting `TAG_BLOCK` short (anything above U+E0041) still passes.

  The test file mentions U+009B, U+2029 and U+E007F only in its own oracle (`tests/test_backend.py:63-66`), never as input. Fix: add U+009B, U+2029, U+E007F, U+0000/U+001F and U+061C to `HIDDEN`. The JSON parser rejects repeated keys (`src/nl_shell/proposal.py:157-161`), so the two loaders treat the same mistake differently. The brief does not require rejecting repeated YAML keys, so this is not a defect against the success criterion.

# Security review (advisory) — issue 143, prompts YAML / `:context` / recording stub

Attacker-reachable input this diff touches: **the model's raw response** (threat model "Where untrusted input enters" item 5), which goes through `proposal.parse` (`src/nl_shell/proposal.py:574-624`) into `show_proposal` (`src/nl_shell/repl.py:777-791`) and out through the REPL-wide escape (`src/nl_shell/repl.py:124`). Nothing else on the attacker's side: the request text is typed by the user (trusted), the state block slot is still empty (`src/nl_shell/prompts.py:301`), and both prompts files are trusted (the target's own `prompts/` and nl-shell's config in the user's home, `threat_model.md:100-101`). Nothing runs yet, so the Critical "what runs" rows can't be reached.

**No finding.** What I checked:

- **Hidden characters in a proposal (must-hold "What the user confirms is exactly what runs", `threat_model.md:127-130`).** `render.is_hidden` (`src/nl_shell/render.py:671-684`) flags C0 except LF/TAB, DEL, C1, the bidi controls, all of Cf, U+2028/2029, the tag block and surrogates. The parser rejects any `command` holding one (`src/nl_shell/proposal.py:611-612`). VT, FF, CR, NEL and U+2028 are all rejected, so `split("\n")` at `repl.py:782` is the only line break a terminal will honour. Every line gets the `  | ` prefix, so a model can't print an unprefixed `Proposed command (...)` line. Tests: `HIDDEN` × `ensure_ascii` True/False, the frame-spoof test, and the TAB test. No gap.
- **Spoofing the UI through other fields.** `risk` and `reason` are checked against the schema enums before they are shown (`proposal.py:600-604`, `_enum` at `:627-631`). `Rejected.why` is never printed. The reply text for `clarify`/`refuse` comes from fixed templates (`repl.py:767-774`). The model can't put free text on screen except inside the prefixed command lines.
- **Strict parsing (no repair).** Duplicate keys are rejected (`proposal.py:563-567`, tested: `duplicate-key`, the last-key-wins vector). NaN/Infinity are rejected via `parse_constant`. Huge integers and deep nesting become `Rejected` instead of a crash (`proposal.py:589-591`; tested: `huge-integer`, `deep-nesting` 100000). A lone surrogate is rejected before it can raise `UnicodeEncodeError` on a UTF-8 stream (tested with `TextIOWrapper` over `BytesIO`). I found no model response that crashes the REPL.
- **Resource use.** `command` is capped at 2000 code points. The raw response has no size cap, but a real model's token limit bounds it and the backend is #77's. Not worth filing as a finding here.
- **Output filter (must-hold "Output rendering is filtered everywhere", `threat_model.md:132-134`).** `:context` escapes both hidden characters and backslashes (`prompts.py:469-474`), so a real ESC and a typed `\x1b` print differently (tested). Every REPL reply also goes through `render.escape` (`repl.py:124`; tested by `test_every_repl_reply_escapes_hidden_characters`, which closes the iteration-1 finding). Start-up errors go through `_error` (`src/nl_shell/cli.py:141-143`), which covers #92's `NoMatchingTarget`, the config/target errors and the new prompts error (tests with U+202E for both the prompts and `target.toml` paths). PyYAML error snippets include file text but are escaped there.
- **YAML loading.** Only `yaml.safe_load` is used (`prompts.py:380`). The `!!python/object/apply` vector is tested to leave no `pwned` file. `ValueError` and `RecursionError` from the safe loader become `PromptsError` (`prompts.py:383-388`; tested with `deep-nesting`). These are trusted files anyway, so this is about not crashing, not about an attacker.
- **Secrets.** Nothing in this diff takes in environment, command output or the sudo password. `:context` shows only the system prompt, the examples and the user's own request.

Notes, not findings (no severity, nothing to do in this diff):

- `_error` escapes without `backslash=True` (`cli.py:143`). So a config path that holds the literal six characters `‮` prints the same as one holding a real U+202E. The paths and config are trusted, and the brief asks for the backslash form only in `:context`, so this is at most Low (error-message ambiguity from the user's own setup).
- `RecordingStub.complete` raises `StubExhausted` (`src/nl_shell/backend.py:87-88`), and `Repl._propose` (`repl.py:869`) doesn't catch backend errors. This is test-only today. When #77 wires a real backend, a socket or HTTP error from it would end the REPL unless #77 catches it. That's for #77's review.
- The `--- <role> ---` separator could be spoofed in `:context` once #11 puts untrusted state text into the user message. The brief already puts that on #11, out of scope here.

The gate evidence agrees: T3 ran 398 passed (`gate-logs/T3-suite.log`), C4 was red before the fix and green after, and T2 shows the threat model was updated. The updated threat-model lines (`threat_model.md:127-130`, `:199-202`) match what the code does.
