- Defect / goal: Goal (new functionality). Natural-language input and `@request` build the model input from an editable prompts YAML, send it to a model backend, and parse the answer strictly as a `proposal/v1` object, which the REPL shows without running it. A recording stub backend returns fixed responses and records every model input it was sent (#13 relies on this). `:context` shows the exact model input of the last request; `:status` lists the loaded prompt files. # Adversarial review — issue #143 (iteration 4)

pytest is not installed on this host, so I could not re-run the suite. I judged the red→green proof from `gate-logs/C4-verify.log` (red leg: 100 of 193 failed, collection errors 0; green leg: 193 passed) and `gate-logs/T3-suite.log` (410 passed). I checked the mutation results below by comparing `render.is_hidden` against narrowed copies of it, using every `HIDDEN` vector. That is the same thing those parametrized tests check.

- NEEDS-HUMAN [impl] — `tests/test_backend.py:493-509` still lets a narrowing of the tag block go unnoticed, which is exactly the gap the round-3 carry-forward asked to close. If `TAG_BLOCK` at `src/nl_shell/render.py:29` is changed to `range(0xE0001, 0xE0080)`, or even to `range(0xE0020, 0xE0080)`, no `HIDDEN` vector changes result. The suite would stay green. This one matters because the Cf (Unicode "format character") fallback at `src/nl_shell/render.py:46` does **not** catch these code points: U+E0000 and U+E0002–U+E001F are category Cn (unassigned), not Cf. So the mutation really would let 31 code points through to the screen and past the parser. The new vector `tag-last-ue007f` only pins the top end. Concrete fix: add `"tag-first-ue0000": ("\U000e0000", "\\U000e0000")`, and maybe U+E0002, to `HIDDEN`. Production is correct today: `is_hidden(chr(0xE0000))` returns True and escapes to `\U000e0000`.
- NEEDS-HUMAN [impl] — The same test gap exists at the top of the C1 range. If `0x7F <= code <= 0x9F` at `src/nl_shell/render.py:41` is narrowed to `<= 0x9E`, or even `<= 0x9B`, every `HIDDEN` vector still gives the same result, because the C1 vectors are only U+0085 and U+009B. U+009F is category Cc, so the Cf fallback doesn't catch it either. Concrete fix: add a `c1-last-u009f` vector. (The sign-off listed U+009B and not U+009F, so the builder did what was literally asked. But the sign-off's stated goal, "narrowing `render.is_hidden` would turn the suite red", is still not met.)
- Unwarranted claim to watch: the round-3 carry-forward says the added vectors close the range-narrowing gap. They close it for C0 (U+0000/U+001F kill `code < 0x1f`), DEL, ALM (U+061C, the Arabic letter mark bidi control) and U+2029. They do not close it for the two ends above. Taking out `BIDI_CONTROLS` (`src/nl_shell/render.py:42`) also survives, but that is harmless: every member is Cf, and the comment at `render.py:23-24` says the list is only there as a hedge against changes in the Unicode version.
- Evidence attack, could not refute: the `:context` oracle (`tests/test_backend.py:54-91`) copies the predicate's ranges rather than calling `render`. The brief requires this. Each hidden-character test also asserts `char not in out` (`tests/test_backend.py:533`), so a production narrowing that the oracle shares would still fail on the raw character, as long as a vector covers that range. The red leg's failures are real assertion failures, not import errors: per the log, "import/collection errors 0". The in-function imports work as designed.
- Fix attack, could not refute: `prompts.volatile` (`src/nl_shell/prompts.py:198-202`) is safe given what `_request_template` (`prompts.py:176-188`) enforces: exactly one `{state}`, exactly one `{request}`, and the template ends with `{request}`. A request holding `{state}` or `{request}` is spliced in as typed, not filled in. `_read` (`prompts.py:127-131`) now catches `ValueError`/`RecursionError` as well as `YAMLError`. `proposal._parse` (`src/nl_shell/proposal.py:105-111`) rejects deep nesting, huge integers, NaN/Infinity and duplicate keys. I found no input that gets a hidden character into a shown `command`.

Summary: production code holds up under every attack I tried. The only findings are two test-strength gaps (tag-block start and C1 end) left over from the round-3 request. Both are cheap to fix by adding vectors. The verdict is provisional on pytest not being available here, but the gate logs are consistent with the claims.

# Security review (advisory) — prompts YAML, `:context`, recording stub (#143)

Attacker-reachable inputs this diff touches: **the model's raw response** (threat model "Where untrusted input enters" item 5), parsed by `src/nl_shell/proposal.py:168` and shown by `src/nl_shell/repl.py:52-66`. The other new inputs are trusted under the threat model: the prompts YAML files (the user's own config and the shipped target default, "Trusted" list, `.oss-scanner/threat_model.md:100-101`) and the request text the user types. They are still escaped on output, which I checked as defence in depth.

## Findings

No findings. What I checked:

- **Hidden characters in a proposal (must-hold "What the user confirms is exactly what runs", `threat_model.md:127-130`).** `proposal._parse` rejects any `command` that `render.has_hidden` flags (`src/nl_shell/proposal.py:205-206`). I fed crafted responses to the patched parser. U+0085 (NEL, a C1 control), U+00AD (soft hyphen, Cf) and U+FFF9 (Cf) were rejected. A real surrogate pair (`"😀"`) was accepted as one emoji, which is correct. The lone-surrogate, ESC, CR, DEL, U+202E, U+200B, U+FEFF, U+2028 and tag-block cases are in the suite, along with the iteration-3 boundary vectors U+0000, U+001F, U+009B, U+061C, U+2029 and U+E007F (`tests/test_backend.py:493-509`).
- **Spoofing the proposal frame (rating High if it worked: "spoofs the confirm UI").** A `command` of `ls\nProposed command (risk: read-only, 1 line):\n  | rm -rf /` prints every line behind `  | ` (`src/nl_shell/repl.py:57-60`), and the line count says 3. CR is rejected, so a line can't be overwritten in place. No spoof.
- **Parser crash or hang from model output.** Invalid JSON, a number with more than 4300 digits (`ValueError`) and deep nesting (`RecursionError`) all become `Rejected` (`src/nl_shell/proposal.py:183-185`). Duplicate keys and `NaN`/`Infinity` are rejected (`:157-165`). `1e999` turns into `inf` but can only end up in an enum field, where any non-string is rejected (`:221-225`). `Rejected.why` is never printed, so no model text gets out through it.
- **Output filter (must-hold "Output rendering is filtered everywhere", `threat_model.md:132-134`).** Every REPL reply goes through `render.escape` (`src/nl_shell/repl.py:124`). `:context` escapes hidden characters and backslashes (`src/nl_shell/prompts.py:216-221`). Start-up errors, including YAML parser messages that quote file text, go through `cli._error` → `render.escape` (`src/nl_shell/cli.py` `_error`). Running the outer escape again over `:context` text that is already escaped changes nothing, because escaping with `backslash=False` leaves plain ASCII as it is.
- **YAML loading.** Only `yaml.safe_load` is used (`src/nl_shell/prompts.py:127`). The `!!python/object/apply` vector is tested. The file is trusted config in any case, so alias-expansion or size problems would at most be Low (a misconfiguration the user made).
- **Accepted but out of scope.** The parser accepts U+034F (combining grapheme joiner), U+115F and U+3164 (Hangul fillers) and U+00A0 (no-break space) in a `command`. The brief hands Default_Ignorable code points outside Cf, blank glyphs and non-ASCII whitespace to #144 (`brief.md` Scope, out of scope), so I am not filing these here. #144 should cover them before #74/#78 put a proposal in front of the user to confirm.
- **Not yet reachable.** `RecordingStub.complete` raises `StubExhausted` straight out of `Repl._propose` (`src/nl_shell/backend.py:263-264`, `src/nl_shell/repl.py:150`). That only happens in tests. The real backend (#77) will need its own error handling, but this diff doesn't create that path.

Gates: C4 and T3 pass (T3: 410 passed, `gate-logs/T3-suite.log`). T2 confirms the threat model was updated for `backend.py`.
