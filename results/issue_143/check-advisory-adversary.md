# Adversarial review — issue #143 (iteration 4)

pytest is not installed on this host, so I could not re-run the suite. I judged the red→green proof from `gate-logs/C4-verify.log` (red leg: 100 of 193 failed, collection errors 0; green leg: 193 passed) and `gate-logs/T3-suite.log` (410 passed). I checked the mutation results below by comparing `render.is_hidden` against narrowed copies of it, using every `HIDDEN` vector. That is the same thing those parametrized tests check.

- NEEDS-HUMAN [impl] — `tests/test_backend.py:493-509` still lets a narrowing of the tag block go unnoticed, which is exactly the gap the round-3 carry-forward asked to close. If `TAG_BLOCK` at `src/nl_shell/render.py:29` is changed to `range(0xE0001, 0xE0080)`, or even to `range(0xE0020, 0xE0080)`, no `HIDDEN` vector changes result. The suite would stay green. This one matters because the Cf (Unicode "format character") fallback at `src/nl_shell/render.py:46` does **not** catch these code points: U+E0000 and U+E0002–U+E001F are category Cn (unassigned), not Cf. So the mutation really would let 31 code points through to the screen and past the parser. The new vector `tag-last-ue007f` only pins the top end. Concrete fix: add `"tag-first-ue0000": ("\U000e0000", "\\U000e0000")`, and maybe U+E0002, to `HIDDEN`. Production is correct today: `is_hidden(chr(0xE0000))` returns True and escapes to `\U000e0000`.
- NEEDS-HUMAN [impl] — The same test gap exists at the top of the C1 range. If `0x7F <= code <= 0x9F` at `src/nl_shell/render.py:41` is narrowed to `<= 0x9E`, or even `<= 0x9B`, every `HIDDEN` vector still gives the same result, because the C1 vectors are only U+0085 and U+009B. U+009F is category Cc, so the Cf fallback doesn't catch it either. Concrete fix: add a `c1-last-u009f` vector. (The sign-off listed U+009B and not U+009F, so the builder did what was literally asked. But the sign-off's stated goal, "narrowing `render.is_hidden` would turn the suite red", is still not met.)
- Unwarranted claim to watch: the round-3 carry-forward says the added vectors close the range-narrowing gap. They close it for C0 (U+0000/U+001F kill `code < 0x1f`), DEL, ALM (U+061C, the Arabic letter mark bidi control) and U+2029. They do not close it for the two ends above. Taking out `BIDI_CONTROLS` (`src/nl_shell/render.py:42`) also survives, but that is harmless: every member is Cf, and the comment at `render.py:23-24` says the list is only there as a hedge against changes in the Unicode version.
- Evidence attack, could not refute: the `:context` oracle (`tests/test_backend.py:54-91`) copies the predicate's ranges rather than calling `render`. The brief requires this. Each hidden-character test also asserts `char not in out` (`tests/test_backend.py:533`), so a production narrowing that the oracle shares would still fail on the raw character, as long as a vector covers that range. The red leg's failures are real assertion failures, not import errors: per the log, "import/collection errors 0". The in-function imports work as designed.
- Fix attack, could not refute: `prompts.volatile` (`src/nl_shell/prompts.py:198-202`) is safe given what `_request_template` (`prompts.py:176-188`) enforces: exactly one `{state}`, exactly one `{request}`, and the template ends with `{request}`. A request holding `{state}` or `{request}` is spliced in as typed, not filled in. `_read` (`prompts.py:127-131`) now catches `ValueError`/`RecursionError` as well as `YAMLError`. `proposal._parse` (`src/nl_shell/proposal.py:105-111`) rejects deep nesting, huge integers, NaN/Infinity and duplicate keys. I found no input that gets a hidden character into a shown `command`.

Summary: production code holds up under every attack I tried. The only findings are two test-strength gaps (tag-block start and C1 end) left over from the round-3 request. Both are cheap to fix by adding vectors. The verdict is provisional on pytest not being available here, but the gate logs are consistent with the claims.
