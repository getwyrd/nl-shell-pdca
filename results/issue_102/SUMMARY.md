# Result — issue 102 / session-terminal-ownership

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: While a command runs, child-1's session does not own the user's real terminal, so interactive programs, keyboard Ctrl-C and window resizes don't work and keys typed during a command have no defined fate. Implement spec `pty-protocol/v1` §6 on top of child-1's session, with the real terminal injectable (its fds) so tests can use an `os.openpty()` pair: between sending a command and its `D` record, put the real terminal in raw mode and forward every input byte to the PTY master unchanged, never logging, capturing or keeping a forwarded byte (§6.1); copy PTY output to the real terminal and capture it except on the alternate screen — capture stops on `ESC [?1049h` / `ESC [?47h` / `ESC [?1047h` and resumes only on the matching reset (§6.2 lists only `?1049`/`?47`; `?1047` is the third xterm alternate-screen mode and the strict pairing is this brief's reading of "the matching reset" — update §6.2 wording to name all three and the pairing); on `SIGWINCH` copy the real terminal's size to the PTY (§6.3); control keys travel as bytes (§6.4); restore the real terminal's mode on every exit path (§6.5). Forwarding window: spec §6.1 governs — from when the paste is sent to the `D` record (ADR-0014 Decision 4's "from the start record" is the looser summary; the spec's window is the wider one and closes the paste→`S` gap). Decisions (parent brief `results/issue_10/brief.md:52-56`, human 2026-10-15): (6) typed-ahead input never joins the next confirmed command — forwarding stops at the `D` record, and input forwarded during the command that nobody consumed is discarded before bash reads its next line. **Mechanism (chosen here):** nl-shell's prompt hook, after it writes `D` and the snapshot records and as its LAST step before writing `E`, drains bash's stdin with builtins only: a loop of `builtin read -r -s -N 4096 -t 0.05` that ends at the first read returning nothing within 50 ms (`read -N` reads in non-canonical mode, so a partial line with no Enter is drained too; `builtin` so a user function named `read` from `~/.bashrc` cannot replace it). It must sit before `E`, not after: nl-shell may write the next paste as soon as it reads `E`, and a drain after `E` would eat it. nl-shell side: the forwarder watches fd 3 together with real-terminal input, checks fd 3 before every write to the session master, writes in chunks of at most 1 KB, and stops forwarding the moment it reads `D`. §5.1's send sequence is unchanged and the mechanism is the same in emacs and vi mode. **Residual race (not a guarantee):** a byte forwarded after bash wrote `D` but before nl-shell read it, that lands after the drain's final 50 ms quiet window, reaches readline and is prepended to the next paste. It needs nl-shell to lag more than the snapshot time plus 50 ms in reading `D`. This brief does not close it; spec §6.1 and the threat model Known gaps must name it, and the human decides at sign-off whether it is acceptable for v1 (see NEEDS-HUMAN note at the end). The exact fix (Option A) is a back-channel: the hook blocks on a second pipe (fd 4) until nl-shell acks "forwarding stopped", then drains. It is not taken here because it changes the start-up command (`v1.md:165`, versioning) and adds an fd confirmed code can close or read; it is the follow-up if the human rejects the race. Interaction with #141: `H` holds nl-shell's hook functions' `declare -p` text compared against the session's OWN baseline, so the drain in the hook body is part of the baseline and does not trigger the tamper check; `read` is in #141's `HOOK_BUILTINS`, so `enable -n read` degrades the session (that is the accepted outcome for a disabled drain). Rejected: sending readline kill keys before the paste (vi mode needs `ESC`, which §5.2 bans, and it changes §5.1); `tcflush` from the master side (not shown to reach the slave's pending input). Unforwarded bytes still queued in nl-shell at `D` are dropped, never kept (§6.1); (7) capture stops at the first forwarded byte for the rest of that command, and the result carries a flag saying so.

# Adversarial review — session-terminal-ownership (iteration 4)

This round changes one thing: the 0x9b / UTF-8 fix in `_AltScreen`, plus the threat-model line for the Ctrl-C race. I tried to break both. The evidence holds up. The fix does what the human asked for, but it closes only part of the bypass the human described.

- **Fix: the cases the human named are closed.** I ran `_AltScreen` from `target/src` on `C3 9B` (Û), `D1 9B` (ћ), the 3-byte `E2 80 9B`, the 4-byte `F0 9F 98 9B` and a lead byte split across reads (including after a 5000-byte chunk, past `_HOLD_LIMIT`). All are treated as text, whole or split. `_c1_csi_at` (`src/nl_shell/session_terminal.py:79-98`) looks back at most 3 bytes, which covers a 4-byte character. `_before` keeps 3 bytes from the last read (`:161`), so a split never loses the lead byte.

- NEEDS-HUMAN [human] — `src/nl_shell/session_terminal.py:96` and `:85` (`_c1_csi_at` returns True for "a stray 0x9b"). The human's bypass still works if a different byte comes before the 0x9b. A stray 0x9b is one with no open UTF-8 lead byte before it: after ASCII (`A\x9b`), after a finished character (`À\x9b` = `C3 80 9B`), or after a byte that can never start a character (`F5 9B`, `C0 9B`). The test at `tests/test_session_terminal.py:225` (`A\x9b?47h…` → `AB`) treats this as the intended behaviour. The builder followed the human's first option exactly ("no 0xC2-0xF4 lead byte before it"). The human's other option, "drop 8-bit CSI matching" (keep only C2 9B), would close this gap. The cost is that a real raw-C1 switch on a non-UTF-8 terminal would be missed. Which terminals to target is a scope call, so this is tagged [human]. Impact is low: captured output is already untrusted, and nothing crosses a confirm.

- **Threat-model line: present.** `.oss-scanner/threat_model.md:226` names the Ctrl-C-at-command-end race and says the session stays degraded until `restart()`, as the sign-off asked. Spec `docs/design/specs/pty-protocol/v1.md:449-450` describes the new 0x9b rule.

I reviewed that change against the threat model. The human accepted the drain race, the Ctrl-C-at-end race and the unfiltered mirror for v1, so I do not raise them again.

**No new finding.** What I checked:
