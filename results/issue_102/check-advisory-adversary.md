# Adversarial review — session-terminal-ownership (iteration 4)

This round changes one thing: the 0x9b / UTF-8 fix in `_AltScreen`, plus the threat-model line for the Ctrl-C race. I tried to break both. The evidence holds up. The fix does what the human asked for, but it closes only part of the bypass the human described.

- **Evidence: could not refute.** `gate-logs/C4-verify.log` shows 19 of 19 tests red on the base (each fails with `ModuleNotFoundError: nl_shell.session_terminal`, as the brief planned) and green with the patch. `gate-logs/T3-suite.log` shows 500 passed, none skipped. The new cases call the production `_AltScreen` directly (`tests/test_session_terminal.py:216-232`), once whole and once byte by byte, and go end to end through real bash (`tests/test_session_terminal.py:204`, `B1Û?1049hB2ћ?47lB3` captured). Before the fix, case 1 at `:221` and the `B1…B3` line would have lost output, so these tests would have failed then.

- **Fix: the cases the human named are closed.** I ran `_AltScreen` from `target/src` on `C3 9B` (Û), `D1 9B` (ћ), the 3-byte `E2 80 9B`, the 4-byte `F0 9F 98 9B` and a lead byte split across reads (including after a 5000-byte chunk, past `_HOLD_LIMIT`). All are treated as text, whole or split. `_c1_csi_at` (`src/nl_shell/session_terminal.py:79-98`) looks back at most 3 bytes, which covers a 4-byte character. `_before` keeps 3 bytes from the last read (`:161`), so a split never loses the lead byte.

- NEEDS-HUMAN [human] — `src/nl_shell/session_terminal.py:96` and `:85` (`_c1_csi_at` returns True for "a stray 0x9b"). The human's bypass still works if a different byte comes before the 0x9b. A stray 0x9b is one with no open UTF-8 lead byte before it: after ASCII (`A\x9b`), after a finished character (`À\x9b` = `C3 80 9B`), or after a byte that can never start a character (`F5 9B`, `C0 9B`). The code treats all of these as 8-bit CSI. But UTF-8 terminals (xterm in UTF-8 mode, VTE, kitty) decode a raw 0x9b as U+FFFD (the "invalid character" symbol), not as CSI. Concrete failing case, which I ran: `filter(b"\x1b[?1049hS" + b"A\x9b?1049lLEAK")` returns `b"LEAK"` with `mode=None`. So capture resumes while the real terminal is still on the alternate screen. That is the "fake reset resumes capture" problem from the iteration-3 sign-off, with `A` in place of `Ã`. The test at `tests/test_session_terminal.py:225` (`A\x9b?47h…` → `AB`) treats this as the intended behaviour. The builder followed the human's first option exactly ("no 0xC2-0xF4 lead byte before it"). The human's other option, "drop 8-bit CSI matching" (keep only C2 9B), would close this gap. The cost is that a real raw-C1 switch on a non-UTF-8 terminal would be missed. Which terminals to target is a scope call, so this is tagged [human]. Impact is low: captured output is already untrusted, and nothing crosses a confirm.

- **Threat-model line: present.** `.oss-scanner/threat_model.md:226` names the Ctrl-C-at-command-end race and says the session stays degraded until `restart()`, as the sign-off asked. Spec `docs/design/specs/pty-protocol/v1.md:449-450` describes the new 0x9b rule.

- **Reviewer verdict.** I found no claim in `check-gates.json` that the logs don't back. C4 and T3 match their logs, and T4 is deferred to publish, which is fine at this stage. I tried to refute the evidence (red→green, production path), the UTF-8 fix (2-, 3- and 4-byte characters, splits, the hold limit, C2 9B) and the doc additions. The only gap I found is the stray-0x9b case above.
