It is not a tautology.
- **Ctrl-C between the paste and `S`** (the start record). §6.1 starts forwarding before the paste (`session.py:717-722`, `session_terminal.py:150-166`). - **The prior round's blocker** (the mirror retried forever on a full terminal). It is fixed. ## Findings

- NEEDS-HUMAN [impl] — `src/nl_shell/session_terminal.py:161`. `os.set_blocking(self._terminal.output_fd, False)` sets `O_NONBLOCK` on the terminal's shared open file description (the kernel object behind the fd, which every copy of the fd shares), not just on nl-shell's fd. In production the caller will pass `Terminal(0)`, and fds 0, 1 and 2 share that description with the outer login shell and any background jobs it started on the same tty. For the whole length of each command, every one of those writers gets non-blocking writes. A background `make &` from the outer shell, or Python logging to stderr from another thread, can then fail with `EAGAIN` / `BlockingIOError` on a busy terminal. I checked the shared-flag behaviour: after `os.set_blocking(s, False)` on an `openpty` slave, `os.dup(s)` also reports non-blocking. The value is put back in `end()`, but nothing protects other processes while the command runs, and a SIGKILL mid-run leaves it set. Concrete fix the builder can make: write the mirror through a private description, e.g. `os.open(os.ttyname(output_fd), os.O_WRONLY | os.O_NOCTTY | os.O_NONBLOCK)`, closed in `end()`, and leave the shared fd alone. The same applies to reads if `input_fd` is ever made non-blocking. Low severity today, because nothing wires `terminal=` to the real stdin until #78.
- Minor, not a blocker: tests (g) at `tests/test_session_terminal.py:582-583, 595, 618-619` check that termios settings and the session master's blocking mode come back. They do not check that the stand-in's own fd (`screen.fd`, the `output_fd`) is blocking again after a normal, degraded or exception exit. Only the stalled-terminal test checks this (`:505`). This is a coverage gap, not a failing case.
- NEEDS-HUMAN [human] — brief "Residual race" and `docs/design/specs/pty-protocol/v1.md` §6.1 (patch hunk at spec line ~429). The race is now named in the spec and in the threat model's Known gaps, as the brief asked. I could not make it fire (80 runs aimed at it). Whether to accept it for v1 or ask for the fd 4 back-channel (Option A) is still the human's call. The patch doesn't settle it, and it shouldn't.
- NEEDS-HUMAN [human] — `.oss-scanner/threat_model.md` Known gaps (patch hunk at :209-228). The round-1 finding is handled the doc-only way it suggested: an "§6 mirror is not filtered yet" bullet, plus a #78 gate line naming the output rendering filter. The mirror still passes OSC 52 and terminal queries through (`session_terminal.py:262-275`). This is out of scope by the brief's own terms. Accepting it as a known gap until the filter issue lands needs the human's sign-off, not a rebuild.
