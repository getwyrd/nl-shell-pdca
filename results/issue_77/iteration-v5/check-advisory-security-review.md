# Security review — issue 77 (teacher client, `--dev-teacher`)

Attacker-reachable inputs this diff touches: threat-model item 11 (the dev teacher endpoint: status line, headers, body, TLS, redirects, timing — a LAN peer controls them), item 8 (the local model socket, same user only), item 5 (model output, passed raw to the proposal parser), and the config exception "a model endpoint in config is refused without `--dev-teacher`" (`.oss-scanner/threat_model.md:101` area, "Trusted" list).

## Findings

- **Low** — `src/nl_shell/teacher_client.py:267` (with `:202-204`, `:310-319`). Input: the host name in a `--dev-teacher` URL and the DNS answers for it (a LAN peer can control DNS on the dev network). What goes wrong: the total deadline does not cover name lookup or the TCP connect. `conn.connect()` calls `socket.create_connection(host, port, timeout=timeout_s)`. `getaddrinfo` has no timeout, and `create_connection` tries each resolved address in turn with the full `timeout_s` each. The `_cut` timer can't help, because `conn.sock` is still `None` until the connect finishes, so `_cut` does nothing. A host that resolves to N blackholed addresses holds the prompt for about N × `timeout_s` plus the lookup time. The brief's Scope (2) says the deadline covers "connect, send and read". Reproducer: point `--dev-teacher http://many.example:8080` at a name with 3 A records in a blackholed range (for example `10.255.255.1-3`), set `[model] timeout_s = 0.5`, send one line, and measure about 1.5 s or more instead of under 0.5 s. A test can do the same by monkeypatching `socket.getaddrinfo` to return three unroutable addresses, or to sleep. This is dev-only and bounded, so it is a hang, not a bypass. Fix: resolve once, connect to a single address with `min(left, …)`, or pass the remaining time per attempt. Or record it as a known gap in the threat model, since item 11 now claims "within one total deadline".
- NEEDS-HUMAN [impl] — the finding above. The brief's success criterion (b) tests the deadline only against a server that accepts the connection (`tests/test_teacher_client.py:371`, `:394`). No test covers the connect phase, even though the threat model (`.oss-scanner/threat_model.md`, item 11) and the module docstring (`src/nl_shell/teacher_client.py:19`) both say the deadline covers connect. Either bound the connect phase and add a test, or narrow the docstring and threat-model wording to "send and read".

## What I checked with no finding

- **No TCP without the flag** (must-hold "Locally complete", ADR-0003). `select_endpoint` (`teacher_client.py:119-122`) returns the unix endpoint whenever `dev_teacher is None`, whatever `teacher_url` holds. The config URL is not even parsed in that case, so a bad config URL can't fail startup. `cli.py:65-70` passes `args.dev_teacher` straight through. The test `tests/test_teacher_client.py:645` patches `socket.socket.connect` and `socket.create_connection` and shows exactly one `AF_UNIX` connect. `http.client` sets `_create_connection` per instance, so the patch takes effect.
- **Server text reaching the terminal** (must-hold "Output rendering is filtered everywhere"). The reason phrase (decoded as Latin-1, so 8-bit C1 such as `\x9b` CSI can appear), the 200-byte error excerpt, TLS errors, `http.client` exception text (`BadStatusLine`, `LineTooLong`, `InvalidURL`) and the unix `FileNotFoundError` text are all passed through `render.escape` at `teacher_client.py:291,296,300,302,306`. `render.escape` covers C0 except LF/TAB, DEL, C1 (`render.py:40-41`), bidi and Cf. `Repl.run` escapes every reply again (`repl.py:126`). Startup notices, `EndpointError` text (which holds the URL) and `:status` lines go through `cli._error` → `render.escape` (`cli.py:112`) or the REPL's escape. Tests: `tests/test_teacher_client.py:51` (OSC 52 + CR in the status line), `:596`, `:606`.
- **Model output stays untrusted** (item 5). `complete` returns raw `message.content` (`teacher_client.py:358-369`). `Repl._propose` hands it only to `proposal.parse` (`repl.py:161`). There is no repair and no retry.
- **Transport rules from item 11.** Redirects are refused before the body is read (`:281-284`). `http.client` ignores `HTTP(S)_PROXY`. TLS uses `ssl.create_default_context()` (certificate and host-name checks on; `:247`) with no plain fallback (test `:431`). Userinfo is refused, including a bare `@` (`:142`). Query and fragment are refused. No `Authorization` header is sent. CR/LF in the URL path or host is rejected by `http.client`'s own checks (`InvalidURL`, caught at `:303`).
- **Resource limits.** The body is read in `read1` chunks capped at `limit+1`, and reading stops past 64 KiB (`:344-352`). Header count and line length are capped by `http.client` (100 headers, 64 KiB lines). Deeply nested JSON (`RecursionError`) and huge integer literals (`ValueError` from the int-digit limit) are caught (`:361`). A slow-drip status line, headers or body is cut by the `_cut` timer at the deadline (`:310-319`), and the base-class `shutdown` also works during the TLS handshake. Tests `:371`, `:394`, `:345`.
- **Loopback warning.** `_is_loopback` (`:151-158`) does no DNS lookup and fails toward warning: `localhost.`, `127.1` and `2130706433` all get the warning even though they reach loopback. I found no input that is counted as loopback but goes off the host.
- **Config** (`config.py:71-88`). `teacher_url` and `teacher_model` are type-checked strings. `timeout_s` rejects bool, non-numbers, NaN/inf and values ≤ 0. A huge finite value (for example `1e308`) can raise `OverflowError` from `settimeout` or the timer. That is the user's own misconfiguration of a trusted file, so it is below the bar and not filed.
- **Error paths.** `PermissionError` on a socket owned by someone else falls into the generic `OSError` branch and gets an escaped reason. Uncaught paths (an `ssl.create_default_context()` failure from a broken `SSL_CERT_FILE`, or Ctrl-C during a request) come only from the user's own environment or keys, not from attacker input.
- The threat model is updated for item 11, the trusted-config exception and "How to exercise it" (T2 gate passed). The T3 suite is green (441 passed, `gate-logs/T3-suite.log`).
