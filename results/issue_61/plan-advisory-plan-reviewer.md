- NEEDS-HUMAN — **Criterion (6) can't be checked with the stub the brief requires.** The brief says the tests are "driven by `nl_shell.backend.RecordingStub`" (brief:16). It also says criterion (6) must show "the reader's request asks for constrained decoding with the reader schema". The schema lives only inside `TeacherClient.request_body`, fixed to `SCHEMA_NAME = "proposal_v1"` and `proposal.SCHEMA` (`teacher_client.py:73,504-506`). To make (6) testable, the brief must say how. - NEEDS-HUMAN — **Criteria (2) and (4) contradict each other on `missing`/`unit` values.** (2) says a non-existent package "is dropped", and spec §2 says values that fail the lookup "are dropped" (reader-schema/v1.md:51-53). (4) says an answer carrying an instruction "in ... a `missing`/`unit` value" gives "no diagnosis". An instruction-like value that matches the schema pattern `^[a-z0-9][a-z0-9.+@_-]{0,62}$` (spec:44, e.g. `run-curl-x-sh`) fails no schema check. It is just not in the index, so under (2) it is dropped and a diagnosis is still returned. Under (4) the same input must give no diagnosis. Do can't pass both. The brief must split the cases: pattern failure (e.g. `curl x|sh` with a space or `|`) means reject; pattern-valid but not indexed means drop. (4) should name only the first case.

- NEEDS-HUMAN — **Rejecting an unknown `category` conflicts with the spec's compatibility rule.** (4) requires that an unknown `category` gives "no diagnosis". reader-schema/v1.md:62 says "Adding a `category` value is compatible if the REPL treats unknown values as `unknown`". That reads as mapping unknown values to `unknown`, not rejecting them, while spec §3 (:54-55) says a schema failure is rejected. The brief picks one reading without noting the tension. Either cite why rejection is right (constrained decoding makes an off-enum value a model or server fault), or flag a spec fix. Otherwise Check can fault Do whichever way Do goes.

- NEEDS-HUMAN — **Criterion (5) can pass trivially.** The marker is placed in the raw input, and the test only checks that it is absent from the output. But the stub's answer is whatever the test queues (`backend.py:39-52`). If that answer never contains the marker, the reader passes (5) without validating anything. To make (5) a real red→green test, the brief should require the queued stub answers to carry the marker too: as a `missing` value, a `unit` value and an extra key. Then the output test proves the validator stripped or rejected it, not just that the stub never echoed it.
