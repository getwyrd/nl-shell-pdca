# Adversarial review — issue 92 / os-target-folder-and-selection

I could not re-run pytest here (the sandbox has no `pytest` module). I relied on the frozen
C4 log instead: `gate-logs/C4-verify.log:1875` shows 37 of 40 failed plus 3 errors with the
production change reverted, and line 12 shows 43 passed with it. The 3 tests that pass before
the fix are the ones the brief expects to be green-only, such as (h). The tests drive the real
code path (`cli.main` → `config.load` → `targets.select` → `Repl`); I found no copy of the
logic standing in for production code. Below are the cases where the fix breaks or the
verdict says more than the evidence supports.

- NEEDS-HUMAN [impl] — `target/src/nl_shell/os_release.py:71-74`: `read()` only catches `OSError`. An os-release file that is not valid UTF-8 raises `UnicodeDecodeError`, a `ValueError` and not an `OSError`. Nothing in `cli.py:28-38` catches it, so nl-shell crashes at start-up with a Python traceback instead of a one-paragraph refusal. Reproduced: a file holding `ID=ubuntu\nVERSION_ID="26.04"\nNAME="Ubunt\xff"`, set as `os_release.PATHS`, makes `cli.main([])` raise `UnicodeDecodeError`. Related problem in the same lines: an `/etc/os-release` that exists but can't be read (for example EACCES, permission denied) silently falls back to `/usr/lib/os-release`. os-release(5) only allows that fallback when the first file does not exist, so `except OSError` should be `except FileNotFoundError`, and any other read or decode error should become a refusal. Neither case has a test.
- NEEDS-HUMAN [impl] — `target/targets/ubuntu-26.04/allowlist.toml:302`: `hostname` allows `-f`/`--fqdn`, `-d`/`--domain`, `-A`, `-i` and `-a`. Each of these resolves names through the system resolver, so it can send DNS queries. That breaks spec §6.3 ("nothing that can open a network connection") and the brief's Scope (2) rule: "list only well-known display/format options and leave out anything doubtful". The same file already leaves out `lspci -q` for the same kind of reason, so `hostname` is handled inconsistently. Fail-closed fix: keep only `-s`/`--short` (and perhaps `-I`, which reads local interfaces). Test (g) can't catch this, because it only checks for the specific options the brief bans.
- NEEDS-HUMAN [impl] — `target/targets/ubuntu-26.04/allowlist.toml:387-393`: `nvidia-smi`, `rocminfo` and `vulkaninfo` have no `max_operands` and no `subcommands`, so any operand passes. `nvidia-smi` takes first-operand subcommands (`mig`, `drain`, `clocks`, `nvlink`, `vgpu`, `conf-compute`, …), and those are what change GPU state. Today the state-changing forms I know of also need an option that isn't listed, so I found no concrete path that runs unconfirmed. Spec §6.4 says "no options except…", and the fail-closed shape for that is `max_operands = 0`, which costs a user nothing. Low severity.
- NEEDS-HUMAN [human] — `gate-logs/T2-threat-model.log` and `check-gates.json` T2 row: the gate reports "no security-relevant path touched". This patch adds `targets/ubuntu-26.04/allowlist.toml`, which the brief itself calls the file that decides what runs without a confirm (human-only review). It also adds nothing to the threat model. T2's path classifier doesn't know about `targets/*/allowlist.toml`, so its green result is not real evidence. Treat the allowlist entries as unreviewed by any gate. The human should decide whether to widen T2's path list and whether the threat model needs a §Trusted entry for `targets/`.
- `target/src/nl_shell/cli.py:13-15` and `target/tests/test_targets.py:490`: adding `import sys` pushed the tagline down a line. The patch then joined `prog=` and `description=` onto one line so the tagline would still sit at `cli.py:14`, the line number test (h) hard-codes. It works, but any later import added to `cli.py` will make `test_no_os_name_in_code` fail for a reason unrelated to OS names. A future fix would be to match the tagline text instead of a line number. This is not a defect in this diff, so it is not tagged.
- Things I tried that held up: path traversal through `--target ../ubuntu-26.04` (blocked by the `_ID` pattern at `targets.py:35`, and tested); `ID_LIKE` or nearby-version fallback (none, `targets.py:240-245`); a folder named like the OS but with different `[match]` values (refused, and tested); CRLF line endings in os-release (parsed correctly); `target = ""` or a non-string target in config.toml (refused, `config.py:51-53`); the `--target` flag beating a config.toml target that has no folder (tested); `:status` matching (an exact payload match, the same as `input_modes.reply`). The red→green evidence looks sound.
