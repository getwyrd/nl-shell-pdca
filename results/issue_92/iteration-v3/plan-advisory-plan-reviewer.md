# Plan advisory — plan-reviewer — issue 92 / os-target-folder-and-selection

I tried to fault the problem statement and found no gap. The brief matches issue #92 point by point: the folder and its two files, exact `ID`/`VERSION_ID` match with no `ID_LIKE` fallback, `--target`/`config.toml`, the mismatch state, `:status`, and the "Done when" cases. It also matches ADR-0023 §Choosing the target (`docs/design/adr/0023-os-targets.md:72-77`). The 70 command words in criterion (g) match spec `policy-gate/v1` §6.4 (`docs/design/specs/policy-gate/v1.md:151-171`), and the excluded words match `v1.md:173-176`. The prior-art claim checks out: `src/nl_shell/cli.py:1-18` has no os-release handling and there is no `targets/` folder. The faults are below.

- NEEDS-HUMAN — **The Scope asks for restrictions that the format test (g) forbids.** Scope (2) says "Encode every restriction the table states (`date` only `+FORMAT`, … `command` only with `-v`)". Test (g) says the allowlist "uses only the spec §6.2 entry fields". Spec §6.2 (`v1.md:137-142`) allows only `flags`, `options`, `subcommands`, `max_operands` and `stdin`. Several required restrictions cannot be written with those fields:
  - "`date` only `+FORMAT`" needs an operand pattern. With `max_operands = 1`, `date MMDDhhmm` is also allowed, and that form sets the clock.
  - "`command` only with `-v`" needs a *required* flag. `flags = ["-v"]` alone still allows `command foo`, which runs a program.
  - `ip addr show`/`list` with "no `add`/`del`/`set`/`flush`" is a two-level subcommand. `subcommands` only covers the first operand (`v1.md:140`).
  - `diff` "without `--to-file` writing", and `jq` "no `--rawfile`/`--slurpfile` from devices".

  Do has two options, and both are bad: add fields, which fails (g), or silently leave out restrictions, which breaks fail-closed on a human-only-review surface. The brief should decide this. One option: these entries stay off the allowlist in v1. Another: a spec §6.2 amendment that ships in the same bundle. A third: the restriction is enforced in #12 code and noted in the file.

- NEEDS-HUMAN — **The security-relevant part of the allowlist has no test.** Criterion (g) checks the command-word set and the field names only. None of the restrictions the brief lists is checked by a test: `xxd` has no `-r`, `sort` has no `-o`/`--output`/`--compress-program`, `env`/`printenv` have `max_operands = 0`, the `systemctl`/`apt`/`apt-cache`/`dpkg` subcommand lists match §6.4 exactly, and `journalctl` has no `--vacuum-*`/`--rotate`/`--flush`. An allowlist with `xxd` `flags = ["-r"]` or `sort` `options = ["-o"]` passes the gate. Given "an extra one can run code unconfirmed" (brief Scope (2)), a few negative assertions should go into (g) for the restrictions the table states. Otherwise the only check on this is human review at sign-off.

- NEEDS-HUMAN — **The brief bases the work on `main`, but criterion (c) needs #14, which isn't merged.** The brief says "Repo + branch target: eduralph/nl-shell @ main" and "Depends on: 14". `dependency-state.json` lists #14 as `PLANNED`, not merged. `src/nl_shell/repl.py:33-62` on `main` has no `:status`, so (c) "`:status` shows both the target id and the mismatch" and Scope (5) can't be done or tested on `main`. Citations expected also says to cite the `:status` block "on the wave base". The brief should say whether this is "Stacks on: 14", with #14's branch as the base, or whether Do waits for #14 to merge. As written, Do could start from `main` with no `:status` to extend. The C4 red leg would then revert a `repl.py` that has no `:status`, and that only works if the base includes #14.

- NEEDS-HUMAN — **The brief overrides the issue's "code outside `targets/` must not name an OS", and it misses one place.** The issue body says "Code outside `targets/` must not name an OS." ADR-0023 uses MUST (`0023-os-targets.md:51`). The brief puts the tagline in `src/nl_shell/__init__.py:1` and `src/nl_shell/cli.py:14` (`description="Natural-language shell for Ubuntu 26.04."`) out of scope, and leaves it as an Open question it answers "no" to. It doesn't list `pyproject.toml:8`, which has the same tagline. Scope (6) only stops OS-specific *values* in code, and no test checks that. Either a maintainer approves this exception before Do starts, or the brief adds a check, for example "no `ubuntu`/`26.04` literal in `src/` except the named tagline lines". Without that, criterion (6) can't be checked.

- NEEDS-HUMAN — **The `config.toml` unit is extra scope that belongs to #77.** The issue only asks that `target =` in `config.toml` names a target. Scope (4) and criterion (d) add more: a separate config-reading unit, XDG path handling, "a malformed `config.toml` is refused with a message", and a rule that unknown keys are ignored. That is a new refusal path and a module boundary chosen for #77/#62/#16 folds. Combined with the ~70-entry allowlist translation, which the brief's own Open question says may need to be its own slice, this is three reviewable changes in one bundle: loader and selection, config unit, and allowlist content. Consider moving the allowlist content into its own slice now rather than "if review looks too large". It is the human-only-review surface (INTEGRATION §4, `v1.md:204-206`), and the loader code shouldn't wait on it.

- NEEDS-HUMAN — **(Minor) The criterion says "degraded", but nothing can observe it yet.** The issue's Done-when asks for "a mismatched `--target` (degraded)". Spec §7.7 (`v1.md:197-198`) defines degraded as a gate behaviour, and the gate is #12 and out of scope. Test (c) can only check a recorded flag, a reason string, a warning and a `:status` line. That is fine if a human agrees it meets the issue's "degraded" wording. Say it explicitly at sign-off so the issue isn't closed on a claim the code can't show yet.
