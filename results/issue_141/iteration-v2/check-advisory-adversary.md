# Adversarial review: #141 persistent-bash-session tamper checks (iteration 2)

I ran live attacks against the patched tree at `$PDCA_TARGET` with the host's bash 5.3.9 and `ptyprocess`. pytest is not installed in my sandbox, so I could not re-run the C4/T3 gates myself. The frozen `gate-logs/C4-verify.log` shows 31 of 130 tests red before the fix and all green after. My scratch scripts are in `scratch/`.

## Findings

- NEEDS-HUMAN [impl] — **A background job can still change the next paste's bytes while the session stays healthy (I1 broken).** `src/nl_shell/session.py:325-335` (`_RL_IFLAG`, `_RL_LFLAG`, `_RL_CC`) and `_termios_view` at `session.py:1099-1105` drop `ISTRIP`, `INPCK`, `ICRNL`, `INLCR`, `IXON`, `IXANY`, `VMIN`, `VTIME`, `VLNEXT` and `VDISCARD` from every comparison. That includes the check right before the paste (`session.py:722` → `_check_outside` → `_check_termios`), which runs while readline holds the terminal. A confirmed command can start a job that ignores SIGTTOU and changes those bits after readline has set up the terminal. Live repro (`scratch/repro_istrip.py`): `run("(trap '' TTOU; sleep 0.5; stty istrip) &")` → healthy; wait 1.5 s; `run("printf '%s' 'é' | od -An -tx1")` → healthy, output ` 43 29` (`C)`), not `c3 a9`. Bash ran bytes other than the confirmed ones, and nothing degraded. The masked bits are only "what readline changes" from the shell's point of view. At the prompt, readline sets them to fixed values (it clears ISTRIP/INPCK with CS8 and clears ICRNL/INLCR). So the check before the paste can compare against a prompt-time baseline taken while readline holds the terminal, with no mask, instead of ignoring them. Add this repro as a test row. `docs/design/specs/pty-protocol/v1.md:274-275` describes the mask and would need the same change. The threat model does not list this as a known gap.

- NEEDS-HUMAN [human] — **Even with that fix, there is a small window between the check and the write.** The check at `session.py:722` and the write at `session.py:726` are separate steps. A job that ignores SIGTTOU and keeps running `stty istrip` / `stty -istrip` in a loop will sometimes pass the check and still mangle the paste. The E-time check uses the same mask, so it does not catch this afterwards either. Closing it fully means the session has to deal with background jobs that hold the terminal (or ignore SIGTTOU). That is a scope decision, so it should be fixed or listed as a known gap with a follow-up issue.

- NEEDS-HUMAN [impl] — **Test (r) does not test what it claims.** At `tests/test_session.py:1294-1306`, the assignment `PS4='$(…)'` fails because PS4 is now readonly (`session.py:179`). Bash then drops the rest of the line, so `set -x` never runs. Live: the command's output is `bash: PS4: readonly variable`, and the only H difference is `declare -- BASH_XTRACEFD="9"` (plus the sequence number). So `h-changed` comes from BASH_XTRACEFD alone. The xtrace row (`__nls_x`) and the PS4 row never fire in this test, and no `_TAMPER` row covers a bare `set -x`. A bare `set -x` does degrade (`__nls_x="1"`, checked live), but no test would catch a regression there. Add a `set -x` row to `_TAMPER`. Assert in (r) which H line changed, or split (r) into the PS4 case and the xtrace case.

- NEEDS-HUMAN [human] — **Readonly PS4 changes behavior beyond the brief's "PS4 value in H; a difference degrades".** With `readonly PS4` at `session.py:179` (spec `v1.md:59-60`), a confirmed `PS4='+ ${LINENO}: '; set -x; ./script` (a common way to debug a script) runs only the part before the assignment. Bash prints an error and drops the rest of the line, and the session stays healthy. That fails safe for I1, but users will see a confirmed command run only partly. Someone should decide whether that trade-off is acceptable or whether PS4 should be compared in H instead (with xtrace turned off before PS4 is ever expanded).

- (note, no action) The brief's plan-review item (4) says "(m)/(p) are red on #140 alone". They are not. `test_m_…` and `test_p_…[bracketed-paste-off]` / `[readline-off]` pass on the red leg (`gate-logs/C4-verify.log` lists only `p[vi-mode]`), because the base already forces `enable-bracketed-paste on` after `~/.bashrc` (base `session.py:100`). This does not break anything, but (m) is not evidence for this patch.

## Attacks that failed

- The iteration-1 ISIG findings are fixed. `__nls_done` now waits on fd 4 (`session.py:197`) until nl-shell has read the terminal settings at D (`session.py:1063-1065`). If the D-time read finds ICANON and ECHO off, the session degrades instead of skipping the check (`session.py:964`). I tried replacing the ack on fd 4 (`exec 4< <(yes)`) to bring the race back. Bash then reads either the command's settings or readline's, and both lead to a degrade. If fd 4 is closed or stolen, the read times out, `__nls_k` changes, and H changes.
- (r)'s safety claim holds: no marker in either live variant.
- A signal trap that rebinds `\r` after the snapshot (`trap 'bind …' USR1; (sleep .5; kill -USR1 $$) &`) did not run inside readline. It ran after the next line had been read, so the next paste ran unaltered and that command's snapshot degraded with `h-changed` (`scratch/repro_trap2.py`).
- `enable -n trap; enable trap` and `set -o functrace; set +o functrace` within one command return to the baseline, so they are rightly healthy.
- `exec >&3` (from reading the code at `session.py:934-940`, not run live): it passes the E-time check because fd 1 is allowed to be the control pipe then, but the check before the paste (`at_prompt=True`) has no such exception and would catch it.
