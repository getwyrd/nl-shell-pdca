# Brief — issue 141 / persistent-bash-session-tamper-checks (re-plan, round 4)

> Re-planned after three builds (`iteration-v1..v3`) did not converge: each review found a new
> way around the checks in the same area. This brief keeps the v3 requirements and settles
> the six scope questions the v3 sign-off left open (see "Decisions settled in this re-plan").

- **Slug:** persistent-bash-session-tamper-checks
- **Kind:** enhancement
- **Defect / goal:** After #140, a confirmed command can still change bash or its terminal so that the NEXT confirmed paste runs bytes other than the confirmed ones, or so that a paste is mangled, without the session degrading. Close that for the closed list below, so that **I1 holds: the bytes bash executes for a paste are exactly the confirmed bytes, or nothing is sent** (threat model "What must hold"; spec `pty-protocol/v1` §5.1). For every "detect" row, a change made by a command shows in that command's own snapshot (session degrades), or an outside check catches it before the paste is written.
  **Defect found in v3 (must be fixed here).** On #140's rcfile, code that is not nl-shell's runs AFTER `D` is written: the user's `PROMPT_COMMAND` elements (`src/nl_shell/session.py:126-131`, inside `__nls_done`, after the `D` write at `:125`) and a top-level DEBUG trap, which fires before each simple command of the hook element (`session.py:177`). v3 read the terminal at `D`, so `trap 'if [[ $BASH_COMMAND == *__nls_snap* ]]; then trap - DEBUG; stty -isig; fi' DEBUG` turned signals off after the reading, removed itself before the trap list was captured, and the next paste was written with `-isig` while healthy (10 of 10 runs). The same window is open to anything the user's `PROMPT_COMMAND` elements call, since a confirmed command can redefine those functions (`F` is only reported).
  **Table A rows added to `H`** (compared to the baseline; a difference degrades at that command's snapshot): traps `DEBUG`/`RETURN`, `extdebug`, `functrace` (`T`/`X` still reported for the gate); `xtrace` and `BASH_XTRACEFD`; the enabled/disabled state of every builtin the hooks call, exposed as a module-level tuple `HOOK_BUILTINS`. Its contents are defined by the rcfile, not by a hand list: it is exactly the set of names written as `\builtin <name>` or `builtin <name>` in the hook functions, `PS0` and nl-shell's `PROMPT_COMMAND` element of the patched `RCFILE`. On `0771812` that is `printf`, `declare`, `set`, `shift`, `return`, `eval`, `:`, `shopt`, `compgen`, `alias`, `enable`, `jobs`, `trap`, plus `builtin` itself, plus whatever the new reading point and `H` rows add (e.g. `bind`, and `read` only if the new code calls it). `unset` is called only while the rcfile loads (`session.py:176`, `:178`), not by any hook, so it is left out (tests read it inside each test, never at module level, so its absence on the red leg is a per-test failure, not a collection error); readline on/off, emacs/vi mode, readline variables (`bind -v`) EXCEPT `history-size` (it follows `HISTSIZE` and cannot change paste bytes); ALL key bindings in every keymap (functions, macros, `bind -X` shell commands); history expansion (`set -H`). The locale-sensitive readline variables (`convert-meta`, `input-meta`, `output-meta`) stay in `H`, so `LC_ALL=C` degrades: that is failing safe, accepted. Every command substitution in the hooks captures stderr (`2>&1`), so a failing or disabled builtin never yields an empty, baseline-matching value (on the base, `trap -p` and `declare -p` drop stderr: `session.py:139`, `:151`, `:159`, `:177`).
  **PS4** (decision 3 below): `PS4` is made `readonly` after `~/.bashrc` is sourced, because bash traces `PROMPT_COMMAND` itself, so a planted `PS4` would run before any snapshot could see it. A later confirmed `PS4=…` fails with "readonly variable". This is a user-visible change and the spec must say so. `H` also carries `declare -p PS4` (value and attributes), so if some path ever left PS4 changed or not readonly, the snapshot degrades `h-changed`.
  `B` stays a reported-only field for the gate; `H` separately holds the enabled/disabled state of the `HOOK_BUILTINS` only, so `enable -n` of a hook builtin degrades and `enable -n` of any other builtin is only reported in `B`. Every degrade carries a fixed machine-checkable code so tests can assert WHICH check fired. **Interface:** `ProtocolTracker.degrade(reason: str, code: str = "other")` stores `degraded_code` next to `degraded_reason` (`pty_protocol.py:172-175`); `Session.degraded_code` is a property like `Session.degraded_reason` (`session.py:470`); `SessionDegraded` gains a `code` attribute next to `reason` (`session.py:225-232`), filled at every `raise SessionDegraded(...)`. Codes: the new triggers get `outside-check`, `stopped`, `tiocsti`. Of #140's sites, only the three this brief's tests assert on are tagged: the H compare `pty_protocol.py:295` → `h-changed`; the missing-record paths `pty_protocol.py:273` and the prompt rule's "no done record after the shell returned to a prompt" / "snapshot did not finish" `session.py:568-572` → `missing-record`; "the shell exited" `session.py:702` → `exited`. Every other #140 site keeps the default `other`. This is an allowed edit to #140's code: adding the `code=` argument only. The reason TEXT at every #140 site stays byte-for-byte the same, so #140's tests that match `degraded_reason` text (e.g. `tests/test_session.py:929` `"H differs"`) stay unchanged and green. When `builtin` or `printf` is disabled no record can be written at all; the hook then stops before the snapshot and the prompt rule degrades with `missing-record` (decision 6: accepted as the right signal, not a workaround).
  **Table B outside checks:** read from outside bash the PTY's termios (via the master) and bash's fds 0/1/2 (via `/proc`); any difference from the baseline degrades and the paste is not written. **Why both reading points (from v3's live trace, `iteration-v3/check-advisory-adversary.md:5`):** while readline holds the terminal it turns `ISIG` on and `ICANON`/`ECHO` off, and it restores the shell's own settings when the line is accepted, so the command runs with them. v3's pre-paste full compare against the first-prompt baseline saw `ISIG, prepped` and passed even though the shell's setting was `-isig`. So reading (b) cannot see `-isig`, `-icanon` or `-echo` at all; only a reading taken while bash runs its hooks, not readline, can. v3's hook-time reading was at `D`, before the planted trap ran, which is the defect above. Reading (b) is what catches changes to bits readline does NOT reset (`istrip`, `icrnl`, `inlcr`, `intr` character, and a background job's change while readline holds the terminal). Tests that need (a) and fail with only (b): (h2) all rows, (j) `stty -isig` and `stty -icanon -echo -isig`. Tests that need (b): (j) background-job rows. These readings are taken (a) for each command, at the LAST point in the hooks after which no non-nl-shell code can run before readline takes the terminal (so after the user's `PROMPT_COMMAND` elements and after the last DEBUG-trap firing), and (b) immediately before every paste, while readline holds the terminal, comparing every termios setting against a baseline taken in that same state at the first prompt. At startup read `tiocsti_path` (constructor keyword, default `"/proc/sys/dev/tty/legacy_tiocsti"`, read-only); missing, unreadable or not `0` → start degraded with a reason naming it. A stopped bash (`/proc` state `T`) degrades: checked before every paste and on every poll tick of `Session._wait_for_result` (`session.py:522-578`, the loop that waits for `D`/`E` while a command runs; with `timeout=None` it would otherwise wait forever on a stopped bash), and of `_wait_for_prompt` (`session.py:614`) if it can block. No separate background poller. The 5 s figures below are test timeouts matching #140's limits, not spec numbers.
