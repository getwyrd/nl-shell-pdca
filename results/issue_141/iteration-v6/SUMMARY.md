# Result — issue 141 / persistent-bash-session-tamper-checks

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: After #140, a confirmed command can still change bash or its terminal so that the NEXT confirmed paste runs bytes other than the confirmed ones, or so that a paste is mangled, without the session degrading. Close that for the closed list below, so that **I1 holds: the bytes bash executes for a paste are exactly the confirmed bytes, or nothing is sent** (threat model "What must hold"; spec `pty-protocol/v1` §5.1).
  **Why option B (the design decision of this re-plan).** While readline reads a line it forces a fixed set of terminal fields ("the readline-forced fields", R). Measured live on the host's bash 5.3.9 (Plan revision, 2026-10-17: termios read from the PTY master while readline waited, then after a foreground `stty icrnl inlcr istrip inpck`, then while a command ran): R is at least `c_lflag` ISIG on, ICANON off, ECHO off (also v3's trace, `iteration-v3/check-advisory-adversary.md:5`: `ISIG, prepped`); `c_iflag` ICRNL, INLCR, ISTRIP, INPCK off; `c_cc` VMIN=1, VTIME=0, VLNEXT and VDISCARD disabled. The foreground `stty icrnl inlcr istrip inpck` was invisible while readline held the terminal and visible while the next command ran. Do confirms R against readline's `rltty.c` (`prepare_terminal_settings`) in bash 5.3.9 and widens it if readline forces more, naming each extra field in build-notes. The old phrase "the masked bits" in this brief now means all of R. So a change the shell makes to a field in R cannot change the bytes readline reads from a paste. It changes how the command runs afterwards (Ctrl-C/Ctrl-Z off, no echo). No reproducer in five rounds produced a marker this way. Rounds 3–5 used an fd-4 pipe handshake to read the masked bits after the hooks, and every round found a way around it, because any process of the user can reopen bash's fd 4 through `/proc` (v5 security review, 5 of 5 runs). Option B drops the handshake. The claim is split into three parts:
  **(1) Bash state that can change paste bytes degrades before the next paste.** That is everything in Table A below, captured in `H` after the last code that can run synchronously before readline (the user's `PROMPT_COMMAND` elements already run before `__nls_snap`, `session.py:126-131`, `:177`). **All traps** move into `H`, not only DEBUG/RETURN: on the base, traps are only reported in `T` (`session.py:164`, `:177`), so a signal-trap handler could run `bind …` while readline waits, after the snapshot. `T` stays as a record for the gate.
  **(2) The whole termios state while readline holds the terminal** is read from outside bash (via the PTY master) **immediately before every paste** and compared, every field including R, with a baseline taken in that same state at the first prompt. Fields outside R (`intr`/`susp`/… characters, IXON, IEXTEN, the other flags) carry the shell's own settings, so a confirmed `stty intr '|'` shows here. Fields in R must equal readline's forced values; a mismatch means something changed the terminal while readline held it (e.g. a background job's `stty -isig` or `stty istrip`), and is tampering. Any difference degrades with code `outside-check` and the paste is not written. This pre-paste check of R against readline's forced values is explicitly allowed and expected. The check-to-write race is the Known gap #147 (decision 1).
  **(3) The fields in R of the shell's OWN settings** (as they are when readline does not hold the terminal) are compared with their startup values (after `~/.bashrc`) no later than the end of the first command that runs under a change: that `run()` ends in `SessionDegraded` with code `outside-check`, and the paste after it is refused. That one command runs with the changed settings. This is a new Known gap (follow-up **#149**). Part (3) is what catches a foreground `stty -isig` or `stty icrnl`; part (2) cannot see it. How and when to read them is Do's choice, but it must not depend on bash waiting for nl-shell (no handshake). A reading that cannot tell the shell's settings from readline's must fail closed (degrade), not pass.
  **Table A rows added to `H`** (compared to the baseline; a difference degrades at that command's snapshot): **every trap** (`trap -p` for all signals plus `DEBUG`, `RETURN`, `ERR`, `EXIT`), `extdebug`, `functrace`, `errtrace`; `xtrace` and `BASH_XTRACEFD`; `declare -p PS4` and `declare -p MAILCHECK`; the enabled/disabled state of every builtin the hooks call, exposed as a module-level tuple `HOOK_BUILTINS`. On `0771812` that is `printf`, `declare`, `set`, `shift`, `return`, `eval`, `:`, `shopt`, `compgen`, `alias`, `enable`, `jobs`, `trap`, `builtin`, plus whatever the new rows add (e.g. `bind`). `unset` is called only while the rcfile loads (`session.py:176`, `:178`), so it is left out. Tests read `HOOK_BUILTINS` inside each test, never at module level, so its absence on the red leg is a per-test failure, not a collection error. Also: readline on/off, emacs/vi mode, readline variables (`bind -v`) EXCEPT `history-size` (decision 5), ALL key bindings in every keymap (functions, macros, `bind -X` shell commands), history expansion (`set -H`). The locale-sensitive readline variables (`convert-meta`, `input-meta`, `output-meta`) stay in `H`, so `LC_ALL=C` degrades (failing safe, accepted). # Adversarial review: issue 141, persistent-bash-session-tamper-checks (option B)

# Security review — issue 141 (persistent-bash-session-tamper-checks, option B)

**Attacker-reachable inputs touched:** threat-model item 4, session state (traps, key bindings, readline variables, shell options, `PS4`/`MAILCHECK`/`MAILPATH`, the enabled state of builtins, and terminal settings, all set by a confirmed command or by a background job it leaves behind), plus what bash shows nl-shell through `/proc/<pid>/{stat,fd,fdinfo}` and the PTY's termios (terminal settings).

No finding. Here is what I checked.

- **Trap capture order** (`src/nl_shell/session.py:256`, `:200-203`). The `$(\builtin trap -p 2>&1)` argument to `__nls_snap` is expanded only after `\__nls_done` returns, so a trap installed by a user `PROMPT_COMMAND` element (which runs inside `__nls_done`) is already in `$1`. EXIT stripping removes only an exact leading copy of the current `trap -p EXIT` line. If the EXIT trap changed between the two readings, the strip does nothing, the whole text stays in `H`, and the session degrades. That is the safe direction. A crafted EXIT trap string can't hide a later trap line, because only the prefix is removed. An EXIT trap does not run in the hooks' `$( … )` subshells.
- **Readline state in `H`** (`session.py:209-233`). `bind -v` minus only the `history-size` line: the `${…/…/…}` pattern is quoted, so a crafted value can't widen what gets removed. `-p/-s/-X` cover all five real keymaps (`emacs`, `vi`, `vi-move` are aliases). Disabled hook builtins go through `compgen -A disabled` with fixed names. A disabled `compgen`/`bind`/`trap` gives error text (stderr kept), not an empty value that matches the baseline. `declare -pF` catches the `-t` (trace) attribute on hook functions.
- **`PS4`/`MAILCHECK` pin** (`session.py:150-155`). The names are fixed, so the `eval` is a constant. `local PS4=…` and `local MAILCHECK=…` fail on a readonly variable. With MAILCHECK unset, bash turns the mail check off, so a planted `MAILPATH` message never expands.
- **Pre-paste outside check** (`session.py:691-693`, `:917-938`). This compares the whole `tcgetattr` result and fds 0-2 with the first-prompt baseline, read from the master fd. A background `stty` that lands after this reading is Known gap #147. A process that is stopped, or whose `/proc` can't be read, degrades. `/proc/<pid>/stat` is parsed after the last `)`, so a crafted `comm` (process name) can't move the state field.
- **Part 3 reading of R** (`session.py:940-970`, `:713-736`). A reading counts only if no control bytes are pending after it. If D and E come in one read, the session degrades with `outside-check` instead of passing (fail closed, as the brief requires). A background `stty` during the D→E window shows up as a change, which again is the safe direction. Fake fd-3 records that could fool this ordering are Known gap #135.
- **fd 0-2 check** (`session.py:990-1034`). It compares device, inode, rdev, file type and access mode. `exec >/dev/null`, a different pts, or `/dev/tty` all differ. A closed fd degrades (stat fails).
- **TIOCSTI** (lets a process push bytes into a terminal's input; `session.py:1058-1080`). A missing file, an unreadable file, or any value other than `0` starts the session degraded. It is read once, and changing it needs root.
- **Live probe, outside the claimed list: SIGINT to bash.** I ran the patched `Session` against the host's bash 5.3.9 (scripts in `exp/` of this sandbox).
  - (a) A confirmed `(trap '' INT; while :; do kill -INT $$; sleep 0.001; done) &`: every run degraded with "control record 'D' arrived out of order" before the next paste. 8/8 runs, no marker.
  - (b) One SIGINT sent halfway through writing `: aaa…(200)… || touch MARK` (simulating a perfectly timed background `kill -INT $$`): the run ended `SessionDegraded`/`outside-check` and `MARK` was not created. The leftover half of the paste did not run as its own line.
  - So I found no I1 break by this route. Signals other than STOP sent to bash are not in the brief's closed list. They belong under #145 if anyone wants them tracked.
- **Threat model and spec wording.** The new Known-gaps bullets (`.oss-scanner/threat_model.md:181-211`) name #147-#150 with no catch-all sentence. The spec and code comments say R is read as readline's forced values before a paste, and the shell's own values only after the fact (`docs/design/specs/pty-protocol/v1.md:225`, `:338`; `session.py:917-922`). Neither claims more than the brief allows.
- **Tests.** C4 is red on the reverted tree (60 of 163 failed) and green with the fix (`gate-logs/C4-verify.log`). T3, the full suite, passes. The briefed tests go after the attack paths (marker absent, zero writes, degraded), not only friendly paths.
