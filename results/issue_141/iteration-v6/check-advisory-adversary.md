# Adversarial review: issue 141, persistent-bash-session-tamper-checks (option B)

I found no I1 bypass (no way to get bytes other than the confirmed ones executed). I did find one reproducible false alarm that the gates missed.

- NEEDS-HUMAN [impl] — **The fd 0/1/2 check at E races with bash's own `>&3` redirect, so healthy sessions degrade under CPU load.** E is written by `\builtin printf 'E\n' >&3` (`src/nl_shell/session.py:251`). To run a builtin with `>&3`, bash points its own fd 1 at the control pipe, runs printf, then puts fd 1 back. `_wait_for_result` calls `self._check_fds()` as soon as it parses E (`src/nl_shell/session.py:728-729`). If bash is paused between the write and the restore, `/proc/<pid>/fd/1` is still the control pipe. **Concrete failing case:** start a `Session` with an empty test HOME and `TERM=xterm`, run `run("true")` 30 times, with Python, bash and 3 busy loops all pinned to CPU 0 (`taskset -c 0`). 3 of 10 sessions over two tries ended in `SessionDegraded(code="outside-check")` with reason `the shell's fd 1 is not what it was at the first prompt (now pipe:[…])`. Without load, 5 of 5 were fine. It fails closed, so it is not a security hole. But any busy machine or CI runner will hit it, and the (fa) "50 × `true` stays healthy" guard passes only because the host was idle. Fix ideas: check fds only while bash is known to be at the prompt (the pre-paste check in `_prompt_check` already does this, since bash is then blocked in `read`), or have the E-time check retry or wait until bash's fd 1 is no longer the control pipe. The probe is `probe/load.py` in this sandbox.

- NEEDS-HUMAN [impl] — **Unwarranted claim in the evidence: the T3 / C4 green legs (`gate-logs/T3-suite.log`, `gate-logs/C4-verify.log`, 163 passed) are taken to show the new outside checks raise no timing false alarms.** They ran on an idle host. The brief makes (fa) a guard against part 3's fail-closed timing rule ("guards part 3's fail-closed rule against timing"), but the race above shows the E-time checks depend on scheduling. A test that loads the CPU, or that sleeps between bash's write of E and its fd restore (e.g. a fake `/proc` root as `proc_root` already allows), would have gone red. Add one so the fix for the item above is proven.

- Checked and could not break: the part 3 reading taken between D and E (`_read_shell_r`, `src/nl_shell/session.py`, called at `:736-737`). Its rule "if nothing more arrived on fd 3 after `tcgetattr`, readline had not taken the terminal" holds, because `tcgetattr` runs before the `select`. The other suspected false alarm, D and E arriving in one `os.read` (`:721-733`, where `shell_r` would still be None at E), did not happen in 180 loaded runs with the fd check stubbed out. Bash's snapshot forks take long enough in practice. It is still possible in theory, and it would fail closed.

- Other ways I tried to change paste bytes without being seen; all were caught or are harmless:
  - Terminal fields outside R that still change input: `stty iuclc`, and `stty cs7` (readline clears ISTRIP/INPCK only under CS8). Both show up in the whole-termios compare before the paste (`_prompt_check`).
  - Hiding a trap behind the EXIT-trap strip (`${1#"$__nls_v"}` in `__nls_snap`). It only removes an exact prefix, which is the `trap -p EXIT` text itself.
  - A readline string variable holding `\nset history-size …` to confuse the `history-size` removal. The variable's own change already shows in H.
  - `exec 0<>/dev/pts/N`. The fd tuple is the same, but the device is the same too, so nothing changes.
  - `TMOUT=1`. bash exits, and the session degrades with `exited`.
  - Aliases, functions, `exec bash --rcfile` with faked records. These are out of scope or already named gaps (#135, the `session-altering` class).

- Red→green evidence: re-reading `gate-logs/C4-verify.log` confirms 60 of 163 tests failed with the production code reverted, with no collection errors. The failures are on the attack outcome (`_assert_degrades_at_its_snapshot` asserts `SessionDegraded` before the code), not on imports. The tests drive the real `Session` over a real PTY, not a copy of the production logic. I could not re-run pytest here (it is not installed), but I drove the patched `Session` directly with the installed `ptyprocess` and bash 5.3.9. That is how the race above was found.
