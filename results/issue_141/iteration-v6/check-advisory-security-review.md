# Security review — issue 141 (persistent-bash-session-tamper-checks, option B)

**Attacker-reachable inputs touched:** threat-model item 4, session state (traps, key bindings, readline variables, shell options, `PS4`/`MAILCHECK`/`MAILPATH`, the enabled state of builtins, and terminal settings, all set by a confirmed command or by a background job it leaves behind), plus what bash shows nl-shell through `/proc/<pid>/{stat,fd,fdinfo}` and the PTY's termios (terminal settings).

No finding. Here is what I checked.

- **Trap capture order** (`src/nl_shell/session.py:256`, `:200-203`). The `$(\builtin trap -p 2>&1)` argument to `__nls_snap` is expanded only after `\__nls_done` returns, so a trap installed by a user `PROMPT_COMMAND` element (which runs inside `__nls_done`) is already in `$1`. EXIT stripping removes only an exact leading copy of the current `trap -p EXIT` line. If the EXIT trap changed between the two readings, the strip does nothing, the whole text stays in `H`, and the session degrades. That is the safe direction. A crafted EXIT trap string can't hide a later trap line, because only the prefix is removed. An EXIT trap does not run in the hooks' `$( … )` subshells.
- **Readline state in `H`** (`session.py:209-233`). `bind -v` minus only the `history-size` line: the `${…/…/…}` pattern is quoted, so a crafted value can't widen what gets removed. `-p/-s/-X` cover all five real keymaps (`emacs`, `vi`, `vi-move` are aliases). Disabled hook builtins go through `compgen -A disabled` with fixed names. A disabled `compgen`/`bind`/`trap` gives error text (stderr kept), not an empty value that matches the baseline. `declare -pF` catches the `-t` (trace) attribute on hook functions.
- **`PS4`/`MAILCHECK` pin** (`session.py:150-155`). The names are fixed, so the `eval` is a constant. `local PS4=…` and `local MAILCHECK=…` fail on a readonly variable. With MAILCHECK unset, bash turns the mail check off, so a planted `MAILPATH` message never expands.
- **Pre-paste outside check** (`session.py:691-693`, `:917-938`). This compares the whole `tcgetattr` result and fds 0-2 with the first-prompt baseline, read from the master fd. A background `stty` that lands after this reading is Known gap #147. A process that is stopped, or whose `/proc` can't be read, degrades. `/proc/<pid>/stat` is parsed after the last `)`, so a crafted `comm` (process name) can't move the state field.
- **Part 3 reading of R** (`session.py:940-970`, `:713-736`). A reading counts only if no control bytes are pending after it. If D and E come in one read, the session degrades with `outside-check` instead of passing (fail closed, as the brief requires). A background `stty` during the D→E window shows up as a change, which again is the safe direction. Fake fd-3 records that could fool this ordering are Known gap #135.
- **fd 0-2 check** (`session.py:990-1034`). It compares device, inode, rdev, file type and access mode. `exec >/dev/null`, a different pts, or `/dev/tty` all differ. A closed fd degrades (stat fails).
- **TIOCSTI** (lets a process push bytes into a terminal's input; `session.py:1058-1080`). A missing file, an unreadable file, or any value other than `0` starts the session degraded. It is read once, and changing it needs root.
- **Live probe, outside the claimed list: SIGINT to bash.** I ran the patched `Session` against the host's bash 5.3.9 (scripts in `exp/` of this sandbox).
  - (a) A confirmed `(trap '' INT; while :; do kill -INT $$; sleep 0.001; done) &`: every run degraded with "control record 'D' arrived out of order" before the next paste. 8/8 runs, no marker.
  - (b) One SIGINT sent halfway through writing `: aaa…(200)… || touch MARK` (simulating a perfectly timed background `kill -INT $$`): the run ended `SessionDegraded`/`outside-check` and `MARK` was not created. The leftover half of the paste did not run as its own line.
  - So I found no I1 break by this route. Signals other than STOP sent to bash are not in the brief's closed list. They belong under #145 if anyone wants them tracked.
- **Threat model and spec wording.** The new Known-gaps bullets (`.oss-scanner/threat_model.md:181-211`) name #147-#150 with no catch-all sentence. The spec and code comments say R is read as readline's forced values before a paste, and the shell's own values only after the fact (`docs/design/specs/pty-protocol/v1.md:225`, `:338`; `session.py:917-922`). Neither claims more than the brief allows.
- **Tests.** C4 is red on the reverted tree (60 of 163 failed) and green with the fix (`gate-logs/C4-verify.log`). T3, the full suite, passes. The briefed tests go after the attack paths (marker absent, zero writes, degraded), not only friendly paths.

#78 is still not wired to confirmed commands (threat model `:210-211`), so none of this is reachable from model output in the product yet.
