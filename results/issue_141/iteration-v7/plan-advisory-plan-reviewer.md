# Plan review — issue 141 / persistent-bash-session-tamper-checks (option B)

- NEEDS-HUMAN — **The premise "readline sets three terminal bits itself" looks incomplete, so parts (2) and (3) split the termios fields in the wrong place.** Brief line 13: "While readline reads a line it sets three terminal bits itself: ISIG on, ICANON off, ECHO off". Line 15 says part (2) compares "every termios field except those three `c_lflag` bits", including `istrip`, `icrnl` and `inlcr`. As I remember readline's `rltty.c` `prepare_terminal_settings`, it also clears `ICRNL | INLCR`, clears `ISTRIP | INPCK` when CS8 (always the case here), sets `VMIN=1`/`VTIME=0` and sets `c_cc[VLNEXT]` (and `VDSUSP`) to `_POSIX_VDISABLE`. I could not check this here: there is no readline source in `$PDCA_TARGET` and Bash was down. The only evidence the brief gives is v3's trace (`ISIG, prepped`), and that shows `c_lflag` only. If my reading is right, two things follow. (a) A confirmed foreground `stty icrnl`/`inlcr`/`istrip` gets overwritten by readline's prep before part (2)'s pre-paste reading, so part (2) never sees it. Part (3) only covers ISIG/ICANON/ECHO, so nothing catches it, and the Docs closed list and spec §3 would claim coverage the design does not have. (b) The part (2) baseline is taken while readline holds the terminal, so it is readline's settings, not the shell's. The rule "everything except three bits is readline-independent" is then false. Ask the planner to check `rltty.c` for bash 5.3.9 and widen the "masked" set (and Known gap #149's wording) to every field readline forces. Otherwise state why the forced `c_iflag`/`c_cc` fields can't affect the command that runs afterwards.
