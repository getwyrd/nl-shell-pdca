# Result — issue 141 / persistent-bash-session-tamper-checks

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: After #140, a confirmed command can still change bash or its terminal so that the NEXT confirmed paste runs bytes other than the confirmed ones, or so that a paste is mangled, without the session degrading. Close that for the closed list below, so that **I1 holds: the bytes bash executes for a paste are exactly the confirmed bytes, or nothing is sent** (threat model "What must hold"; spec `pty-protocol/v1` §5.1).
  **Why option B (the design decision of this re-plan).** While readline reads a line it forces a fixed set of terminal fields ("the readline-forced fields", R). Measured live on the host's bash 5.3.9 (Plan revision, 2026-10-17: termios read from the PTY master while readline waited, then after a foreground `stty icrnl inlcr istrip inpck`, then while a command ran): R is at least `c_lflag` ISIG on, ICANON off, ECHO off (also v3's trace, `iteration-v3/check-advisory-adversary.md:5`: `ISIG, prepped`); `c_iflag` ICRNL, INLCR, ISTRIP, INPCK off; `c_cc` VMIN=1, VTIME=0, VLNEXT and VDISCARD disabled. The foreground `stty icrnl inlcr istrip inpck` was invisible while readline held the terminal and visible while the next command ran. Do confirms R against readline's `rltty.c` (`prepare_terminal_settings`) in bash 5.3.9 and widens it if readline forces more, naming each extra field in build-notes. The old phrase "the masked bits" in this brief now means all of R. So a change the shell makes to a field in R cannot change the bytes readline reads from a paste. It changes how the command runs afterwards (Ctrl-C/Ctrl-Z off, no echo). No reproducer in five rounds produced a marker this way. Rounds 3–5 used an fd-4 pipe handshake to read the masked bits after the hooks, and every round found a way around it, because any process of the user can reopen bash's fd 4 through `/proc` (v5 security review, 5 of 5 runs). Option B drops the handshake. The claim is split into three parts:
  **(1) Bash state that can change paste bytes degrades before the next paste.** That is everything in Table A below, captured in `H` after the last code that can run synchronously before readline (the user's `PROMPT_COMMAND` elements already run before `__nls_snap`, `session.py:126-131`, `:177`). **All traps** move into `H`, not only DEBUG/RETURN: on the base, traps are only reported in `T` (`session.py:164`, `:177`), so a signal-trap handler could run `bind …` while readline waits, after the snapshot. `T` stays as a record for the gate.
  **(2) The whole termios state while readline holds the terminal** is read from outside bash (via the PTY master) **immediately before every paste** and compared, every field including R, with a baseline taken in that same state at the first prompt. Fields outside R (`intr`/`susp`/… characters, IXON, IEXTEN, the other flags) carry the shell's own settings, so a confirmed `stty intr '|'` shows here. Fields in R must equal readline's forced values; a mismatch means something changed the terminal while readline held it (e.g. a background job's `stty -isig` or `stty istrip`), and is tampering. Any difference degrades with code `outside-check` and the paste is not written. This pre-paste check of R against readline's forced values is explicitly allowed and expected. The check-to-write race is the Known gap #147 (decision 1).
  **(3) The fields in R of the shell's OWN settings** (as they are when readline does not hold the terminal) are compared with their startup values (after `~/.bashrc`) no later than the end of the first command that runs under a change: that `run()` ends in `SessionDegraded` with code `outside-check`, and the paste after it is refused. That one command runs with the changed settings. This is a new Known gap (follow-up **#149**). Part (3) is what catches a foreground `stty -isig` or `stty icrnl`; part (2) cannot see it. How and when to read them is Do's choice, but it must not depend on bash waiting for nl-shell (no handshake). A reading that cannot tell the shell's settings from readline's must fail closed (degrade), not pass.
  **Table A rows added to `H`** (compared to the baseline; a difference degrades at that command's snapshot): **every trap** (`trap -p` for all signals plus `DEBUG`, `RETURN`, `ERR`, `EXIT`), `extdebug`, `functrace`, `errtrace`; `xtrace` and `BASH_XTRACEFD`; `declare -p PS4` and `declare -p MAILCHECK`; the enabled/disabled state of every builtin the hooks call, exposed as a module-level tuple `HOOK_BUILTINS`. On `0771812` that is `printf`, `declare`, `set`, `shift`, `return`, `eval`, `:`, `shopt`, `compgen`, `alias`, `enable`, `jobs`, `trap`, `builtin`, plus whatever the new rows add (e.g. `bind`). `unset` is called only while the rcfile loads (`session.py:176`, `:178`), so it is left out. # Security review (advisory) — issue 141, round 7

**Attacker-reachable inputs this diff touches:** session state (threat model "Where untrusted input enters" item 4: traps, `bind`, `stty`, `exec` redirects, `PS4`/`MAILCHECK`, `enable -n`, set by a confirmed command or `~/.bashrc`) and the terminal settings a background job can change. No new input path is added. This round's only behaviour change is the fd 0/1/2 check at E (the end-of-command record) in `_check_fds_after_e`.

## What I checked

- **The new retry at E** (`src/nl_shell/session.py:956-978`, called at `:819-820`). If the first reading of bash's fds 0-2 after E differs from the baseline, it waits until bash is blocked reading the terminal again (`_reading_terminal`, `:861`), or until `_SETTLE` (3 s, `:283`) runs out. Then it reads again, and a difference still degrades the session.
  - Can an attacker use the retry? The only change it lets through is one that bash undoes by itself before readline takes the terminal, which is what bash's own `>&3` redirect for `printf 'E\n'` does. A confirmed `exec >/dev/null`, `exec 2>/dev/null` or `exec </dev/null` lasts past that point, so the second reading still differs. Other processes can't change bash's fds without ptrace (Known gap #137, out of scope).
  - Even if the E check missed something, I1 (the pasted bytes are exactly the confirmed bytes, or nothing is sent) does not depend on it. `_prompt_check` (`:896-917`) compares the fds again right before every paste, while readline holds the terminal (`:788-790`). So the retry can only delay detection by one step. It cannot let a paste through.
  - When the wait times out, the code falls through to a second `_check_fds()` and degrades if the fds still differ (fail closed). When `/proc` can't be read it degrades with the error, and a stopped bash also degrades. I found no path that skips the second reading. `_fds_match` asserts `self._fds is not None` (`:1023`). That assert can only fail on a session that is already degraded, and degraded sessions skip this call (`:819`).
  - Can an attacker cause a hang or use too many resources? The loop is capped at `_SETTLE` and polls every 2 ms. That is the same cap as `_wait_for_prompt`, and it runs at most once per command.
- **Tests for the attacker case.** `tests/test_session.py:1090-1105` (`test_redirected_shell_fds_are_refused`) still requires `exec >/dev/null` and `exec 2>/dev/null` to degrade at their own snapshot with code `outside-check`, and the next paste to be refused with no marker file created. So the retry did not weaken the hostile case. The new `test_fd_check_at_e_waits_out_the_e_redirect` (`:1302-1345`) replays the brief race, with fd 1 pointing at the control pipe at E, and requires the session to stay healthy. That covers the false alarm from round 6. T3 (the full test suite): 401 passed. C4 (the red-before-fix, green-after-fix check): 61 of 164 tests fail without the fix and all pass with it.
- **Everything else in the patch.** The EXIT-trap wording, `H` rows, `HOOK_BUILTINS`, the `PS4`/`MAILCHECK` pins, the R checks (R = the terminal fields readline sets itself while it reads a line), TIOCSTI (the kernel call that pushes bytes into a terminal's input) and the stopped check are carried over from round 6. The sign-off said to keep these as built, and round 6's security review found no I1 bypass in them. I did not re-raise the known gaps #147, #148, #149 or #150 (all settled in the brief).

## Findings

No findings. The retry delays detection of a lasting fd redirect by at most one bounded wait. It does not hide the redirect, and the pre-paste fd check still guards I1. The patch's tests cover the hostile redirect as well as the friendly race.
