# Adversarial review — issue 141, iteration 7 (fd 0/1/2 false-alarm fix)

Toolchain was available (bash 5.3.9, `/proc` readable, `legacy_tiocsti = 0`); pytest was not, so I drove `Session` directly from small scripts in this sandbox (`scratch/`). Gate logs: C4 red 61/164 → green, T3 401 passed.

- NEEDS-HUMAN [human] — **New false alarm, same kind the round-6 sign-off rejected, now in the part-3 reading.** `src/nl_shell/session.py:736-737` takes the shell's own termios reading only on a loop pass after `D` and before `E`. If `D` and `E` arrive in one read, `shell_r` stays `None`, and `session.py:732-733` → `_check_shell_r` (`:956-960`) degrades a healthy session with `outside-check`. Startup does the same through `:581-582` and `:616-621`. The gap from `D` to `E` is only ~5-10 ms, so any stall of nl-shell's Python thread longer than that trips it. Measured on this host, all with the patched tree. (a) Sleeping 10 ms after the paste write (`_write_all` wrapped), then `run("true")`: degraded 3/3. At 5 ms: healthy 3/3. (b) Python pinned to a core with 8 busy loops, bash moved to an idle core (`os.sched_setaffinity(pid,{1})`), 30× `run("true")`: **9 of 10 sessions degraded**. (c) **One busy Python thread in the same process** (the normal shape once #78 puts the session inside the REPL): **10 of 10 sessions start degraded** ("could not be read between its first done record and E"). The unpatched base under (c): 0 of 5. The sign-off's own scenario (everything on one core, 3 or 8 busy loops) gave 0/10 both times, so the gates and the round's load test miss this. Failing closed is what the brief asks for (Defect part 3: "a reading that cannot tell … must fail closed"). But with no handshake, the reading depends on nl-shell being scheduled inside a few-ms window, so the session is unusable in a threaded host. Someone has to choose: accept this, move the part-3 reading somewhere not tied to that window, or relax "fail closed" to "check at the next chance" (which weakens #149's "by the end of the first command").
- NEEDS-HUMAN [impl] — **No test guards the false alarm above.** `tests/test_session.py:1302-1342` replays only the fd-1-at-E race. The (fa) guard (50× `run("true")`) runs unloaded, with Python never stalled. A test that wraps `_write_all` (or `_read_control`) to sleep ~50 ms after the paste, then asserts the session stays healthy, goes red on this patch now. It would pin whatever the human decides above.
- **Unwarranted claim:** the carry-forward says "keep everything else as built (gates green, no I1 bypass found)". Green gates were taken as proof the outside checks don't raise false alarms. They only show that for an idle host and a single-threaded caller. See the first bullet; `session.py:952-960` is the site.
- **Tried to refute the fd fix itself; could not.** (1) The sign-off's load (taskset one core + 3 busy loops, then 8; 10 sessions × 30 `run("true")` + `echo hello`): 0/10 degraded both times. (2) `_check_fds_after_e` (`session.py:977`) re-reads only after a mismatch and only once bash waits on the terminal (or after `_SETTLE`). A real `exec >/dev/null` still differs at the prompt, so it still degrades. `exec </dev/null` hits the deadline and is then checked. A change undone before the prompt is re-checked before the paste by `_prompt_check` → `_check_fds` (`session.py:691-692`). So the retry hides no attack. (3) The new test would go red on round 6's single reading at E: the replayed reading shows fd 1 as bash's fd 3. It also asserts the replay happened (`:1339`), so it cannot pass vacuously. (4) `_read_shell_r`'s "nothing more on the control pipe" rule is sound in order: bash writes `E` before readline sets up the terminal, and nl-shell is the only reader, so a reading taken after readline took the terminal always sees `E` waiting.
