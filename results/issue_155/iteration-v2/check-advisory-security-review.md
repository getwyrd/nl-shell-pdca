# Security review (advisory) — failure-classifier-by-exit-code

Attacker-reachable inputs this diff touches: the confirmed command text passed to `classify` (it can be model output, threat model "Where untrusted input enters" item 5, shaped by text the model read), and the session snapshot's `aliases`, `functions` and `path` (item 4, session state). The `lookup` provider is injected and owned by #156; this module only applies display safety to what it returns. Command output never reaches the classifier: `classify` takes no output argument and never reads `result.output`.

Severity note: a wrong class here does not run anything. It only decides whether a failed command gets a correction offer and is handed to the reader. Both of those still go through the gate and the confirm later (#17, #61). So a privileged command missed here is not the High "privileged step classed lower" outcome, which belongs to the policy gate. It breaks brief decision 1 / ADR-0015 ("never offer anything that touches the sudo password"). I rate it **Low** today, the same rating as the previous round, and it gets worse once #17 is wired.

## Findings

- NEEDS-HUMAN [impl] — **Low (today; worse once #17 is wired)**, `src/nl_shell/failure_classes.py:216-220` (`_coarse`), with `:94` (`_COARSE_DROP`) and `:95` (`_COARSE_SPLIT`), used by `is_privileged` at `:256-273` and `classify` at `:165`. **Input:** the confirmed command text (model-written, item 5). **What goes wrong:** the round-1 fix handled the specific spellings it was shown (`$'sudo'`, `${X:-sudo}`) but not the general trick. A word built by putting an expansion that comes out empty inside a privilege name still runs `sudo`/`pkexec`, yet it is not seen as privileged. A failed run then becomes `OTHER` with `offer_correction=True` and `to_reader=True`. `_coarse` drops only the `$` character and then *splits* on `{}`, `(`, `)` and backticks, so `sud${X}o` becomes `sud`, `X`, `o` and never `sudo`. **Shown by:** I ran the patched module with status 1 and an empty snapshot. Each of these returned `OTHER True True`: `sud${X}o apt update`, `sud$X'o' apt update`, `pk${X}exec x`, `sud${X:+q}o x`, `sud${X#q}o x`, `sud$@o x`, `sud$(:)o x`, `` sud`:`o x ``. In bash (with `X` unset and a `sudo` function standing in for the real one), every one of them called `sudo`. With status 127, `sud${X}o` comes back as `NOT_FOUND`, not `PRIVILEGE`. **Fix the builder can make:** add one more coarse pass that *deletes* every expansion span (`$NAME`, `$@`, `$*`, `$#`, `$-`, `$?`, `$!`, `$0`–`$9`, `${…}`, `$(…)`, `` `…` ``) and joins the pieces, then removes quotes. Match on that pass too (over-matching is the safe direction). Add the rows above to the `PRIVILEGED` table at `tests/test_failure_classes.py:199-209`. Right now that table has only the exact spellings from the round-1 finding, so the test covers the shapes that were reported and not the general bypass.

- NEEDS-HUMAN [human] — **Low**, `src/nl_shell/failure_classes.py:256-273` (`is_privileged`). **Input:** session state (item 4): a function defined by `~/.bashrc`, a raw `\cmd` or a confirmed `source`. **What goes wrong:** `Snapshot.functions` holds only names, not bodies, so a function that wraps `sudo` (`s() { sudo "$@"; }`, then `s apt update`, status 1) gives `OTHER` with a correction offer and a reader handoff. The threat model says "Wrappers, aliases, functions and session hooks don't hide a privileged step". The brief's decision 1 covers aliases only. A human needs to choose one of three: accept this until #12 (the gate already resolves functions against the live snapshot, and the caller could reuse its class); treat any word that names a snapshot function as privileged (over-matches); or carry function bodies in the snapshot. This may already be among the 11 deferred findings from round 1. If so, it is settled.

- NEEDS-HUMAN [human] — **Low**, `src/nl_shell/failure_classes.py:146-153` (`to_reader=kind is FailureClass.OTHER`). **Input:** the output of a failed command that read a sensitive location or dumped the environment (for example `grep x ~/.ssh/id_rsa`, status 1). **What goes wrong:** nothing in this diff yet, because calling the reader is #61's job. But `to_reader=True` does not know about the ADR-0025 secret label, and its name reads like permission to send the output to the reader. The module docstring should say that `to_reader` means only "eligible by exit status", and that the caller must still drop secret-labelled output. Alternatively, #61's brief should state it. A human should decide which of the two owns that check.

## Checked, no finding

- Command output cannot pick the class or the message. There is no output parameter, and the test fixture fills `output` with attack-shaped text (`sudo: wrong password`) that has no effect.
- Display safety at `:359-375`: the shown word and package names go through `isprintable`, `render.has_hidden`, `render.too_many_marks` and a 64-character cap. A bare `str` or `None` from `lookup` is now handled (`:307-311`). At most 5 packages are shown.
- Privilege and not-found messages are fixed text. Neither claims "wrong password" nor suggests re-running anything.
- Resource use: the alias walk is bounded by `seen_aliases` (`:265-272`). The regexes at `:81-95` have no nested repeats, so there is no catastrophic backtracking on long input.
- The `$'…'` decoder (`:223-240`) caps `\U` values at U+10FFFF and does not raise on bad escapes.
- Gates: C4 and T3 pass (`gate-logs/C4-verify.log`, `gate-logs/T3-suite.log`). T2 says no security-relevant path was touched, and that is correct for a new module that nothing calls yet.
