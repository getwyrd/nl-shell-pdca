# Adversarial review — failure-classifier-by-exit-code (iteration 3)

I could not run pytest here (`/usr/bin/python3: No module named pytest`), so I relied on the frozen C4 log for the red/green proof. I ran the patched `classify` directly with `python3 -I` and an empty snapshot, and checked each bash claim with a stand-in `sudo` / `pkexec` / `run0` shell function.

- **Evidence holds.** `gate-logs/C4-verify.log`: green is 185/185. Red is 184/185, and every failure is a `ModuleNotFoundError` from an import inside a test function, with no collection errors. The one test that passes before the fix is `test_this_file_writes_every_non_ascii_character_as_an_escape` (`target/tests/test_failure_classes.py:519`). It checks the test file itself, so passing without the module is expected. The tests call the real `nl_shell.failure_classes.classify` (`target/tests/test_failure_classes.py:73`), not a copy, and they build a real `session.CommandResult`. I found no tautology or mocked-away defect.

- NEEDS-HUMAN [impl] — **The pattern-substitution expansion still bypasses the privilege rule.** `target/src/nl_shell/failure_classes.py:318-324` (`_as_braces`, the `${...}` branch) only keeps the word after `-` `=` `+` operators (`_YIELDS_WORD`, `:266`). It drops `${NAME/pattern/replacement}` completely, and the coarse pass (`_coarse`, `:216-220`) leaves `HOME//*/sud` as one piece whose basename is `sud`. In bash, `${HOME//*/sud}o x` runs `sudo x` (I confirmed this; `HOME` is always set and non-empty, so no assignment is needed). `${HOME/*/pk}exec x` runs `pkexec`, and `X=; ${X/#/sud}o x` runs `sudo`. All three return `OTHER offer_correction=True to_reader=True` at status 1. This is the same bug class iteration 2 was sent back for (`${X:-su}do`), and the value `sud` is written in the text, so the comment's "values the text does not hold" carve-out at `:257-258` does not cover it. Fix: in `_as_braces`, treat `${NAME/pat/rep}`, `${NAME//pat/rep}`, `${NAME/#pat/rep}` and `${NAME/%pat/rep}` as `{,rep}` (or `{,rep,rep…}`), and add these three rows to `PRIVILEGED` (`target/tests/test_failure_classes.py:168`).

- NEEDS-HUMAN [impl] — **An expansion that comes out as `0` is dropped, so `run0` is missed.** `target/src/nl_shell/failure_classes.py:327-328` drops `$#` and `$?` outright, and `:318-324` drops `${#X}` and `${#}` (no `_YIELDS_WORD` match). Only `$((…))` / `$[…]` get the `{,0..9}` treatment (`:310-317`). In bash with `X` unset and no positional arguments (the normal case for an interactive session), `run${#X} x`, `run$# x` and `run${#} x` all run `run0` (confirmed). All three classify as `OTHER True True`. `true; run$? x` only comes back PRIVILEGE by luck: the coarse pass turns it into the glob `run?`. Fix: give `$#`, `$?`, `${#…}` and `${#}` the same `_ARITHMETIC_VALUES` treatment as `$((…))`, and add rows.

- NEEDS-HUMAN [human] — **This is round three of patching one spelling at a time.** Rounds 1 and 2 each fixed the spellings the reviewers showed (`$'sudo'`, `${X:-sudo}`, `sud${X}o`, braces), and each round a new expansion form slips through (above). The fix is now a partial bash expander (`target/src/nl_shell/failure_classes.py:240-412`, about 170 lines) inside a module the brief scoped as "medium" with a placeholder splitter that #12 replaces. Someone has to decide whether rule 1's "ANY shell word" means "every spelling bash can expand to a privilege name". If it does, a word matcher can never fully deliver it. The alternative is to accept a documented residual gap (expansion forms not listed) until #12's parse lands, and record that in the threat model. Neither the brief nor the module comment draws that line clearly. Today the comment at `:257-258` only excludes values that are not in the text, and my first finding shows forms that are in the text still get through.

- **Things I tried that the fix handles:** NUL truncation (`$'sudo\0zz'`, from round 2), `$'\x73\x75\x64\x6f'`, quoted brace items (`s{"u",}do`), one-item sequences (`s{u..u}do`), braces nested inside a default (`${X:-s{u,}do}`), `command sudo`, alias chains, and a lookup that returns a bare `str` or `None` (pinned at `target/tests/test_failure_classes.py:504-511`). All of these returned PRIVILEGE, or behaved as the brief asks. `_brace_expand` / `_brace_close` take quadratic time on many unmatched `{` (8000 of them took 0.84 s), which is too small to file.

- **Where the reviewer may have been too generous:** `check-gates.json` reports C4/T3 as passing, and they do pass. But the C5 adequacy claim that rule 1 is now covered rests on the `PRIVILEGED` table (`target/tests/test_failure_classes.py:168-254`, the rows from :212 on), and that table again lists exactly the spellings from the round-2 finding. It is a record of reported cases, not evidence that the general bypass is closed.
