# Security review (advisory): issue 155, failure-classifier-by-exit-code

Attacker-reachable inputs this diff touches: the confirmed command text (it starts as a model proposal, threat model "Where untrusted input enters" item 5, which untrusted text can steer) and the session snapshot's `aliases`, `functions` and `path` (item 4, which a sourced repo script or `~/.bashrc` can set). The command's `output` is never read by `classify`, so input item 1 does not reach it.

Rated on `.oss-scanner/threat_model.md` "How we rate severity". Both findings below are **High** ("a privileged or destructive step is classed lower"). In practice the impact is delayed: `classify` has no caller yet (#17 wires it in), and the policy gate's confirm still runs before the command. What breaks is the classifier's own promise that a privileged failure gets no correction offer and its output never goes to the reader.

- NEEDS-HUMAN [human] — **High**, `src/nl_shell/failure_classes.py:106` (`_CUT`) vs `:109` (`_REDIRECTION`). Input: the command text (model-proposed, then confirmed). Problem: P3 cuts at every `&` and `|` *before* it looks for redirections. So the operators `>&`, `<&`, `>|` (and `&>` when a space follows it) never survive the cut, and the fd number or target file after them becomes the segment's "first word". That word is a plain name, so the real command word after it is never checked. Reproducer (run on the patched tree): `is_privileged("2>&1 sud${X}o x")`, `">&2 sud${X}o x"`, `"<&0 sud${X}o x"`, `">| out sud${X}o x"` and `">& out sud${X}o x"` all return `False`. `classify(status=1, …)` would then give OTHER with `offer_correction=True, to_reader=True`. Bash really runs the hidden word: `bash -c '2>&1 ec${X}ho RAN-1; >&2 ec${X}ho RAN-3'` prints both lines. `2>&1 cmd` is a very common prefix, so this does not look odd to a reader. The brief's P3 text has the same order (cut first, then a skip list that names `>&`, `<&`, `>|`, `&>`), so the code follows the rule as written. Under the brief's review bound that makes this a gap in the rule, not a build bug. The human needs to choose: amend P3 (for example, fold the redirection operators that contain `&` or `|` into a placeholder before cutting; it is still stateless and only a few lines), or record the form for #12. The new Known-gaps bullet (`.oss-scanner/threat_model.md`, the `failure_classes` bullet) does not name it. Its kind (1) says "behind a plain first word", but here the hidden word *is* the command word, so the bullet claims more than holds. No test row covers a redirection operator that contains `&` or `|` in front of a non-plain word: the test file only has `"> out sud${X}o x"` and `"2>/dev/null sud${X}o x"`.

- NEEDS-HUMAN [impl] — **High**, `src/nl_shell/failure_classes.py:284-293` (`_parse_aliases`). Input: `snapshot.aliases`, the raw `alias -p` text. Session state is attacker-controlled (threat model input item 4). Problem: an alias value can hold a newline, and `alias -p` prints it inside single quotes on several lines. A value line that starts with `alias NAME=` is read as a new alias, and a repeated name overwrites the real one (`values[match.group(1)] = value`). Reproducer: set `alias s=$'sudo -v\nalias s=ls #'`. Bash prints `alias s='sudo -v` / `alias s=ls #'`, the parser keeps only `s -> "ls #'"`, and `is_privileged("s x", (), that_text)` returns `False`. Bash runs the real value: with `echo RAN-ALIAS` in place of `sudo -v`, `bash -ic` on `s x` prints `RAN-ALIAS`. The real value is privileged by P1, so P5 as written covers this, and the code gets it wrong. The builder can fix it by iterating. Options: treat a name that appears more than once as privileged (the safe direction), or run P1–P3 over the whole raw alias text of every alias the command names, or parse each value by its quoting instead of by line starts. Add test rows for a repeated alias name and for a multi-line alias value.

Checked, no finding:
- Display safety: the 127 command word and each package name go through `_displayable` (`:355-358`): printable ASCII, no space, 1–64 characters. A word with ESC or U+202E fails P3 first, so it never reaches `message`. The fixed messages contain no command or output text otherwise.
- Untrusted output: `classify` never reads `result.output`, and the signature has no output parameter. `test_output_does_not_change_the_class` pins this.
- Bounded work: alias recursion stops at depth 8 and keeps a memo per call, so the Python recursion depth stays bounded. The lookup result is cut at 1000 items with `islice`, and lookup errors are caught. `snapshot.path` causes one `stat` per entry, which is linear in the input. A depth-cut chain that later hits the memo is not a miss: a memo entry of `False` means the full value was checked.
- Path entries: an empty, `.` or relative `PATH` entry gives no suggestion, so there is no guess about the session's directory. The word cannot hold `/`, so `os.path.join` cannot point outside the entry.
- `coproc X { sud${X}o x; }`, `exec sud${X}o x` and `time -p …` pass the check, but they fall under Known-gaps kind (1), which the human accepted. Not raised.
- Gate evidence: `check-gates.json` is `overall: pass`, and the C4 log shows the tests red without the fix and green with it. The tests cover the attacker forms the brief lists, but not the two forms above.
