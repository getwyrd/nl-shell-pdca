# Adversarial review — ast-policy-gate-shell-layer (iteration 3)

I could not re-run the gate here: `tree_sitter` is not installed in this sandbox (`ModuleNotFoundError`). Whether the tests go red then green therefore rests on `gate-logs/C4-verify.log` (153 of 153 fail before the fix, all on the missing module) and `gate-logs/T3-suite.log` (1254 passed). The red leg proves only that `nl_shell.gate` does not exist on `main`. It does not show that any single assertion would catch a regression. That is expected for brand-new code, so I don't count it against the patch. I did run every bash behavior below with real bash 5.3.9 (the version Ubuntu 26.04 ships). The gate-side results come from reading the Python code. Where they also depend on how tree-sitter shapes the tree, I say so.

- NEEDS-HUMAN [impl] — **A glob in a redirect target reaches fd 3 and is not rejected.** At `src/nl_shell/gate/parse.py:613-616`, the descriptor-path check runs `_descriptor_path(target.value)` on the raw glob text. `/dev/f?/3` does not fullmatch `_DESCRIPTOR_DIRECTORY` (`parse.py:81`), so the check returns None and `_output` (`:638-641`) only raises to `mutating`, with `rejected=False`. Bash expands globs in redirect targets. In real bash, `exec 3>h3.txt; echo viaglob >>/dev/f?/3` and `echo viaglob2 >>/d*/fd/3` both wrote to fd 3. This breaks the rule the patch adds to `.oss-scanner/threat_model.md:120-122` ("a redirection the gate cannot prove uses only descriptors 0-2 … is rejected"). Fix: for a file target with `literal=False` whose value holds a glob character, reject it unless the text before the first glob character rules out `/dev/` and `/proc/`, or simply reject every globbed redirect target. Add `echo x >/dev/f?/3` and `echo x >>/d*/fd/3` to `test_descriptor_not_provably_below_three_is_rejected` (`tests/test_policy_gate.py:268-305`).
- NEEDS-HUMAN [impl] — **`/proc/<pid>/root/…` gets around the descriptor-path rule.** `_DESCRIPTOR_DIRECTORY` (`parse.py:81`) matches only `/dev/fd` and `/proc/X[/task/Y]/fd`. In real bash, `exec 3>r3.txt; echo viaroot >>/proc/self/root/dev/fd/3` wrote to fd 3. `/proc/self/root/proc/self/fd/3` works the same way. The gate classes these as plain output redirections (`mutating`, not rejected). Fix: before matching, strip any leading `/proc/[^/]+/root` prefix, repeatedly, or reject any target under `/proc/*/root/`. Add both forms to the test above.
- NEEDS-HUMAN [impl] — **A named descriptor that uses an array element (`{a[0]}>`) is missed.** `_named_fd_before` (`parse.py:482-497`) only accepts `[A-Za-z0-9_]` between the braces (`_NAME_BYTES`, `:76`). Bash also takes an array element. Real bash: `exec {b[1]}>out6.txt` gave a new fd (10), and `a=(4); exec {a[0]}>&-` closed fd 4 for the rest of the shell, so a later `echo >&4` failed with "Bad file descriptor". `exec {a[0]}>&-` is the array-element form of `exec 3>&-`, which the brief says must be rejected. In the gate, the scan stops at `]`, sees no `{`, and returns False. The `>&-` itself gets no finding either (`>&-` is in neither operator branch, `:618-636`). Fix: when the byte before the redirect is `}`, scan back over `[`, `]` and subscript bytes too, or treat any `…}` right before a redirect as a named fd (fail closed). Add `exec {a[0]}>&-` and `{a[0]}>x` to the test. (The parser part is unverified: if tree-sitter turns `{a[0]}` into an ERROR, the result is `unparseable`/`mutating`, but it is still not rejected.)
- NEEDS-HUMAN [impl] — **A line continuation inside double quotes hides a command substitution (unverified on the parser side).** In real bash, `echo "$\⏎(echo RAN)"` prints `RAN`. `_check_continuations` (`parse.py:304-326`) lets a continuation through when the node under it is `string_content` (`_CONTINUATION_TOKENS`, `:88-91`). tree-sitter-bash has no `$(` token there, so it most likely reads `$` as an anonymous token and `\⏎(echo RAN)` as `string_content`. `_evaluate` (`:419-426`) then reads only the named `string_content` children: the value is literal, the anonymous `$` is dropped, and there is no `command_substitution` node, so `rm x` in `echo "$\⏎(rm x)"` never reaches the command layer. The test only covers the unquoted form (`tests/test_policy_gate.py:339`). Fix: fail closed (`SplitContinuation`) when a continuation inside `string_content` comes right after a `$` or a backquote. Separately, make `_evaluate` for `string` return `(None, None)` when the string has any child token other than `string_content` and the quotes. Add `echo "$\⏎(rm x)"` to `test_split_line_continuation_fails_closed`.
- NEEDS-HUMAN [impl] — **bash 5.3 `${ cmd; }` / `${| cmd; }` (funsub: a command substitution that runs in the current shell) is not counted as a substitution (unverified on the parser side).** In real bash 5.3.9, both `echo ${ echo FUNSUB; }` and a here-doc body line `${ echo INHEREDOC; }` run the command. The pinned grammar predates this syntax. `_substitutions_in` (`parse.py:710-722`) counts only `$(` and backquotes, so `UnreadHeredoc` does not fire for `cat <<E⏎${ rm x; }⏎E`. The inner command produces no invocation. The best case is `unparseable` (`mutating`), which with real rules would hide a `destructive` command. That breaks the walk-coverage criterion ("every simple command inside … command substitutions reaches the command layer"). Fix: in `_substitutions_in` and on `expansion` nodes, treat `${` followed by a blank, a newline or `|` as a substitution the parser did not read, and fail closed.
- NEEDS-HUMAN [human] — **A non-literal redirect target is never checked for fd 3 or higher.** Real bash: `x=/dev/fd/3; echo viavar >$x` wrote to fd 3. At `parse.py:610`, the descriptor-path check is skipped when `target.value is None`, so `>$x` and `>"$f"` are only `mutating`. The threat-model text this patch adds (`.oss-scanner/threat_model.md:120`) promises that "a redirection the gate cannot prove uses only descriptors 0-2" is rejected, and the gate cannot prove this for `>$x`. Rejecting every non-literal output target would be a large change in behavior. So either the threat-model wording should be narrowed, or the rule extended. That is a scope decision.
- NEEDS-HUMAN [human] — **Arithmetic assignment to a §3 variable reaches no layer.** Real bash: `((PATH=0)); echo $PATH` prints `PATH=0`. There is no `variable_assignment` node, so `check_assignment` never runs. `((…))` is not a command, so no invocation goes to #197's command layer either. The brief puts "forms with no plain `variable_assignment` node" in #197, but #197 only sees invocations. So `((IFS=0))`, `: $((PATH=0))` and `((SUDO_PROMPT=1))` currently have no owner in any child. The result today is `mutating` ("no simple command was classed", `src/nl_shell/gate/__init__.py:134-136`), not `session-altering` or rejected.
- I also tried these and could not break them: the move form `>&3-`/`1>&3-` (`parse.py:624-627`, tested); `/dev/fd/03` and `//dev/fd/3` (`normpath` plus the slash collapse); a backslash-newline before a redirect (`3\⏎>y`, `>\⏎&3`, both tested); a digit run before a redirect after a quote (`''3>y`, correctly read as an argument); the `{name}` window bound; the input-byte budget being charged before `encode`/parse (`parse.py:290-294`, `__init__.py:115-117`); and `classify` never raising (`__init__.py:86-97` catches `Exception`). I had no tree-sitter to confirm the test cases pass. The T3 log shows they do.
