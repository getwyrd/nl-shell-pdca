# Adversarial review — issue #196 (ast-policy-gate-shell-layer), round 2

The toolchain was available: I installed `tree-sitter==0.26.0` and `tree-sitter-bash==0.25.1` into a scratch venv and ran `tests/test_policy_gate.py` against `$PDCA_TARGET`. All 90 tests pass. The C4 log (`gate-logs/C4-verify.log`) shows 90 of 90 red before the fix, which is expected for a new module. The tests call the production `nl_shell.gate.classify` and `parse.walk`, not a copy. The round-1 findings are fixed: `>&3-`, `1>&3-` and `>&"3"-` are now rejected (`parse.py` `_MOVE_TARGET` branch), and a 64 KB worst-case input classes in about 0.1 s. Each case below was run by hand, and the bash behaviour was checked with real bash.

- NEEDS-HUMAN [impl] — **A line continuation hides an fd-3 redirect from the §5 rule.** `src/nl_shell/gate/parse.py:260` hands the raw text to tree-sitter. tree-sitter-bash does not join backslash-newline inside a redirect operator, but bash does (I checked: `exec 3>f; echo via-cont >\⏎&3` writes to `f`; `echo d 1\⏎>/dev/null` prints nothing). Gate results:
  - `echo x >\⏎&3` gives `mutating`, `rejected=False` (unparseable, "output redirection: '>'", and a phantom command `3`). The same command written as `echo x >&3` (row 25) is rejected.
  - `echo x <\⏎&3` gives `mutating`, not rejected.
  - `echo x 3\⏎>y` **parses cleanly** (no unparseable flag): `3` becomes an argument word and `>y` an fd-less redirect, so the result is `mutating`, not rejected. Bash runs it as `3>y`, which the brief requires to be rejected.

  This breaks "a descriptor the gate cannot prove is below 3 is rejected". The threat-model text added by this diff (`.oss-scanner/threat_model.md`, "Until #191, a command that tree-sitter-bash parses differently from bash is in scope as a gate bypass") puts it in scope. Fix: before parsing, fail closed (or reject) when the text has a backslash-newline outside single quotes next to a redirect operator or digit. The simplest version: any unquoted `\⏎` in a proposal means the fd rule cannot be proved, so reject. Add all three to `test_descriptor_not_provably_below_three_is_rejected` (`tests/test_policy_gate.py:282`).

- NEEDS-HUMAN [impl] — **A command inside a `number` node never reaches the command layer.** `parse.py:773` lists `number` in `_LEAVES`, so `_leaf` does not walk its children. tree-sitter-bash puts the substitution in `echo $((10#$(rm x)))` under `number`: `(arithmetic_expansion (number (command_substitution (command …))))`. The walk produces one invocation (`echo`) for two `command` nodes, so `rm x` is never classed. Bash does run it (`echo $((10#$(echo 7)))` prints `7`). The class is still `mutating` today only because the stub floors everything. Once #197 classes `echo` as read-only, this hides a `destructive` command. This breaks the brief's walk-coverage criterion ("every simple command inside … command substitutions reaches the command layer"). Fix: handle `number` with `_children`, like `word`, whose children `_evaluate` already guards against. Add a test that, for every leaf-handled kind, parses inputs and asserts the node has no named children, or more simply counts `command` nodes against invocations. The current "every kind has a handler" test cannot catch a handler that drops children.

- NEEDS-HUMAN [impl] — **`<<-` here-doc with a tab-indented first line: the substitution is recorded as literal stdin text and its command is missed.** For `cat <<-E⏎\t$(rm x)⏎E`, tree-sitter-bash 0.25.1 returns a `heredoc_body` with **no** `command_substitution` child (the same body without the tab, or with a non-tab first line, does parse it). `_heredoc_text` (`parse.py:571-581`) only checks for `\` and non-`heredoc_content` children. So the invocation gets `Stdin(heredoc, text='$(rm x)\n')`, marked literal, and `rm x` produces no invocation. Bash expands it (`cat <<-E⏎\t$(echo RAN)⏎E` prints `RAN`). Backticks behave the same: `` \t`rm x` ``. The brief says only *literal* here-doc text is recorded, and child-3's here-doc exemption will trust that text. Fix: when the delimiter is unquoted, treat any `$` or `` ` `` in the body text as non-literal (text=None), whatever the tree says. If the tree has no substitution node for it, fail closed. Add the case to `test_literal_input_text_is_recorded` (`tests/test_policy_gate.py:387`) as a negative.

- NEEDS-HUMAN [impl] — **A redirect after the last pipeline stage is given to the wrong stages.** tree-sitter-bash attaches a trailing redirect to the whole pipeline: `(redirected_statement body: (pipeline …) redirect: …)`. `_redirected_statement` (`parse.py:632-641`) applies that redirect's stdin and redirects to the pipeline, and `_pipeline` (`:619`) then gives it to the **first** stage. Results:
  - `a | b <x`: the gate records `a` as stdin=file `x` and `b` as pipe. In bash, `a` reads the terminal and `b` reads `x`.
  - `a | cat <<E | sudo tee /x⏎x⏎E`: the gate records `a` as heredoc `'x\n'` and `cat` as pipe. In bash, `a` reads the terminal and `cat` reads the here-doc.

  This is the fail-open direction for child-3. Take `sudo -v | cat <<E⏎y⏎E`: the gate says sudo's stdin is a literal here-doc, but it actually reads the terminal. That is the same class of stdin bug as the v2 regression the brief names. `test_second_stage_reads_the_pipe` (`tests/test_policy_gate.py:373`) only checks the *last* stage, so it passes anyway. Fix: when a `redirected_statement` body is a pipeline, apply its redirects to the last stage only. Assert stdin on **every** stage in the test.

- **Minor, also tree shape:** `cat 0<x` parses as argument `(number)` `0` plus an fd-less `<x`, so the invocation's words are `['cat', '0']`. Stdin comes out right (descriptor 0 either way) and `2<x`/`3<x` parse correctly. The phantom `0` operand will mislead #197's operand rules (e.g. `rm -rf a 0<x` gets an extra operand `0`). This is low impact, so I give it no tag. It belongs with the redirect fix above if the builder is already in `_command`.

- **Reviewer claims that do not hold:** the threat-model text this diff adds says "the budget is spent before the parse, so no input costs the gate more than linear time". I measured it and it holds. The threat-model line "every named node kind of that grammar has a handler" is true but does not show that syntax is closed: the `number` leaf above has a handler and still drops a command. I attempted, but could not refute, these: §3/§5 assignment matching (`SUDO_PROMPT[0]=x`, `export SUDO_PROMPT=x`), named-fd detection (`exec {fd}>x`, `{fd}>&-`), the input budget on `$(`×32k, `` ` ``×64k and `{`×64k, `//usr/bin/rm`, and the "nothing is read-only" invariant (no input gave `read-only`).
