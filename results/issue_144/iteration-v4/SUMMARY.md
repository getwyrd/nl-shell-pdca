## Findings

- NEEDS-HUMAN [human] — `src/nl_shell/render.py:144-146` and `:193-197` (`WORD_SEPARATORS` / `mixed_script_word`). **Shell quotes and backslashes get around the mixed-script rule.** The word splitter breaks at every ASCII punctuation character, including `"`, `'` and `\`. Bash does the opposite: it joins `"с"url` back into the single word `сurl`. Reproduced on the patched tree with `proposal.parse(...)`:
  - `"с"url example.com` → accepted (bash runs the word `сurl`, with Cyrillic U+0441)
  - `с''url x`, `с\url x`, `с$@url x` → accepted
  - `ls /tmp/с""url` → accepted (bash opens the path `/tmp/сurl`), while `ls /tmp/сurl` is rejected
  - `cat D""окумент.txt` → accepted, while `cat Dокумент.txt` is rejected

  `WORD_SEPARATORS.split('ls /tmp/с""url')` gives `['ls', 'tmp', 'с', 'url']`, so each piece has one script and passes. A proposer only needs one pair of empty quotes to defeat test vectors (3) completely. The builder followed the brief here: Scope (3) says to split "at ASCII whitespace and ASCII punctuation (`string.punctuation`)". So the defect is in the brief, and changing the split rule is a scope decision, not a slip. Possible fix: drop `"`, `'`, `\` (and maybe `$`, `` ` ``) from the separator set, or remove them before splitting, so a shell-concatenated word is checked as one word. Then add `"с"url`, `ls /tmp/с""url` and `с\url` to `MIXED` in `tests/test_charsafety.py:160`. The other option is to record this as a known gap for #12's bash parser in the threat model. As it stands, `.oss-scanner/threat_model.md` (the new text at the "What the user confirms is exactly what runs" bullet) says a word that mixes scripts is rejected "anywhere in a `command`, quoted or not". For words built by quote concatenation, that claim is wrong.

- `tests/test_charsafety.py:79-86` (`assert_rejected`). Minor, not a NEEDS-HUMAN item. The test checks only that a proposal was rejected, not which rule rejected it. I checked every vector in `MIXED` and the mark vectors, and none of them trips a different rule (none holds a hidden character), so for now each vector really does test the rule it is named for. A future vector could pass for the wrong reason, though.

## What I tried to refute and could not

- **Red→green evidence.** `gate-logs/C4-verify.log`: with the fix reverted, 50 of 58 fail. The 8 that pass on the old code are the accepted vectors, which is expected. Every rejection vector goes red, including test (5) and the static `unicodedata` check. The tests go through the real `Repl` → `proposal.parse` → `render`, not a copy of it.
- **Vendored tables.** I re-ran `scripts/gen_unicode_tables.py` against `/usr/share/unicode` (16.0.0). Its output is **byte-identical** to the committed `src/nl_shell/_unicode_tables.py`. None of `render.py`, `proposal.py` or `_unicode_tables.py` mentions `unicodedata`.
- **Highly Restrictive logic** (`render.py:185-190`). Latin+Han, Latin+Hiragana, Han+Hangul and `iPhoneの用` are accepted. Hiragana+Hangul, Bopomofo+Hiragana, Cyrillic+Han and Cyrillic + Arabic-Indic digit (`с١`) are rejected. All of these match UTS #39 §5.2.
- **Mark limit** (`render.py:164-171` and the run counter in `escape`). The parser and `escape` agree. A spacing mark (Mc, e.g. U+0903) between marks resets the run in both, so nothing gets past the parser that `escape` would still show raw. Runs of Mc or Lo (`ििि`, `ำำำ`, `ᅡᅡᅡ`) are accepted, but the brief limits the rule to Mn/Me, so this is not a defect of this diff.
- **Hidden set.** U+2003, U+2061, U+200D, U+3164, U+1D173 and U+0D4D inside a Latin word are all rejected. U+0F0C, U+115A and an all-Cyrillic `ас` are accepted, but the human's iteration-3 decisions put look-alikes and blank glyphs outside the named list out of scope.

## What I checked (no finding)

- **Hidden set.** I ran crafted commands against the patched tree. U+3164, U+FFA0, U+2001, U+1680 and `rm -rf /⠀` are all flagged by `has_hidden`. Lone surrogates, tags, bidi, Cf, Co and Cn come from the vendored tables, and the static test at `tests/test_charsafety.py:200-208` closes the `from unicodedata import ...` hole from iteration 3. The checks run on the whole `command`, quoted or not, and come before the rule-2 checks, so no path to a `Command` skips them.
- **Mark limit.** The parser (`render.py` `too_many_marks`) and `escape` count runs the same way: Mn/Me only, and any other character resets the count. So what is rejected and what is escaped match. Two marks on each of several letters (`à̀b̀̀`) is accepted, which matches the brief.
- **Mixed script.** `сurl` with a Cyrillic letter and Inherited/Common characters inside (`с́url`, `сurl҅`) is still rejected. `cat iPhone用.txt` and `cat 2024年report.txt` are accepted, as the human decided.
- **Generator** (`scripts/gen_unicode_tables.py`). It reads Script_Extensions over Scripts.txt, strips Zyyy/Zinh only after that override (so U+0485 keeps `Cyrl Latn`), and fails on a UCD version mismatch. It is build-time only and nothing at runtime reads attacker data through it.
- **Resource use.** Each check is a linear pass with a binary search per character, over a `command` whose length is already capped (`proposal.py`, the length check just above line 133). There is no way to make it blow up.
- **Tests vs. the attacker case.** `tests/test_charsafety.py` feeds every vector as a stub model response through `Repl`, which is the attacker-reachable path, not only the easy one. C4 was red without the fix (50 of 58 failed), and C4 and T3 (539 passed) are green with it (`gate-logs/C4-verify.log`, `gate-logs/T3-suite.log`).

## Findings

- NEEDS-HUMAN [impl] — **Low**, `src/nl_shell/render.py:139-143,190` against `.oss-scanner/threat_model.md:184-188`. **Input:** a proposal `command`, controlled by the model or a text-only attacker steering it. **What goes wrong:** Highly Restrictive (the human's decision) lets Latin mix with Han, Hangul or Bopomofo inside one word. Some letters in those scripts look like Latin letters or ASCII punctuation, and they pass every check and print raw. On the patched tree, `render.mixed_script_word` returns `None` and `has_hidden`/`too_many_marks` return `False` for: `curㅣ example.com` (U+3163 HANGUL LETTER I, looks like `curl`), `ech〇 hi` (U+3007 IDEOGRAPHIC NUMBER ZERO, looks like `echo`), `ls 一la` (U+4E00, looks like `ls -la`) and `cat ㄧetc` (U+3127 BOPOMOFO LETTER I). Bash still runs the same bytes that are shown, so this is a look-alike problem, not a byte mismatch. The policy allows it by design. The gap is that the new known-gap bullet only lists look-alikes "within one script or in Common". These cross-script look-alikes are neither, and the bullet does not name them. A reviewer reading the threat model would expect `curㅣ` to be rejected as mixed script. **Fix (docs only, no change to the rule):** widen the known-gap bullet at `threat_model.md:184` to say that look-alikes from Han, Hangul or Bopomofo mixed with Latin, which Highly Restrictive allows, are also left to #74. Optionally, add `"curㅣ example.com"` as an accepted vector in `tests/test_charsafety.py` so the documented behaviour has a test. If the human would rather close the gap than document it (for example, allow Latin+Hangul or Latin+Bopomofo only when the word also has Han), that is a scope decision and goes back to them. It is filed as `[impl]` because the minimum fix is the doc sentence.
