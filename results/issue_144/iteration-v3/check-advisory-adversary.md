- NEEDS-HUMAN [impl] — `src/nl_shell/render.py:58` (`BLANK_SYMBOLS`). **Input:** a proposal `command` of `ls /tmp/\U00013441` or `cat \U00013442.txt`. U+13441 is EGYPTIAN HIEROGLYPH FULL BLANK and U+13442 is EGYPTIAN HIEROGLYPH HALF BLANK, both category Lo and script Egyp. In UCD 16.0 neither is Default_Ignorable or White_Space. **What goes wrong:** each character is a whole word with one script, so the mixed-script check passes. The mark limit passes, and `has_hidden` returns False. I ran it: `proposal.parse(...)` returns `Command(command='ls /tmp/𓑁', …)` and `render.escape` prints it raw. The user sees `ls /tmp/` followed by blank space, but bash gets a different path. This is the same hole as U+1D159 (round 1) and U+16FE4 (round 2), and it breaks the brief's invariant "no character that renders as nothing or as blank reaches the user unmarked". **Fix:** add `(0x13441, 0x13442)` to `BLANK_SYMBOLS`, add both to `HIDDEN` in `tests/test_charsafety.py:100`, and update the list in the threat model (`.oss-scanner/threat_model.md:133-134`).
- NEEDS-HUMAN [human] — `src/nl_shell/render.py:56-58`. This is the third round in a row where a blank glyph got past the property-based set and was fixed by adding it to `BLANK_SYMBOLS` by name (U+2800, then U+1D159, then U+16FE4, and now U+13441/U+13442). The human rejected exactly this hand-kept-list approach at the iteration-3 sign-off of #16. Unicode has no property for "drawn blank", so this set will never be complete, and every round that adds one more code point leaves the next one open. A human should decide which of these holds: (a) the invariant is "the property-defined set plus a named list of known blanks" and the brief's "no character that renders … as blank" wording should be narrowed to match; or (b) proposal commands are limited further, for example to the UTS #39 §3.1 Identifier_Status=Allowed set (U+13441/2 and the other blanks are Restricted, being in a Limited-Use or Excluded script). Without that call, auto-iterate will keep finding more of these.
- NEEDS-HUMAN [impl] — `tests/test_charsafety.py:16` and `:198-229`. Test (5) checks that the code ignores the runtime `unicodedata` by monkeypatching `unicodedata.category` (patching the function at run time). But `nl_shell.render` is already imported when the test file loads, through `from nl_shell.repl import Repl` (line 16) → `src/nl_shell/repl.py:21`. **Regression the test misses:** suppose `render.py` is changed to `from unicodedata import category` and `is_mark` becomes `category(c) in ("Mn", "Me")`. `render.py` then holds a reference to the real function, made before the patch runs, and every test still passes on Python 3.14. The fake only catches code that looks up the attribute through the module each time. **Fix:** add a static check, for example assert that `"unicodedata"` does not appear in the source of `nl_shell.render`, `nl_shell.proposal` and `nl_shell._unicode_tables`. Or run the policy in a subprocess with a stub `unicodedata` module placed first on `sys.path`.

This counts as a same-script look-alike, which the brief puts out of scope ("whole-script confusables and skeleton matching", #74). So it doesn't refute this diff. I'm noting it only so the human knows that §3.1 (cited in the Invariant) isn't actually applied. No action needed for this patch.
