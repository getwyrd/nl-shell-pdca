# Security review (advisory) — issue #144, charsafety-uts39-policy, round 5

**Attacker-reachable inputs touched:** the proposal `command` string (threat model "Where untrusted input enters" item 5, the model's output, which can be steered by a text-only attacker). It reaches `nl_shell.proposal._parse` → `render.has_hidden` / `too_many_marks` / `mixed_script_word` (`src/nl_shell/proposal.py:133-138`), and `render.escape` on every display path. Typed requests reach only `escape` (in `:context`).

The rubric is `.oss-scanner/threat_model.md`. The bullet that matters is "What the user confirms is exactly what runs" (`.oss-scanner/threat_model.md:127-141`), which now says a word that mixes scripts is rejected "anywhere in a `command`, quoted or not". Severity uses the threat model's scale. Neither finding changes what runs compared with what the user confirms: the confirm still shows the exact bytes, and the escaped confirm UI (#74) is the main defence against look-alikes. So both are **Low**. They break a claim the patch makes, not a Critical/High property.

## Findings

- NEEDS-HUMAN [impl] — **Low** — `src/nl_shell/render.py:149-157` (`WORD_JOINERS` / `WORD_SEPARATORS`). **Input:** proposal `command`, controlled by the model / text-only attacker. **What goes wrong:** a backslash followed by a newline is bash line continuation. Bash deletes both characters and joins the two halves into one word. The splitter keeps `\` in the word but splits at the LF, so `с\` + LF + `url` is checked as two single-script words, `с\` and `url`, and passes. Bash then runs `сurl` (Cyrillic U+0441 + Latin). This is the backslash case the round-4 sign-off asked to close ("`с\url x`"), reached through a newline instead. **Reproducer (checked):** `proposal.parse(json.dumps({"kind":"command","command":"с\\\nurl example.com","risk":"read-only"}))` → `Command(...)`, not `Rejected`. `printf 'printf "[%%s]\\n" с\\\nurl\n' | bash` prints `[сurl]`. **Fix:** remove every `\`+LF pair from the command before splitting into words (this matches what bash does). Add `"backslash-newline-inside": "с\\\nurl x"` to `MIXED` in `tests/test_charsafety.py:160`.

- NEEDS-HUMAN [human] — **Low** — `src/nl_shell/render.py:147-157`, with the claim at `.oss-scanner/threat_model.md:135-141`. **Input:** proposal `command`, model / text-only attacker. **What goes wrong:** the round-4 fix stops splitting at quotes, `\`, `$` and backtick. But bash also joins a word across expansions that are empty and are written with ASCII punctuation, which the splitter still treats as a word break: `$@`, `$*`, `${x}`, `${_:0:0}`, `$(:)`, `` `:` ``. Each of these splits the Cyrillic and Latin halves into separate single-script words, so the command is accepted, and bash runs `сurl`. So the threat model's "rejected anywhere in a `command`, quoted or not" is still false. **Reproducer (checked):** `proposal.parse` returns `Command` for each of `с$@url example.com`, `с$*url x`, `с${x}url example.com`, `с${_:0:0}url example.com`, `с$(:)url example.com` and ``с`:`url example.com``. `bash -c 'set --; printf "[%s]\n" с$@url с${x}url с`:`url с$(:)url с$*url'` prints `[сurl]` five times. The patch's `MIXED` vectors (`tests/test_charsafety.py:172-179`) cover only empty quotes and empty backticks, not expansions. **Why [human]:** closing this means adding more expansion syntax to a joiner list. That is a bash tokenizer by hand, which #12's bash parser is meant to supply, and the same list-widening approach the human turned down for the hidden set. A coarser rule (split only at whitespace and shell operators) would reject valid paths such as `ls Документы/file.txt`. The options are: (a) treat `{ } ( ) @ * ! # ? -` after `$` as joiners here and add the vectors above; (b) record "expansions that join words (`$@`, `${…}`, `$(…)`) are not seen as joiners until #12" as a known gap and soften the "quoted or not" sentence; (c) another rule. A human should pick.

## Checked, no finding

- Hidden set (`render.py:115-129`): built only from the vendored tables plus the named `BLANK_SYMBOLS`, now including U+13441/U+13442 as the round-3 decision asked. No `unicodedata` import in the policy modules. `escape` uses the same predicate and the same mark counter as the parser, so what is rejected and what is escaped cannot drift apart.
- `too_many_marks` / `escape`: the mark run resets on every character that is not a mark, so no gap. Everything is linear in command length (capped at 2000 by the schema); binary search over the tables; no hang or memory blow-up reachable from input.
- `_highly_restrictive` (`render.py:196-201`): every character must meet the same allowed set, so Cyrillic+Han and Hangul+Katakana stay rejected (tests at `tests/test_charsafety.py:169-170`). The Latin+Hangul/Han look-alike pass is a documented, human-accepted gap (`threat_model.md:184-192`) and is not raised again.
- Typed input and `:context` only go through `escape`, so no new untrusted path is opened. The generator script (`scripts/gen_unicode_tables.py`) runs at build time only and reads root-owned UCD files, so no attacker input reaches it.
- The gates passed (C4: red 57/66 without the fix, green with it; T3: the full suite is green). The two bypasses above are not in the test set, so a green gate does not cover them.
