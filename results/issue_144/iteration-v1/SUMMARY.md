# Result — issue 144 / charsafety-uts39-policy

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: #143's hidden-character predicate (`src/nl_shell/render.py`, C0/C1/DEL/bidi/Cf/U+2028-9/tags/surrogates) lets through characters that render as nothing, as blank, or as a look-alike letter from another script. A model proposal can therefore hide or disguise part of a command (`ls<U+3164>` is a different word to bash than `ls`; `сurl` with Cyrillic U+0441 is not `curl`). Verified on the iteration-3 build: U+3164, U+115F, U+1160, U+FFA0, U+034F, U+FE00–U+FE0F, U+E0100, U+17B4, U+180B and U+2800 were accepted and printed raw (`iteration-v3` adversary and security reviews).
- Success criterion: `python3 -m pytest tests/test_charsafety.py` passes and covers, each fed as a stub response through `Repl` with the recording stub: (1) each of U+3164, U+115F, U+1160, U+FFA0, U+034F, U+FE00, U+FE0F, U+E0100, U+17B4, U+180B, U+2800, U+00A0, U+3000, U+E000 (private use) and U+0378 (unassigned in Unicode 16.0) inside a `command` → rejected (`No usable proposal came back from the model.`); and the same character in a request → `:context` prints it as its `\xHH` / `\uHHHH` / `\UHHHHHHHH` escape (lowercase hex). (2) `e` followed by three U+0301 in a `command` → rejected; with two U+0301 → accepted. In `:context`, a request with `e` + three U+0301 prints `e`, two raw U+0301, then the six characters `\u0301`. (3) mixed-script words in a `command` are rejected: `сurl example.com` (Cyrillic U+0441 + Latin), `ls /tmp/сurl`, `cat Dокумент.txt`. (4) these are accepted and shown unchanged: `ls Документы`, `cat αρχείο.txt`, `cat 日本語ファイル.txt` (Han + Katakana, allowed by the UTS #39 Japanese combination), `echo café` (precomposed é, and `e` + one U+0301). (5) the vendored tables record their Unicode version as `16.0.0`, and the policy takes every property it uses (including Cn and the Mn/Me categories) from those tables, so U+0378 is rejected and a code point assigned in 16.0 (U+1C89, CYRILLIC CAPITAL LETTER TJE, a Cyrillic letter) is accepted in `ls \u1c89` whatever the interpreter's `unicodedata` version. `tests/test_backend.py` still passes.
- Repo + branch target: eduralph/nl-shell @ main, built on the wave base that folds #143's accepted patch (and, through it, #92). If #143 is not accepted this bundle is not scheduled.
- Scope (one logical fix) / out of scope: (1) Hidden set (rejected in a proposal `command`, escaped on every display path): #143's set, plus every code point with Default_Ignorable_Code_Point (UCD `DerivedCoreProperties.txt`), every White_Space code point (`PropList.txt`) except U+0020, LF and TAB, U+2800 BRAILLE PATTERN BLANK, and general categories Co (private use) and Cn (unassigned in the vendored 16.0.0 tables — not the runtime `unicodedata`, which is 15.0/15.1 on the Python 3.12/3.13 that `requires-python = ">=3.12"` still allows). (2) Combining marks: at most 2 consecutive characters of category Mn or Me after one base character; a `command` with more is rejected; on display, the 3rd and later marks are escaped. (3) Mixed-script words in a proposal `command`: split the `command` into words at ASCII whitespace and ASCII punctuation (Python's `string.punctuation`); a word passes if the intersection of its characters' Script_Extensions sets (UCD `ScriptExtensions.txt`, falling back to `Scripts.txt`), ignoring Common and Inherited, is non-empty, after the UTS #39 §5.1 augmentation (Han ⇒ +Bopomofo, Hiragana, Katakana, Hangul combinations: Hanb, Jpan, Kore); otherwise the proposal is rejected. Typed input and `:context` are not checked for mixed script (the gate's typed-input handling is #12's). (4) Data: vendor only the needed ranges as a generated Python module (e.g. `src/nl_shell/_unicode_tables.py`) with the Unicode version in it, produced by a generator script in `scripts/` that reads the UCD files from `/usr/share/unicode/` (Ubuntu package `unicode-data`, 16.0.0 — the same version as Python 3.14's `unicodedata`, which CI (`.github/workflows/tests.yml:19`) and the gate run); the module also carries the general category data the predicate needs (Cn, Co, Mn, Me, and #143's Cf), and the predicate reads every property from it, never from `unicodedata`; commit the generated module; no new runtime dependency; `requires-python` is unchanged. (5) Rejection applies anywhere in a `command`, quoted or not — stricter than `docs/design/specs/policy-gate/v1.md:58-61` ("outside quotes"); this is consistent with that spec (it is a MUST-reject rule; rejecting a superset breaks none of its requirements), so the spec is not edited here; say so in the threat model and note that #12, which has the bash parser, may relax it to outside-quotes only. (6) Update the threat model's "What the user confirms is exactly what runs" bullet (find it by that text; on main it is `.oss-scanner/threat_model.md:127-129`, and #143 edits its last sentence) to name this policy. # Adversarial review — #144 charsafety-uts39-policy

## What I tried that held up

- **Red→green evidence.** `gate-logs/C4-verify.log:12` shows 43 passed with the fix. `:947` shows 37 of 43 failed with the production change reverted. The 6 that pass on the red leg are the "accepted" cases in (4) and (5), which are supposed to pass either way. Both `ensure_ascii` encodings are fed in (`tests/test_charsafety.py:80,90`). The raw bytes in the mark tests match the brief: 3×U+0301 at `:138`, 2×U+0301 at `:142`, U+00E9 vs `e`+U+0301 at `:174-175`. I could not re-run pytest myself because it isn't installed in this sandbox, so I relied on the logs.
- **Table accuracy.** I compared `src/nl_shell/_unicode_tables.py` (CF, CO, CN, MARK) against Python 3.14's `unicodedata` (Unicode 16.0.0) for all 0x110000 code points: zero differences. `scripts/gen_unicode_tables.py --output <cwd>` run on `/usr/share/unicode` gives a byte-identical file. Every `str.isspace()` code point other than SPACE, LF and TAB is hidden. Noncharacters (U+FDD0, U+FFFE, U+10FFFF) are hidden through Cn.
- **Mark cap.** `too_many_marks` (`src/nl_shell/render.py:140`) and `escape` (`src/nl_shell/render.py:184`) count runs the same way. `e`+U+0301 U+0301 U+20DD (Me) is rejected. A backslash or any non-mark character resets the run in both.
- **Mixed script.** Non-ASCII separators do not split a word, so `ls ·с·url` (U+00B7) is still flagged. `curlеxample.com`, Cherokee `Ꮯurl` and Arabic-Indic digits next to Latin are all rejected.

## Findings

- NEEDS-HUMAN [human] — `src/nl_shell/render.py:94-110,161`: look-alikes from a single script, or from Common (characters shared by all scripts), still pass. `ⅽurl example.com` (U+217D SMALL ROMAN NUMERAL ONE HUNDRED, script Latin) and `𝐜url example.com` (U+1D41C, script Common) are accepted and shown raw. U+217D looks identical to `c`. That defeats the brief's main example (`сurl` ≠ `curl`) with a one-character swap. The brief cites UTS #39 §3.1 (General Security Profile) as normative, but the patch takes only the hidden-character idea from it. §3.1's Identifier_Status=Allowed would reject both of these (both are NFKC-unstable). The brief scopes "confusables / skeleton matching" out and sends this to #74's escaped confirm UI. That is defensible, but the human should confirm that #74 really covers non-ASCII Latin and Common letters, not just "hidden" ones.
- NEEDS-HUMAN [human] — `src/nl_shell/render.py:161-172`: words that mix Latin and Han are rejected, as the brief asks (single script after augmentation). Two ordinary filenames are refused: `cat iPhone用.txt` (word `iPhone用`) and `cat 2024年report.txt` (word `2024年report`). UTS #39's "Highly Restrictive" level allows Latin+Han+Hiragana+Katakana, Latin+Han+Bopomofo and Latin+Han+Hangul for exactly this reason. This follows the human's Plan decision, but the decision didn't weigh this case. Confirm at sign-off, or relax it to Highly Restrictive.
- NEEDS-HUMAN [impl] — `tests/test_charsafety.py:193-205`: test (5) only fakes `unicodedata.category` for U+0378 and U+1C89, which covers Cn and nothing else. The brief defines the set by properties plus U+2800 only, so this follows the brief. I list it so nobody reads "renders as nothing" in the invariant as a complete guarantee.
- Gate wording (not a defect): `gate-logs/T2-threat-model.log` says "no security-relevant path touched", yet the patch edits `.oss-scanner/threat_model.md:127-137` as Scope (6) asks. The gate is advisory and the threat-model edit is there, so this doesn't change the verdict. ### Advisory — security-review

# Security review — #144 character-safety policy (UTS #39)

Attacker-reachable inputs this diff touches: **the model's proposal `command`** (threat model item 5, checked by `src/nl_shell/proposal.py:133-138`), plus model replies, `:context` text and start-up error text printed through `render.escape` (`src/nl_shell/render.py:184`; called from `repl.py:124`, `prompts.py:219`, `cli.py:70`). `scripts/gen_unicode_tables.py` runs only at build time on the trusted local UCD files, so it is not attacker-reachable.

Severity uses the threat model's scale (`.oss-scanner/threat_model.md:236-269`). One caveat applies to both findings: nothing runs yet (the reply is "Nothing runs yet", `tests/test_charsafety.py:19`), and #74's confirm UI will escape all non-ASCII. So neither finding currently gets a deceptive command executed. Both are gaps in the stated invariant ("What the user confirms is exactly what runs", `.oss-scanner/threat_model.md:127-137`), not working exploits. I rate both **Low** today. They would become High ("spoofs the confirm UI") if #74 shipped without its non-ASCII escaping.

## What I checked and found sound

I ran the patched `nl_shell.render` on Python 3.14.4, tables at 16.0.0.
- Every brief vector is rejected or escaped as specified.
- U+2061/U+2062 and U+1D173 (Cf) are hidden, and so are U+FFFE and U+10FFFF (Cn, noncharacters) and U+D800 (lone surrogate).
- The `SCRIPT_EXTENSIONS` table holds no Zyyy/Zinh/Zzzz entries, so Common and Inherited really are ignored as documented.
- Rejection reasons (`proposal.py:134-138`) do not echo attacker text into errors.
- Only `command` is free text. `kind`, `risk` and `reason` are enums (`proposal.py:122-126`), so no other proposal field gets past the policy.
- The `escape` mark counter (`render.py:188-193`) and `too_many_marks` (`render.py:140-147`) count the same way.
- `WORD_SEPARATORS` is a single character class with `+`, so there is no ReDoS (a regular expression that can be made to take exponential time). The work is linear in a `command` that is already length-capped.
- The tests feed every vector as a stub model response through the real `Repl`, both JSON-escaped and raw (`tests/test_charsafety.py:79-94`). That is the attacker path, not just the friendly path.
- The threat-model edit stays inside the named bullet and leaves the sudo bullets alone.

## Findings

- NEEDS-HUMAN [impl] — **Low** — `src/nl_shell/render.py:96-106` (the `_HIDDEN` set). **Input:** proposal `command`, controlled by the model / text-only attacker. **What goes wrong:** U+1D159 MUSICAL SYMBOL NULL NOTEHEAD (category So, not Default_Ignorable, not White_Space) renders as blank in common fonts and is on the usual lists of invisible characters. It passes every check and prints raw. That breaks the brief's invariant "no character that renders as nothing or as blank reaches the user unmarked". **Reproducer:** `render.has_hidden("ls\U0001d159")` → `False`, and `render.escape("ls\U0001d159")` returns it unchanged. As a test, add `"musical-null-notehead-u1d159": ("\U0001d159", "\\U0001d159")` to `HIDDEN` in `tests/test_charsafety.py:98`; it fails today. **Fix:** add it next to U+2800 as a named blank glyph. This adds one code point to the property-based set; it does not go back to a hand-kept list.
- NEEDS-HUMAN [human] — **Low** — `src/nl_shell/render.py:150-172` (`scripts` / `mixed_script_word`). **Input:** proposal `command`, controlled by the model. **What goes wrong:** Mathematical Alphanumeric Symbols (U+1D400–U+1D7FF) have Script=Common. The mixed-script check ignores Common, so a word made of Latin letters plus look-alike math letters passes as single-script Latin. Fullwidth Latin (`ｃurl`) and Roman-numeral letters (`ⅽurl`, U+217D, Script=Latin) pass the same way. **Reproducer:** `render.mixed_script_word("\U0001d5bcurl")` → `None` (`𝖼url` looks like `curl` in many terminal fonts), and the same for `"ⅽurl"` and `"ｃurl"`. Bash sees a different command word. This is how UTS #39 §5.1 is written, so the patch matches its brief. UTS #39's identifier profile (§3.1) and confusable skeletons are what catch these, and the brief puts skeletons out of scope (#74). **The human needs to decide** whether to accept that #74's non-ASCII escaping covers this, or to widen this policy, for example by rejecting characters whose NFKC (Unicode compatibility normalization) form differs from the character itself (`Identifier_Status=Restricted`).

No other finding. The brief's attacker-reachable cases are covered by tests that drive the real parser and display path.
