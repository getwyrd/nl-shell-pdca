# Adversarial review — #144 charsafety-uts39-policy

I tried to break the fix and could not show it wrong against the brief. What's left are two scope questions for the human and one weak test.

## What I tried that held up

- **Red→green evidence.** `gate-logs/C4-verify.log:12` shows 43 passed with the fix. `:947` shows 37 of 43 failed with the production change reverted. The 6 that pass on the red leg are the "accepted" cases in (4) and (5), which are supposed to pass either way. The tests run through `Repl` + `RecordingStub` (`tests/test_charsafety.py:50-61`), which is the real parse and render code, not a copy. Both `ensure_ascii` encodings are fed in (`tests/test_charsafety.py:80,90`). The raw bytes in the mark tests match the brief: 3×U+0301 at `:138`, 2×U+0301 at `:142`, U+00E9 vs `e`+U+0301 at `:174-175`. I could not re-run pytest myself because it isn't installed in this sandbox, so I relied on the logs.
- **Table accuracy.** I compared `src/nl_shell/_unicode_tables.py` (CF, CO, CN, MARK) against Python 3.14's `unicodedata` (Unicode 16.0.0) for all 0x110000 code points: zero differences. `scripts/gen_unicode_tables.py --output <cwd>` run on `/usr/share/unicode` gives a byte-identical file. Every `str.isspace()` code point other than SPACE, LF and TAB is hidden. Noncharacters (U+FDD0, U+FFFE, U+10FFFF) are hidden through Cn.
- **Mark cap.** `too_many_marks` (`src/nl_shell/render.py:140`) and `escape` (`src/nl_shell/render.py:184`) count runs the same way. `e`+U+0301 U+0301 U+20DD (Me) is rejected. A backslash or any non-mark character resets the run in both.
- **Mixed script.** Non-ASCII separators do not split a word, so `ls ·с·url` (U+00B7) is still flagged. `curlеxample.com`, Cherokee `Ꮯurl` and Arabic-Indic digits next to Latin are all rejected.

## Findings

- NEEDS-HUMAN [human] — `src/nl_shell/render.py:94-110,161`: look-alikes from a single script, or from Common (characters shared by all scripts), still pass. `ⅽurl example.com` (U+217D SMALL ROMAN NUMERAL ONE HUNDRED, script Latin) and `𝐜url example.com` (U+1D41C, script Common) are accepted and shown raw. U+217D looks identical to `c`. That defeats the brief's main example (`сurl` ≠ `curl`) with a one-character swap. The brief cites UTS #39 §3.1 (General Security Profile) as normative, but the patch takes only the hidden-character idea from it. §3.1's Identifier_Status=Allowed would reject both of these (both are NFKC-unstable). The brief scopes "confusables / skeleton matching" out and sends this to #74's escaped confirm UI. That is defensible, but the human should confirm that #74 really covers non-ASCII Latin and Common letters, not just "hidden" ones.
- NEEDS-HUMAN [human] — `src/nl_shell/render.py:161-172`: words that mix Latin and Han are rejected, as the brief asks (single script after augmentation). Two ordinary filenames are refused: `cat iPhone用.txt` (word `iPhone用`) and `cat 2024年report.txt` (word `2024年report`). UTS #39's "Highly Restrictive" level allows Latin+Han+Hiragana+Katakana, Latin+Han+Bopomofo and Latin+Han+Hangul for exactly this reason. This follows the human's Plan decision, but the decision didn't weigh this case. Confirm at sign-off, or relax it to Highly Restrictive.
- NEEDS-HUMAN [impl] — `tests/test_charsafety.py:193-205`: test (5) only fakes `unicodedata.category` for U+0378 and U+1C89, which covers Cn and nothing else. Brief (5) says the policy must take "every property it uses (including Cn and the Mn/Me categories)" from the tables. On Python 3.14 the tables match `unicodedata` exactly (checked above). So if someone later rewrote `is_mark` as `unicodedata.category(c) in ("Mn", "Me")`, every test would still pass. Fix: in the same monkeypatch, map U+0301 to `"Lo"` and assert `echo é́́` is still rejected. Also fake one Default_Ignorable code point to a visible category and assert it is still rejected.
- Note (no action needed): some characters that render blank in some fonts but have no blank-related Unicode property are not caught: U+1D159 MUSICAL SYMBOL NULL NOTEHEAD (So) and U+FFFC (So) are accepted. The brief defines the set by properties plus U+2800 only, so this follows the brief. I list it so nobody reads "renders as nothing" in the invariant as a complete guarantee.
- Gate wording (not a defect): `gate-logs/T2-threat-model.log` says "no security-relevant path touched", yet the patch edits `.oss-scanner/threat_model.md:127-137` as Scope (6) asks. The gate is advisory and the threat-model edit is there, so this doesn't change the verdict. But T2's path list doesn't treat `src/nl_shell/render.py` / `proposal.py` as security-relevant, and that should be looked at separately.
