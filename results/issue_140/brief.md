# Brief — issue 140 / persistent-bash-session-core

- **Slug:** persistent-bash-session-core
- **Kind:** enhancement
- **Defect / goal:** nl-shell has no shell session. Add a session object (`src/nl_shell/session.py`, record parsing in `src/nl_shell/pty_protocol.py`) that starts one long-lived interactive bash (≥ 5.1) on a PTY via `ptyprocess` (ADR-0021 §2), with nl-shell's control channel on fd 3 and a generated rcfile (spec `pty-protocol/v1` §1). It parses the `S`, `D`, `F`, `L`, `T`, `B`, `X`, `P`, `J`, `H`, `V`, `E` records (§2–§3) and ignores unknown types. It records the first snapshot as the baseline, checks sequencing, and on every degrade trigger enters degraded mode with a human-readable reason. Degraded mode is sticky until restart; while degraded the session sends NOTHING more to the PTY (it raises; the REPL, #78, offers the restart). It sends exactly the confirmed bytes as one bracketed paste plus `CR`, and refuses, without writing, a command containing `ESC`, any other C0 control except TAB/LF, or `ESC [201~` (§5). Interrupt writes `\x03`; restart starts a fresh session with a fresh baseline. A result carries the sequence number, `$?`, `PIPESTATUS`, the PTY output between `S` and `D` (bounded, with a truncated flag) and the snapshot. Status and completion come only from fd-3 records, never from printed text. `cd` and `export` persist. No terminal ownership (#102). Nothing calls the session yet (#78 wires it).
  **What this child CLAIMS — a closed list. Nothing else is claimed.** (I2) A command that ran is never reported as "nothing ran" while the session stays healthy, **for these cases only**: (I2-a) ordinary commands — everything in criteria (a)–(e), (k), (l), (q); (I2-b) a confirmed command that changes any item `H` covers — `PS0`, every `PROMPT_COMMAND` element, the saved user hook, the text of nl-shell's hook functions, every `__nls_*` hook state variable (value AND attributes, so `readonly` too), and `TERM` — degrades at THAT command's own snapshot; (I2-c) the (g) reproducers (`PS1` side effects, `readonly`, a top-level `trap … DEBUG` assigning hook state); (I2-d) user aliases cannot change what the hooks run (every command word inside `PS0`, `PROMPT_COMMAND`, `__nls_done` and the `$( … )` bodies of `__nls_snap` is `\builtin`-quoted / runs with `expand_aliases` off). (I3) Of `PROMPT_COMMAND`, `PS0`, `PS1` and `PS2` — and only these — nothing confirmed code sets runs after the snapshot: nl-shell's hook is the LAST `PROMPT_COMMAND` element, every user element runs BEFORE the snapshot, and nl-shell sets fixed `PS1`/`PS2` after it (a confirmed change to `PS0` or `PROMPT_COMMAND` degrades by I2-b; a confirmed change to `PS1`/`PS2` is overwritten by nl-shell after the snapshot, which is why `PS1='x$ '` stays healthy in (f)). Other routes that can run code after the snapshot — readline `bind -x` on the `CR`, a top-level `trap … DEBUG` firing around `PROMPT_COMMAND` elements, `PS4`/xtrace — are NOT claimed (#141 / #145). **Anything not in this list is NOT claimed by this child** — tamper resistance in general (I1) is #141, and the systematic review of what else can evade the hooks is #145. Do not add detection for unlisted cases, and do not write docs that claim more than this list.
