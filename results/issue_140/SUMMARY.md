# Security review (advisory) — issue 140 / persistent-bash-session-core

Attacker-reachable inputs this diff touches: the confirmed command text (threat model "Where untrusted input enters" item 5, model output), PTY output of what the command runs (item 1), and session state a confirmed command can change (item 4). Nothing calls the session yet (#78), so none of these is reachable in a shipped path today.

**Verdict: no finding.** What I checked:

- **Bytes sent = bytes confirmed** (Critical if broken). `check_command` (`src/nl_shell/pty_protocol.py:139-148`) refuses `ESC [201~`, ESC and every C0 byte except TAB/LF before any write; `run()` calls it first (`src/nl_shell/session.py:501`) and writes one paste plus `CR` (`session.py:515`). The test covers the hostile cases, not only the friendly path: paste-end, ESC, CR, BEL, NUL, SOH, US, ETX, each asserting nothing reached the PTY and no file was touched (`tests/test_session.py:290-310`). I also ran bytes the filter lets through on the real session (bash 5.3.9): `DEL` (0x7f), C1 CSI (U+009B → `c2 9b`) and TAB all reached bash unchanged (`printf %s 'a\x7fb' | od` → `61 7f 62`, and so on). Refusing DEL, C1 and bidi characters belongs to the confirm UI (#74), not this patch.
- **Output can't forge status or completion** (High). Status, `ran` and sequencing come only from fd-3 records (`pty_protocol.py:214-303`). Printed text never reaches the tracker. The test vectors `printf 'D 99 0 0\n'` and OSC 133 are covered. Records with `\r`, bad escapes, over-long numbers or a length over 1 MiB degrade the session instead of crashing it (`pty_protocol.py:25-29, 104-123, 195-196, 210-211`). Command writes to fd 3 are settled as out of scope (#135, brief decision 1), and the threat model already lists inherited fd 3 as a known gap.
- **Output boundary.** The end marker is a 128-bit random token per start (`session.py:410-413`). A text-only attacker who controls file contents or command output can't guess it, so they can't cut the captured output short. The token can be seen from inside the shell (`declare -f __nls_done`, and the `H` record), but only by code the user confirmed, which could already do anything. Captured output is capped and keeps the tail (`session.py:317-322`). Each control record is capped at 1 MiB (`pty_protocol.py:19, 195`). So memory stays in proportion to the input.
- **Hook changes degrade the session** (Medium if missed). `H` is compared exactly against the baseline, with only the sequence counter changed (`pty_protocol.py:131-136, 294-300`). While degraded, `run()` raises before writing (`session.py:504-513`), and the tests show nothing gets written (`tests/test_session.py:517-572`). The previous round's wording defect is fixed: spec §1.3 (`docs/design/specs/pty-protocol/v1.md:157-165`) and the threat-model bullet (`.oss-scanner/threat_model.md:181-188`) now say that a readonly `PS1`/`PS2` or a `PS0`/`PROMPT_COMMAND` change degrades the session but may run once after the snapshot. Only plain or exported `PS1`/`PS2` values are claimed to be overwritten, which matches `session.py:138-143`.
- **Unlisted ways around the hooks** (top-level `trap … DEBUG` running code after the snapshot, which `T` reports but nothing compares; `bind -x`; `read -u 2`). The brief's R1 excludes these and leaves them to #141/#145/#136. The threat model's new Known-gaps bullet names them and says #78 must not wire the session before #141 lands. Not re-raised.
- **Temporary rcfile.** It is written inside `tempfile.mkdtemp` (mode 0700) and removed once bash has loaded it (`session.py:408-413, 450`), so another local user can't swap it out.
- **Prompt rule.** It fails closed: if `/proc/<pid>/syscall` or `fd/0` can't be read, the session degrades (`session.py:636-691`). That is not reachable from untrusted text.

C4 gate log (`gate-logs/C4-verify.log`): 93 of 93 tests red without the fix, green with it.
