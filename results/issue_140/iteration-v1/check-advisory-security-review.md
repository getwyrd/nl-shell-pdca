# Security review (advisory): persistent-bash-session-core (#140)

**Attacker-reachable inputs this diff touches:** session state (threat model input 4: functions, aliases and hooks set by `~/.bashrc` or a confirmed `source` of a cloned repo's script), command output on the PTY (input 1), and the command bytes sent to bash (the confirmed command, input 5 once #78 wires the REPL in).

The patch did not apply to the target checkout (C4 `worktree-mismatch`; `$PDCA_TARGET` is at `2ddc3e8` and has no `session.py`). So the `path:line` refs below are line numbers in the new files the patch creates. I pulled `pty_protocol.py` and `session.py` out of `patch.diff` into the scratch dir and ran them against the host's bash 5.3.9 with `ptyprocess`.

## Findings

- NEEDS-HUMAN [human] — **High** (scale: "a session change (alias, function, hook) goes undetected by the gate"; it also breaks the brief's invariant I2). Locations: `src/nl_shell/session.py:106` (the rcfile comment says the hooks are safe because every call goes through `builtin`), `:126` (`PS0` uses `builtin printf` to write `S`), `:140`, `:175-176`, and the same claim in the spec §1.3 text (`patch.diff:194`). **Input:** a shell function named `builtin` (or `command`). Bash lets a function shadow both names. Anyone who controls a script the user confirms with `source`, or the user's `~/.bashrc`, can define one. Once it exists, every `builtin …` call in `PS0`, `__nls_done` and `__nls_snap` runs the attacker's function instead. The function can then fake any record: H, F, L, T, P, V, even `S`. No external program is needed, so the `hash -p` / `BASH_CMDS` / `PATH` tests in (l) never see it. **What goes wrong**, reproduced against the patch's own `Session`:
  1. Run `builtin() { if [ "$1" = compgen ]; then __o=$(command builtin "$@"); __o=${__o/builtin$'\n'/}; command builtin printf '%s\n' "$__o"; elif [ "$1" = alias ]; then :; else command builtin "$@"; fi; }; alias ls='echo PWNED'`. Then `run("ls")` returns `PWNED`. The session stays HEALTHY, the snapshot's F and L equal the baseline's exactly, and H still matches. A future gate checking F/L would see no change.
  2. Run `builtin() { if [ "$1" = printf ] && [ "$2" = 'S %s\n' ]; then :; else command builtin "$@"; fi; }`, then `run("touch MARK; echo printed; (exit 7)")`. The result is `ran=False`, `status=7`, `output=b''`, the session is not degraded, and `MARK` was created. That is exactly what I2 forbids ("a command that ran is never reported as nothing ran while the session stays healthy"), and the (g) tests don't cover it.

  The new Known-gaps bullet (threat_model.md, interim until #141) lists traps, extdebug, xtrace, disabled builtins, readline state, `set -H` and Table B. It does not list shadowing `builtin`/`command` with a function. So this is not covered by the documented deferral, and the bullet plus the rcfile/spec text overstate what the hook row protects. Practical reach is low today, because nothing calls the session until #78. **Why [human]:** bash has no call path a function can't shadow, apart from keywords. Special builtins win over functions only in POSIX mode, and entering POSIX mode needs `set`, which can itself be shadowed. So the fix is a design choice. Options: detect it from outside bash, change how hooks reach builtins, or name it in the interim Known-gaps bullet and move it to #141's Table A along with a test. Whichever is chosen, add the two inputs above as tests in `tests/test_session.py`. Today they pass silently.

## Checked, no finding

- **Command refusal** (`src/nl_shell/pty_protocol.py:159-173`): refuses `ESC [201~`, `ESC` and every C0 byte except TAB/LF before anything is written. `run()` calls it first (`session.py`, `run`). C0 bytes that would raise a signal through the PTY's line discipline (`^C`, `^\`, `^Z`) and flow control (`^S`/`^Q`) are therefore all refused. DEL and C1/bidi characters pass through. That matches the brief (§5), and bidi rejection belongs to the confirm UI (#74). A `str` with lone surrogates raises `UnicodeEncodeError` before any write.
- **Forging completion or status from output**: status, `PIPESTATUS`, start and done come only from fd-3 records (`ProtocolTracker`). Printed `D 99 0 0` and OSC 133 text don't reach the tracker. fd-3 writes by child processes are the known gap / #135.
- **Output delimiting**: the end marker carries a 128-bit token chosen per start (`session.py:202`, `secrets.token_hex(16)`), so file contents or command output can't cut a command's output short without first reading the token from inside the shell. That would be confirmed-code tampering, the same deferred class. Even then it only shortens captured output, never status.
- **Resource limits**: one control record is capped at 1 MiB (`pty_protocol.py:30`), with numeric fields at 18 digits so an oversized `int()` can't raise. Captured output is capped at 1 MiB with a truncated flag (`session.py:213`). A malformed record degrades the session instead of raising or hanging.
- **rcfile handling**: written into a fresh `mkdtemp` directory (`0700`) and removed once the baseline arrives (`session.py:433`, `:474`).
- **Degraded mode**: `run()` raises before writing, and `interrupt()` writes nothing unless the tracker is RUNNING.
- **Secrets**: no sudo or password path is touched. `on_record` only sees control records.
