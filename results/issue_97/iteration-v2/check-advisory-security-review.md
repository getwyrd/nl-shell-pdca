# Security review — docs-checks-adr-immutability

**Attacker-reachable inputs touched (per `.oss-scanner/threat_model.md`): none.** The patch adds a CI-only docs check (`scripts/docs_checks.py`, `.github/workflows/docs-checks.yml`), two index sentences and tests. None of it is on the runtime path the threat model covers (command output, file names in the shell, env, session state, model output, reader output, model socket, install artifacts, training data). So nothing here can break a "What must hold" property, and the findings below are **unrated**: the threat model's severity scale does not cover CI integrity.

Outside the threat model, the input that matters is **the PR itself**: its file contents, file names and the files it adds to the checkout. I checked that input against the goal from the iteration-1 sign-off ("a PR cannot switch off its own check").

- NEEDS-HUMAN [impl] — `.github/workflows/docs-checks.yml:36` (and `:39`). The base copy runs as `git show "$BASE:scripts/docs_checks.py" | python - …` from the PR's checkout. With `-`, Python puts the current directory first on `sys.path`, so a PR that adds a top-level `dataclasses.py` (or `__future__.py`, `re.py`, `subprocess.py`) runs its own code in place of the stdlib module. That code can `sys.exit(0)` before any check runs, which defeats the base-copy defence the sign-off asked for. Reproduced locally with Python 3.14.4: in a repo holding `dataclasses.py` = `print("HIJACKED"); raise SystemExit(0)`, running `python3 - immutability HEAD HEAD < docs_checks.py` printed `HIJACKED dataclasses` and exited 0. With `python3 -I -` (isolated mode: no cwd on `sys.path`, `PYTHON*` env vars ignored) it printed `docs-immutability: OK` as expected. Fix: use `python -I -` on line 36. On the fallback at line 39, `python -I scripts/docs_checks.py` also keeps `scripts/` off `sys.path`, though that branch runs PR code anyway. Neither pytest nor C4 covers the workflow, so check it by reading the diff or with a throwaway commit on the draft PR.
- NEEDS-HUMAN [human] — `.github/workflows/docs-checks.yml:1-40`. On `pull_request`, GitHub runs the workflow file from the PR's own merge commit. A PR can edit `docs-checks.yml` itself to skip the step, so running the base copy of the script only blocks the quiet bypass, not a deliberate one. A deliberate bypass shows in the diff as a change under `.github/`. Fully closing it needs repo settings rather than code: a required check, plus CODEOWNERS or review rules on `.github/workflows/` and `scripts/docs_checks.py`. The brief puts the required-check setting out of scope, so this is the maintainer's call.

Checked, no finding:
- **Trigger and token:** `pull_request` only (not `pull_request_target`) with `permissions: contents: read`. Fork PR code gets a read-only token and no secrets.
- **Git argument injection:** `BASE`/`HEAD` come from event SHAs, not PR-written strings, and are passed through `env:`, not pasted into the script text. Paths only ever appear after `rev:` in `git cat-file` (`scripts/docs_checks.py`, `git_blob`), so a file name starting with `-` cannot become an option. Diff output is parsed with `-z`, so names containing newlines or tabs split correctly.
- **Log injection:** a renamed frozen record's new name (PR-controlled, may contain a newline) is printed in the violation message. That message only appears when the job already fails (exit 1), so at most it adds fake annotations. It cannot turn a failure into a pass, and `set-env`/`add-path` commands are disabled on runners.
- **Parsing:** non-UTF-8 bytes use `errors="replace"`. A leading BOM is stripped only for parsing, and the byte-exact comparison still sees it (sign-off item 2). No regex in the script is open to catastrophic backtracking from file content.
- **Gates:** C4 passed (red 69/69 without the fix, green with it). T2 reports no security-relevant path touched, which matches the reading above.
