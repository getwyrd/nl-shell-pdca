# Adversarial review: docs-checks-adr-immutability (iteration 2)

Verdict: **refuted on the iteration-1 carry-forward item 1** ("a PR cannot disable its own check"). The core freeze logic held up against every attack I tried.

- NEEDS-HUMAN [impl] — `.github/workflows/docs-checks.yml:36`: running the base copy as `git show "$BASE:scripts/docs_checks.py" | python - immutability …` does not stop a PR from switching off its own check. With `python -`, `sys.path[0]` is the current directory, which is the PR's checkout. The script imports `__future__`, `re`, `subprocess` and `dataclasses` (`scripts/docs_checks.py:22-29`), and Python has not loaded any of them yet at startup. So a PR that adds, for example, `re.py` at the repo root (`import sys; print("docs-immutability: OK"); sys.exit(0)`) takes over the base script. **Concrete failing case, reproduced:** I built a repo whose base has the real script and an Accepted ADR. The head edits the ADR body and adds `re.py`, `subprocess.py`, `dataclasses.py` or `__future__.py`. I ran the workflow's `run:` block word for word. The step prints "Running scripts/docs_checks.py from the base commit …", then "docs-immutability: OK", and exits 0 for all four names. With a harmless file name instead, it exits 1 as it should. **Fix, verified:** `python -I - immutability "$BASE" "$HEAD"` (`-I` is isolated mode: the current directory is left off `sys.path` and `PYTHON*` env vars are ignored). With that change the `re.py` case exits 1 and names the path. Also add a test next to `test_ci_step_runs_the_base_copy_so_a_pr_cannot_disable_the_check` where the head plants `re.py` at the root. The current test only replaces `scripts/docs_checks.py`, so it passes for a narrower reason than its name says. Using `-I` on the fallback line `:39` costs nothing, but it matters less there because that branch already runs PR code.
- NEEDS-HUMAN [human] — `.github/workflows/docs-checks.yml:8-9`: on `pull_request`, GitHub runs the workflow file **as the PR has it**. So a PR can still edit `docs-checks.yml` itself, for example change `:36` back to the head copy or delete the step, and the `docs` job still reports green. Nothing in the patch freezes the workflow file, and the brief keeps "required check" out of scope. Item 1 therefore narrows the bypass but does not close it. Real protection needs a human decision: CODEOWNERS review on `.github/workflows/` and `scripts/docs_checks.py`, branch protection, or a ruleset. The reviewer should not treat "a PR cannot disable its own check" as fully met.
- Evidence (could not refute): `gate-logs/C4-verify.log` shows 69 of 69 tests failed with the script removed and all passed with it, and none were collection errors. The tests call the real script through `subprocess` (`SCRIPT = REPO_ROOT/"scripts"/"docs_checks.py"`). The CI-step tests pull the real `run:` block out of the workflow file instead of copying it into the test, so they check what production runs. Every must-fail case asserts exit 1 and that the path shows up in stdout. The must-pass cases also go red on the red leg, but only because the script is missing, which is the expected red. I could not re-run pytest here because pytest is not installed in this sandbox. My probes used the patched script directly.
- Freeze logic (`scripts/docs_checks.py:206-245`, `:262-287`), tried and could not break: a rename of a frozen file whose content changes under the rename threshold (shows up as a delete, which fails); renaming a frozen file X away while renaming another file onto X (`head_path != frozen_path`, which fails); a status-line change plus an extra frontmatter line (`differing == [idx]` fails); a CRLF or BOM change on the status line; Accepted → Superseded on the PR while main already superseded it differently (base tip still frozen, fails); a symlink type change (`T`, blob differs, fails). The allowed suffix after `Superseded by ADR-NNNN` lets someone put free text in the status line, but the brief accepts that on purpose, so I am not counting it.
