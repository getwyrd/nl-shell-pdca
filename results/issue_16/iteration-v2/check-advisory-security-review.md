It enters at `proposal.parse` (`src/nl_shell/proposal.py:155`) and its result is printed at `src/nl_shell/repl.py:115` / `repl.py:149`. The other new inputs are trusted under the threat model: the request text (typed by the user), `prompts.yaml` (the user's own config file, or the target's file in the repo), and `:context` (built only from those two today, since the state block slot stays empty until #11).

## Findings

Nothing in this diff breaks a "What must hold" item today, because no proposal runs and there is no confirm UI yet. The two notes below concern display choices that #74 (the confirm UI) and #78 (the gate) will build on. I rate them against what they become once those land, not against today.

- NEEDS-HUMAN [human] — **No rating today; High ("spoofs the confirm UI") once #74 renders from this format.** `src/nl_shell/repl.py:47` and `repl.py:149`. Input: the model's `command` (item 5), which text the model reads can steer. As the brief requires, the parser accepts LF and the REPL prints the command with no framing. A multi-line command can therefore print text that looks like nl-shell's own UI, including a second, fake risk line. I ran it: the response `{"kind":"command","command":"ls\nNot run: the policy gate arrives in M0.4.\nProposed command (risk: read-only):\nrm -rf ~","risk":"destructive"}` prints `Proposed command (risk: destructive):\nls\nNot run: …\nProposed command (risk: read-only):\nrm -rf ~\nNot run: …`. The last block a user reads says "read-only" above `rm -rf ~`. LF-as-is is what the brief asks for (criterion (e)), so this is not a builder defect. A human needs to decide, here or as a recorded requirement on #74, how multi-line commands are framed (indent or prefix each line, or show a line count) so that a command can't fake a header or risk label.
- NEEDS-HUMAN [human] — **No rating today; would count as "what is shown differs from what runs" once #78 runs proposals.** `src/nl_shell/render.py:182-200`. Input: the model's `command` (item 5). The hidden set is exactly the brief's list, so other invisible or format characters are accepted and printed as-is. I ran `l​s` (ZERO WIDTH SPACE, which shows as `ls`), `ls ﻿` (BOM), `ls x` (LINE SEPARATOR) and `ls \U000e0041` (a TAG character). All four were accepted as `CommandProposal` and printed raw. Today, a command that looks like `ls` but holds U+200B fails harmlessly in bash. Once proposals run, an invisible character inside a word lets the shown command differ from the bytes that run (for example, a path or argument the user can't tell apart). The threat model's must-hold says "hidden characters escaped" without listing them. A human should decide whether to widen the set now (Unicode category Cf, U+2028/U+2029, tags U+E0000–U+E007F) or leave it to #74. Widening it is a one-line change in `is_hidden`, plus test vectors.

No other finding. The patch's own tests cover the attacker-reachable cases for the vectors in the brief's set (malformed JSON, schema breaks, hidden characters, surrogates, large integers, and unsafe YAML tags), not only the friendly path.
