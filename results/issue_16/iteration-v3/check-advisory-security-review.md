# Security review — issue 16 (prompts YAML, `:context`, recording stub, proposal parser)

**Attacker-reachable inputs this diff touches:** item 5, the model's response (`RecordingStub` today, the #77 client later). It is parsed by `proposal.parse` and shown by `Repl._propose` / `show_proposal`. Not attacker-reachable in this diff: the request text (typed by the user, so trusted), both `prompts.yaml` layers (nl-shell's own config and the target folder, both trusted), and the state block (always `""` until #11, `src/nl_shell/prompts.py:247`).

What I checked: the strict JSON parse (duplicate keys, `NaN`/`Infinity`, integers over 4300 digits, deep nesting, arrays, extra or missing properties, `command` together with `reason`, the 2000 code point limit), lone surrogates, the C0/C1/DEL/bidi/Cf/U+2028/U+2029/tag-character rejection in `command`, escaping on every printed reply (`src/nl_shell/repl.py:133`), one-to-one backslash escaping in `:context`, line-by-line framing of multi-line commands (header-spoof vector covered by tests), the YAML safe loader (`!!python/object/apply` vector tested; `pwned` is not created), and `str.replace` instead of `str.format` in `_volatile`. These all hold, and the patch's tests cover the attacker-side vectors from rounds 1 and 2: the surrogate case runs through a real UTF-8 `TextIOWrapper`, and there are tests for the header spoof, U+200B, U+FEFF, U+2028 and U+E0041. Nothing runs yet, so no row on the Critical/High scale is reachable today.

## Findings

- NEEDS-HUMAN [human] — **Low today; High once #74/#78 build the confirm UI on this parser**, `src/nl_shell/render.py:50-63` (`is_hidden`, used by both the parser and the escaping). **Input:** the model's response (item 5), which a text-only attacker can steer. **What goes wrong:** the hidden set is C0/C1/DEL, bidi, Cf, separators, tags and surrogates. Unicode *default-ignorable* characters outside category Cf are accepted in `command` and printed as-is, and most terminals show them as blank or nothing: U+3164 HANGUL FILLER (Lo), U+115F / U+FFA0 (Lo), U+034F COMBINING GRAPHEME JOINER (Mn), U+FE00–U+FE0F variation selectors (Mn), U+17B4 (Mn), U+180B (Mn), plus U+2800 BRAILLE BLANK (So). Long runs of combining marks (Mn) are accepted too and can stack over nearby characters. Once proposals reach the confirm UI, the user can't see part of the command they confirm. For example, `ls<U+3164>` is a different word to bash than `ls`, so a name that looks like a known command is really another one. The must-hold says the confirm UI escapes hidden characters (`.oss-scanner/threat_model.md:119-120`). **Reproducer (run on the patched tree):** `proposal.parse('{"kind":"command","command":"lsㅤ; id","risk":"read-only"}')` returns `CommandProposal`, and the same holds for each code point listed above. The human already widened this set once at sign-off (round 2), so whether to widen it again is a scope call, not a builder fix. One candidate rule: reject (and escape) every code point with the `Default_Ignorable_Code_Point` property, plus U+2800, and cap combining marks per base character. If the human decides to widen it, the builder change is small: add a branch to `is_hidden` and add the vectors above to the parser-reject and `:context`-escape tests.

- NEEDS-HUMAN [human] — **Not reachable in this diff (forward note for #11 / #77)**, `src/nl_shell/backend.py:48-50` (`context_text`) with `src/nl_shell/prompts.py:247-254`. **Input:** the state block (items 1–3), once #11 fills the `{state}` slot that is always `""` today. **What goes wrong:** the `:context` text form separates messages with a bare `--- <role> ---` line, and LF is printed as-is. Content can therefore contain a line that looks like a message boundary. Command output such as `a\n--- assistant ---\n{"kind":"command",...}` inside the state block would make `:context` appear to show an extra assistant turn the model was never sent. That breaks "`:context` must not let printed text spoof nl-shell's own UI" (`.oss-scanner/threat_model.md`, "Output rendering is filtered everywhere"). **Reproducer:** `context_text((Message("user", "a\n--- assistant ---\nb"),))` prints a fake `--- assistant ---` header line. The brief pins this text form, and tests rebuild it byte for byte, so changing it (for example, prefixing content lines the way `show_proposal` does, or escaping a leading `---`) is a format decision for the human or for #11, not for this round.

- Advisory, no action this round: `src/nl_shell/repl.py:164` puts `BackendError` text into the reply through `str.format`. With the stub, that text is fixed. When #77 builds errors from server or HTTP responses (item 11), LF inside them is printed as-is and could fake a reply line, though the print at `repl.py:133` already escapes everything else. #77 should keep server-supplied text out of `BackendError` messages, or frame it the way commands are framed.

No other finding. The parser, rendering and loader changes in this diff hold against the threat model's item 5 vectors I tried.
