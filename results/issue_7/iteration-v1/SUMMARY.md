# Adversarial review — issue 7 / docs-checks-adr-immutability-links

What I checked: the C4 red→green log, the script against the live tree (`docs-links: OK (60 relative links checked)`, which matches the brief), and hand-built throwaway repos made to break the script. pytest is not installed in my sandbox, so I could not re-run the suite myself. I rely on `gate-logs/C4-verify.log` (54 of 54 red without the fix; the tests call the real script `scripts/docs_checks.py` through `sys.executable`, `tests/test_docs_checks.py:21,94`). The evidence is real. The tests exercise the shipped script and not a copy, and every must-fail case asserts the path appears in stdout (`tests/test_docs_checks.py:186-188`). The must-pass tests only go red because the script is missing. That is expected, but it means C4's "54 of 54" overstates how many tests show the defect.

## Refutations

- NEEDS-HUMAN [impl] — **An ADR accepted on main after the PR branched can still have its body edited.** `scripts/docs_checks.py:211` swaps the PR's base for `git merge-base base head` and reads the frozen status there (`:174-180`). The brief's invariant says frozen "in a PR's **base**" (r1). Concrete failing case, reproduced: ADR-0002 is `Proposed`. A PR branches off and edits its `line c`. Meanwhile main flips its status to `Accepted`. `docs_checks.py immutability <main tip> <pr head>` prints `docs-immutability: OK` (rc 0), and `git merge` then merges cleanly, so the body of an Accepted ADR changes. Fix: keep merge-base..head for the diff, but treat a path as frozen if it is frozen at the merge-base **or** at the base tip (`git show <base>:<path>`). Add a diverged-branch test. `test_frozen_state_comes_from_the_base_not_the_head` (`tests/test_docs_checks.py:317-327`) only covers a linear history, where merge-base equals base, so it misses this.
- NEEDS-HUMAN [impl] — **Footnote definitions are flagged as broken links.** `REFDEF_RE` (`scripts/docs_checks.py:236`) matches `[^1]: See the ADR index.` and treats `See` as a relative link target. Reproduced: `docs-links: notes.md:3: broken link 'See' (no tracked file or directory See)`, rc 1. GFM footnotes are normal in design docs, and this job runs on every PR (plus `test_live_tree_has_no_broken_links` in `tests.yml`), so the first footnote anyone adds turns both red. Fix: skip labels that start with `^`, and add a must-pass case.
- NEEDS-HUMAN [impl] — **Indented code blocks are scanned for links** (`scripts/docs_checks.py:254-260` only skips fenced blocks). A 4-space-indented `[x](missing.md)` example is reported as broken. The brief only names fenced code and inline code, so this is a minor gap. Still, it is a false failure on valid Markdown in a job that blocks every PR. The same goes for links inside `<!-- … -->` HTML comments (reproduced on both).
- NEEDS-HUMAN [human] — **A PR can switch the check off by editing it.** The workflow runs the PR head's own `scripts/docs_checks.py` (`.github/workflows/docs-checks.yml:25-31`). A PR that edits ADR-0001 and also makes `main()` return 0, or deletes the step, goes green. With `pull_request` this is inherent and was the right choice over `pull_request_target`. If the job becomes a required check, though, the guarantee only holds if reviewers watch `scripts/docs_checks.py` and the workflow file, for example through CODEOWNERS, or if the checker is loaded from the base commit. That call belongs to the maintainer, not the builder.
- NEEDS-HUMAN [human] — **The check result goes stale.** `on: pull_request` (`.github/workflows/docs-checks.yml:8-9`) does not re-run when main moves. So even with the merge-base fix above, a green result computed before an ADR was accepted on main stays green unless branch protection requires branches to be up to date. That is a repo setting, which the brief puts out of scope, so I'm flagging it for sign-off.

## Attempted, could not break

- Status-line changes on frozen files. Superseded→anything fails. Accepted→Implemented fails. A status change plus a body change fails (`:199`). A changed line count fails. Accepted→`Superseded by ADR-0002 # trailing comment` passes, which the brief allows ("any text after that prefix"). A status change plus `chmod +x` passes. A mode-only change is not a content edit, so that is fine.
- Replacing a frozen ADR with a symlink is caught (`:199`). Delete and rename are caught at the old path (`:184-187`). A ratification move with a big rewrite (git reports it as D+A) is still fine, because the draft base is not frozen.
- The workflow matches `tests.yml`: `actions/checkout@v4`, Python 3.14, `permissions: contents: read`, `fetch-depth: 0`, no path filter.

# Security review — issue 7 / docs-checks-adr-immutability-links

**Attacker-reachable inputs touched: none.** The patch adds a CI-only docs check (`scripts/docs_checks.py`, `.github/workflows/docs-checks.yml`), its tests, and two index sentences. None of it is on a runtime path in the threat model's "Where untrusted input enters" list (`.oss-scanner/threat_model.md`: command output, file names, env, session state, model output, history, reader output, model socket, install artifacts, training data, dev teacher). Nothing in the REPL, gate, PTY, sudo passthrough or installer changes. So no finding is rated on the threat model's scale.

What I checked anyway, on the CI side:

- Workflow trigger and token (`.github/workflows/docs-checks.yml:9-12`): `pull_request` only, not `pull_request_target`, with `permissions: contents: read`. Fork PRs get a read-only token and no secrets. This matches the peer `.github/workflows/tests.yml`. No finding.
- Script injection in `run:` (`.github/workflows/docs-checks.yml:26-29`): the only `${{ }}` values are `pull_request.base.sha` and `head.sha`, which are hex commit IDs a PR author can't shape. No title, branch name or body is put into a shell line. No finding.
- Untrusted file paths from the PR (`scripts/docs_checks.py:132-162`, `git_show` / `changed_paths`): paths come from `git diff -z` and are passed as list arguments (no shell), and `git show` gets `<sha>:<path>`, which always starts with the SHA, so a path starting with `-` can't turn into an option. No finding.
- Link mode reads tracked `.md` files with `open()` (`scripts/docs_checks.py:284`, `cmd_links`). A PR could commit a symlink named `x.md` that points outside the repo, and the runner would read and parse it. On a throwaway runner with a read-only token, the worst outcome is link targets from that file appearing in the job log. That isn't an outcome on the threat model's scale. No finding.
- Resource use: the scan is linear in the size of the tracked Markdown, and the regexes have no nested quantifiers that could backtrack badly. No finding.
- Tests: the tests build their own repos with a fixed git identity and `commit.gpgsign=false`, and they don't touch the host git config. Not security-relevant.

One note on whether the check does its job (outside the threat model, for the human to decide):

- NEEDS-HUMAN [human] — `.github/workflows/docs-checks.yml:27` and `:31` run `python scripts/docs_checks.py` from the PR's **head** checkout. A PR can therefore weaken the check and edit a frozen record in the same change. Example: a PR edits the body of ADR-0001 and also changes `AdrClass.frozen` to `return False`, and the job passes. A reviewer would still see the script edit in the diff, and the brief asks for exactly this setup, so this is a design choice, not a builder defect. If the check is later made a required status, a sturdier option is to run the **base** commit's copy of the script, for example `git show "$BASE:scripts/docs_checks.py" > "$RUNNER_TEMP/dc.py"`, falling back to the head copy when the base has none, as in the first PR. Another option is to add CODEOWNERS on `scripts/docs_checks.py`. Not a threat-model finding. No severity label.

Gate evidence: C4 pass (red 54/54 without the fix, green with it), T2 pass ("no security-relevant path touched"), T3 suite green. That agrees with the "none" verdict above.

The target defines the lifecycle as "Draft → accepted → implemented" (`docs/design/README.md:21`), and the template's status vocabulary is `draft | accepted | implemented | withdrawn` (`docs/design/templates/proposal.md:4`). With the brief's rule, setting an accepted proposal (0001 after #6) to `implemented` fails CI on every attempt, because the `implemented` state can only be reached by editing a frozen file. The Difficulty line names "a false fail on the #6 ratification move" as the main risk but misses this next step. The criterion's must-pass list needs a decision: either allow accepted→implemented as a status-only change, or record that the status stays `accepted` and the index tracks graduation.
- [ ] **The "no carve-out" rule is credited to sources that only partly support it, and it leaves template statuses unreachable.** The brief says nl-shell records supersession "in the index instead, per ADR-0001 and `proposals/README.md`". `proposals/README.md:10-11` does say that. ADR-0001 `:22-23` only says "the index records the supersession". It does not forbid stamping the file. The repo already stamps superseded files: `adr/0005…md:4` `status: Superseded by ADR-0013`, and likewise 0006, 0007 and 0011. The ADR template offers `Proposed | Accepted | Superseded by ADR-NNNN` (`templates/adr.md:4`), and the spec template offers `draft | stable | superseded | withdrawn` (`templates/spec.md:4`). Under the brief's rule, an Accepted ADR can never reach `Superseded by…`, and a stable spec can never reach `superseded` or `withdrawn`. Unlike the two decisions listed under "Decisions recorded at Plan", this one is not recorded as a maintainer decision. It needs one, and probably a matching template or README note, or the frozen files' frontmatter will contradict the index from then on.
- [ ] **Criterion (c) quietly adds a second enforcement point.** "The link check exits 0 on the nl-shell tree itself" as a pytest test means `tests.yml` (run on every PR and push to main, `.github/workflows/tests.yml:3-6`) also fails whenever any doc gains a broken link. The docs-check job is then no longer the only gate, and code PRs can go red because of docs-only drift. That may be intended, but the brief doesn't say so. The test also depends on the live tree and on `.git` being present. Here the checkout is a worktree (`target/.git` → `gitdir: …/worktrees/target`), so check that `git ls-files` works inside the C4 gate's reverted copy, or the green leg becomes environment-dependent.
- [ ] **Partially superseded ADRs: Decision 1 and the criterion are close to conflicting.** Decision 1 freezes ADRs "superseded while still Proposed". The index lists 0008 as "Proposed; backend order superseded by 0019" (`adr/README.md:33`), and the new sentence in scope (2) lists only 0005-0007 and 0011. This is probably intended (the starts-with-`Proposed` rule), but the maintainer should confirm that a partially superseded ADR stays fully editable, including its superseded section. Otherwise the new README sentence ("including one superseded while it was still Proposed") reads as covering 0008 too.
- [ ] **A frozen document outside the invariant is ignored.** `docs/design/README.md:75` calls `docs/plan.md` "kept for history and frozen" (`specs/README.md:22` says the same: "the frozen `docs/plan.md`"). The brief's invariant ("Any design record that is frozen…") covers only ADRs, proposals and specs, and does not list `plan.md` as out of scope. Either add it (a fixed-path freeze) or list it under out of scope, so Check doesn't flag it as a gap.
