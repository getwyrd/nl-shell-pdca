# Result — issue 62 / failure-classes-by-exit-code

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: A deterministic first pass that classifies a finished command's failure from trusted facts only — the exit status from the PTY session's done record and the command the user confirmed — into: not found (127), not executable (126), interrupted (130), killed by signal n (128+n), privilege-wrapper failure (sudo, su, pkexec, doas), and other. Each class carries its fixed response: what to tell the user, whether a correction may be offered, and whether the case goes to the quarantined reader. For "not found" it suggests the package that provides the command from local package data named by the active target.
- Success criterion: `python3 -m pytest tests/test_failure_classes.py` passes, with a table-driven test that covers each class: exit 0 → no failure · 127 for `htop` with a fake provider lookup that knows `htop` → not-found, suggests package `htop`, no reader · 127 for a command the lookup doesn't know → not-found without a suggestion, no reader · 127 for `cat f | htop`, `make && htop`, `true; htop`, `FOO=1 htop` and `env htop` (fake lookup knows `htop`, `cat`, `make`, `env`) → not-found with NO suggestion (the not-found word can't be told from the first token, see Scope (2)), no reader · 126 → not-executable ("permission or noexec"), no reader · 130 → interrupted, no correction offer and no message presented as an error · 137 → killed by `SIGKILL`, with the OOM-killer hint · 143 → `SIGTERM` · `sudo apt update` with status 1 → privilege-wrapper failure: a fixed message saying the password was wrong or the user may not use sudo, no correction offer, nothing that re-runs sudo, no reader · `pkexec …` with 126 and with 127 → privilege-wrapper failure (pkexec's own codes for a dismissed or refused authentication), not "not executable" / "not found" · `su -c …` with 1 → privilege-wrapper failure · 1, 2, 100, 128 and 255 for an ordinary command → other, and ONLY this class goes to the reader. Plus, each as its own assertion: passing a bare `int` instead of #10's done-record type raises `TypeError`; `inspect.signature` of the classify function has no parameter whose name contains `stderr` or `output`; the classifier module's source text (read from its `__file__`) contains none of `/var/`, `/usr/`, `commands.db`, `ubuntu` (the lookup is defined by the active target's `target.toml`); provider names `HTOP`, `htop; rm -rf ~`, `htop\nevil` and `-htop` from the fake lookup are each dropped (whole-string match, not prefix), while `libc6`, `g++` and `python3.12` are kept; the real `targets/ubuntu-26.04` lookup returns `htop` for `htop` when the local data exists on the host (skip that one test when it doesn't — the binding table uses the fake lookup).
- Repo + branch target: eduralph/nl-shell @ main (built in a later wave than #10 and #92: per `Depends on` the driver folds their accepted patches into the wave's integration branch and verifies against it via `$PDCA_VERIFY_BASE`, so #10's done-record type and #92's target loader exist when this bundle builds; if either is not accepted, this bundle is not scheduled. Use their names as they landed; do not invent stand-ins.)
- Scope (one logical fix) / out of scope: (1) A classifier module under `src/nl_shell/`: input = the session's completion result (#10) plus the confirmed command's parsed command word(s) and the command word that would have been not found; output = the class, the user-facing message (fixed templates, no model), `offer_correction` (false for interrupted and privilege-wrapper failures), `to_reader` (true only for "other"). Precedence: exit 0 → none; privilege wrapper (the confirmed command's first word is `sudo`, `su`, `pkexec` or `doas`) with that wrapper's own failure status (sudo/su/doas: 1; pkexec: 126, 127) → privilege-wrapper failure; then 127, 126, 130, 129–192 (128+n, n = 1…64) → signal n by name; everything else → other. Use the command's last pipeline status as the exit status (bash's `$?`), and keep `PIPESTATUS` available to callers. (2) The command word for the 127 lookup comes from the confirmed command text, never from stderr ("bash: x: command not found" is attacker-shaped text). Until the policy gate (#12) supplies a parse, take the first shell word of the confirmed command with the same no-raise tokenizer the router uses (`router.first_token`, `src/nl_shell/router.py:38-48`); note in a comment that #12's parse replaces it. Because `$?` is the *last* command's status, the first word is only the not-found word for a simple command: when the confirmed text contains `|`, `;`, `&`, a newline, or a backtick/`$(`, or its first word is a leading assignment (contains `=`, see `router.py:9-10`) or a wrapper (`env`, `nohup`, `time`, `nice`, `command`, `exec`, `xargs`), the result is not-found with no suggestion. A confident wrong package is worse than none. (3) A provider lookup defined per target: add a field to `targets/ubuntu-26.04/target.toml` describing the local source (on Ubuntu 26.04: the read-only SQLite database `/var/lib/command-not-found/commands.db`, tables `commands(command, pkgID)` and `packages(pkgID, name)` — checked at Plan on this host, `htop` → `htop`), open it read-only, no network (ADR-0003), and return nothing when the data is absent; extend #92's target loader to validate the field (the target loader only — #77 edits #92's separate `config.toml` unit in the same wave). Validate returned names against the Debian package-name rule with a whole-string match (`re.fullmatch(r"[a-z0-9][a-z0-9+.-]+", name)` — not `re.match`, and not a `$` anchor, which accepts a trailing newline). / out of scope: offering or running a correction (#17); `?why` (#14 route → later); calling the reader (#61); deciding "the gate's parse" (#12); real sudo/su/pkexec behaviour checks (M1 #24, the VM tests #75); localisation of messages (ADR-0022); wiring into the REPL; architecture doc 05 (one docs pass after the batch).

# Adversarial review — issue 62 / failure-classes-by-exit-code (iteration 3)

The red→green evidence holds. `gate-logs/C4-verify.log:10-17`: 103 passed with the fix, 103 of 103 failed with the production files reverted, and there were no import or collection errors. The tests call the real `nl_shell.failure_classes.classify` (`tests/test_failure_classes.py:87`) with real `CommandResult`/`Snapshot` objects. They are not a copy of the production code, and the fake lookup only stands in for the SQLite data. T3 is green (`gate-logs/T3-suite.log`, 584 passed). I could not re-run pytest myself (pytest is not installed in this sandbox). I checked the cases below by importing the patched module directly with plain Python, using the host's real `/var/lib/command-not-found/commands.db`.

The two carry-forward items from rounds 1 and 2 are fixed: the `ran`/NOT_RUN check, the `$PATH`/builtin/alias resolution check, `None` in the message, the `htop\n` row, the `sudo` key in the fake lookup, and the sudo-rs/sudoedit aliases. The holes below are new, and all but the last two are on the ADR-0006 path the privilege class exists to protect.

- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:215-218`: the wrapper check only looks at the literal first word, so a sudo run behind any prefix the module already treats as transparent loses its protection. Every one of these was checked with status 1 and returns `other`, `offer_correction=True`, `to_reader=True`: `FOO=1 sudo apt update`, `command sudo apt update`, `env sudo apt update`, `time sudo apt update`, `nice sudo apt update`, `nohup sudo apt`, `exec sudo apt update`. A failed sudo password then gets a correction offer and is sent to the reader, which breaks the ADR-0006 must-hold. The module already lists these exact prefixes in `_COMMAND_WRAPPERS` (`:95-99`) for the not-found path, but never skips them to find the privilege wrapper. `time sudo …` and `VAR=x sudo …` are common forms. Fix: skip leading assignments and the `env`/`command`/`exec`/`time`/`nice`/`nohup` words (plus their option words) before the wrapper lookup, and add table rows. This goes beyond the brief's literal "first word" rule, but in the safe direction, the same way round 2's alias fix did.
- NEEDS-HUMAN [human] — `src/nl_shell/failure_classes.py:72-90`: `run0` (systemd's sudo replacement) is installed on the reference host (`/usr/bin/run0`) and isn't in `WRAPPER_FAILURE_STATUS` or `WRAPPER_ALIASES`. `classify(status=1, "run0 apt update")` → `other`, `offer_correction=True`, `to_reader=True`. A failed or refused polkit (the desktop permission service) authentication under run0 is the same kind of password failure the class is for. This is a new program, not an alias of the four the brief names, and its own failure status is not checked here (I did not run it). So the human should decide whether it joins the list now (with an "unverified" note like the sudo-rs one) or goes to #24/#75.
- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:207` vs `:172-173`: `classify` still accepts a bare `pty_protocol.Done`, which has no `ran` field (`src/nl_shell/pty_protocol.py:51-56`). So the stale-`$?` problem fixed in round 1 comes back on that path: `classify(Done(1, 1, (1,)), "# note")` → `OTHER`, `to_reader=True`, and a stale 127 reads as "Command not found." `tests/test_failure_classes.py:226-233` treats classifying a bare `Done` as supported behavior. Either accept only `CommandResult` (the brief's "completion result"), or have a bare `Done` say in its result that "ran" is unknown. Don't silently treat it as "ran".
- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:277-280`: pkexec 127 shows "you are not authorized, or authentication failed." But pkexec(1) RETURN VALUE also gives 127 for "an error occurred" (for example, the program doesn't exist), and `pkexec sh -c frob` returns the inner 127. The class and flags are what the brief asks for, which is safe. The fixed message, though, tells the user something that may be false. Use wording like "pkexec did not run the command, or it was not found" so the template doesn't overclaim. Low.
- `src/nl_shell/failure_classes.py:292-298` (low, no tag needed): `_is_simple` doesn't treat shell expansions in the first word as uncertain. Checked: `(frobnicate)` → message "Command not found: (frobnicate).", where bash's not-found word is `frobnicate`. `$CMD args` would likewise show `$CMD`. I found no input where this gives a confident *wrong package*: the DB holds no words with `(`, `$`, `*` or `{`, so the lookup returns nothing. The only harm is a wrong word in the display.

Attempted and could not break: the `$`-anchor and suffix tricks on package names (`fullmatch` holds), ESC/bidi/over-long words reaching `message`, `\sudo`/`'sudo'`/`s\udo`/`/usr/bin/sudo` (the tokenizer unquotes them and the class is correct), `\htop` (bash also runs `htop`, so the suggestion is right), and a relative or empty `$PATH` entry (it counts as found, no suggestion). The C4 red leg is real (no import errors) and T3 is green.

### Advisory — security-review

# Security review (advisory) — issue 62, failure classes by exit code

Attacker-reachable inputs this diff touches: the confirmed command text (may be a model proposal, threat-model item 5) and the session snapshot's `$PATH`, functions and aliases (item 4, session state). It does not read stdout/stderr (item 1): `classify` takes only `Done`/`CommandResult` and reads `status`, `pipestatus`, `ran` and `snapshot`, never `output` (`src/nl_shell/failure_classes.py:184-191`). The exit status itself is trusted (control channel). Forged fd-3 records are known gap #135, and this patch does not widen it.

Rated against `.oss-scanner/threat_model.md`. The classifier has no consumer yet (#17, #61 and the REPL wiring are later work), so nothing below can be reached today. Each finding is about what the consumers will inherit.

## Findings

- NEEDS-HUMAN [impl] — **Low** (rated as a defect in a defence for the sudo must-hold; no sudo password leaves the PTY), `src/nl_shell/failure_classes.py:215-218`. Input: the confirmed command text. A steered model proposal or a user habit controls it. The privilege-wrapper rule looks only at the first shell word, so a failed sudo authentication behind a prefix is classed `other`, with `offer_correction=True` and `to_reader=True`. That is exactly what this class exists to prevent (brief: "no correction offer, nothing that re-runs sudo, no reader"; ADR-0006). Reproduced on the patched tree with a `CommandResult` whose status is 1: `env sudo apt update`, `nohup sudo apt`, `time sudo apt`, `command sudo apt`, `exec sudo -i`, `FOO=1 sudo apt` and `true && sudo apt update` all give `other True True`. `env pkexec ls` with 127 gives `not_found` with `offer_correction=True`, where it should be a pkexec authorization failure. (`ls | sudo tee …` gives the same, but the gate rejects pipes into sudo, so it is not reachable.) A user alias such as `s=sudo` gives the same result: `s apt update` → `other`. Fix: take the conservative side. If any shell word of the confirmed command (basename, after `WRAPPER_ALIASES`) is a privilege wrapper and the status is in that wrapper's failure set, return `PRIVILEGE_WRAPPER`. Check the snapshot's aliases for the first word too. Add table rows for `env sudo …`, `FOO=1 sudo …`, `true && sudo …` and `env pkexec …` (127). Today's tests cover only a wrapper in first position (`tests/test_failure_classes.py:123`, `:313-315`).

- NEEDS-HUMAN [human] — **Low**, `src/nl_shell/failure_classes.py:72-90`. Input: the confirmed command text. `run0` (systemd's sudo-like wrapper) is installed on this host (`/usr/bin/run0`). It is not in `WRAPPER_FAILURE_STATUS`/`WRAPPER_ALIASES`, so `run0 apt update` exiting 1 is classed `other`, with a correction offer and `to_reader=True`. run0's own failure status is not documented the way pkexec's is, so the builder can't just pick a number. A human should decide whether nl-shell treats run0 as a privilege wrapper. That decision also affects the gate's privileged class (#12), not only this table.

## Checked, no finding

- **Display of the not-found word** (`:227-242`, `:301-303`): only printable words of at most 64 characters reach `message`/`command_word`. ESC, BEL, U+202E, U+200B and U+2028 all give the plain "Command not found.". Tests pin this (`tests/test_failure_classes.py:250-263`). The wrapper message interpolates only names from the fixed tables (`:217-222`).
- **Package names from the database** (`:330-342`): `re.fullmatch` against the Debian rule, at most 5 names. Tests include `htop\n`, `htop; rm -rf ~` and `-htop` (`tests/test_failure_classes.py:364`).
- **SQL** (`:361-373`, `src/nl_shell/targets.py:213-231`): the query comes from the repo's `targets/<id>/target.toml` (loaded from `TARGETS_ROOT`, which is trusted). The command word is bound as a `?` parameter, so it can't inject SQL. The database is opened with `mode=ro` and a 1 s timeout, with no network. sqlite3's `execute` refuses multiple statements.
- **Session `$PATH` from the snapshot** (`:306-327`): an attacker-set `PATH` (direnv) can only switch the suggestion off, or name a package from the trusted local database. Nothing runs. The stat calls are the same lookups bash makes itself. Empty or relative entries count as "found", which is the safe side.
- **Stale status**: `ran=False` → `NOT_RUN` (`:207-208`), with a test (`tests/test_failure_classes.py:240`).
- **Gates**: C4 is red without the fix and green with it (103/103). T3 suite: 584 passed (`gate-logs/T3-suite.log`). T2 found no security-relevant path, which is right: the patch adds no new path for untrusted input.
