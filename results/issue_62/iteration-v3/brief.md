- **Slug:** failure-classes-by-exit-code
- **Kind:** enhancement (design proposal)
- **Goal:** A deterministic first pass that classifies a finished command's failure from trusted facts only — the exit status from the PTY session's done record and the command the user confirmed — into: not found (127), not executable (126), interrupted (130), killed by signal n (128+n), privilege-wrapper failure (sudo, su, pkexec, doas), and other. Each class carries its fixed response: what to tell the user, whether a correction may be offered, and whether the case goes to the quarantined reader. For "not found" it suggests the package that provides the command from local package data named by the active target.
- **Success criterion:** `python3 -m pytest tests/test_failure_classes.py` passes, with a table-driven test that covers each class: exit 0 → no failure · 127 for `htop` with a fake provider lookup that knows `htop` → not-found, suggests package `htop`, no reader · 127 for a command the lookup doesn't know → not-found without a suggestion, no reader · 127 for `cat f | htop`, `make && htop`, `true; htop`, `FOO=1 htop` and `env htop` (fake lookup knows `htop`, `cat`, `make`, `env`) → not-found with NO suggestion (the not-found word can't be told from the first token, see Scope (2)), no reader · 126 → not-executable ("permission or noexec"), no reader · 130 → interrupted, no correction offer and no message presented as an error · 137 → killed by `SIGKILL`, with the OOM-killer hint · 143 → `SIGTERM` · `sudo apt update` with status 1 → privilege-wrapper failure: a fixed message saying the password was wrong or the user may not use sudo, no correction offer, nothing that re-runs sudo, no reader · `pkexec …` with 126 and with 127 → privilege-wrapper failure (pkexec's own codes for a dismissed or refused authentication), not "not executable" / "not found" · `su -c …` with 1 → privilege-wrapper failure · 1, 2, 100, 128 and 255 for an ordinary command → other, and ONLY this class goes to the reader. ## Motivation

A non-zero exit is not one kind of failure. Several kinds can be told apart without a
model, cheaply and testably, and two of them must never produce a correction offer:
Ctrl-C (not an error) and a failed sudo authentication (ADR-0006: nothing may touch the
password). Sending only the remaining "other" class to the reader keeps raw stderr away
from models in the common cases.

## Design

Fixed precedence (above), fixed message templates, and a result type with explicit
`offer_correction` and `to_reader` flags so #17 and #61 can't misread it. The
privilege-wrapper rule is deliberately conservative: `sudo grep x f` exiting 1 (no match)
is classed as a wrapper failure, which only suppresses a correction offer — the safe
direction.

## Alternatives considered

- Parsing stderr ("command not found", "incorrect password"): rejected, stderr is
  untrusted and locale-dependent; the issue says only the exit code and the gate's parse
  are trusted.
- Running `/usr/lib/command-not-found`: its output is localised prose; the SQLite data is
  structured and read-only.

## Impact & compatibility

New `target.toml` field; no user-visible change until #17 uses the classes.

## Open questions

- **Needs explicit sign-off (product decision).** Privilege wrapper + status 1 cannot tell
  "wrong password" from "the command under sudo returned 1". Treating both as a wrapper
  failure (proposed) goes beyond the issue's Done-when and removes fix-on-failure and the
  reader for every `sudo grep …`, `sudo systemctl …` that exits 1. #13's passthrough state
  could later tell them apart. The human confirms or rejects this at sign-off.
