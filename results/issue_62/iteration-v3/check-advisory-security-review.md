# Security review (advisory) — issue 62, failure classes by exit code

Attacker-reachable inputs this diff touches: the confirmed command text (may be a model proposal, threat-model item 5) and the session snapshot's `$PATH`, functions and aliases (item 4, session state). It does not read stdout/stderr (item 1): `classify` takes only `Done`/`CommandResult` and reads `status`, `pipestatus`, `ran` and `snapshot`, never `output` (`src/nl_shell/failure_classes.py:184-191`). The exit status itself is trusted (control channel). Forged fd-3 records are known gap #135, and this patch does not widen it.

Rated against `.oss-scanner/threat_model.md`. The classifier has no consumer yet (#17, #61 and the REPL wiring are later work), so nothing below can be reached today. Each finding is about what the consumers will inherit.

## Findings

- NEEDS-HUMAN [impl] — **Low** (rated as a defect in a defence for the sudo must-hold; no sudo password leaves the PTY), `src/nl_shell/failure_classes.py:215-218`. Input: the confirmed command text. A steered model proposal or a user habit controls it. The privilege-wrapper rule looks only at the first shell word, so a failed sudo authentication behind a prefix is classed `other`, with `offer_correction=True` and `to_reader=True`. That is exactly what this class exists to prevent (brief: "no correction offer, nothing that re-runs sudo, no reader"; ADR-0006). Reproduced on the patched tree with a `CommandResult` whose status is 1: `env sudo apt update`, `nohup sudo apt`, `time sudo apt`, `command sudo apt`, `exec sudo -i`, `FOO=1 sudo apt` and `true && sudo apt update` all give `other True True`. `env pkexec ls` with 127 gives `not_found` with `offer_correction=True`, where it should be a pkexec authorization failure. (`ls | sudo tee …` gives the same, but the gate rejects pipes into sudo, so it is not reachable.) A user alias such as `s=sudo` gives the same result: `s apt update` → `other`. Fix: take the conservative side. If any shell word of the confirmed command (basename, after `WRAPPER_ALIASES`) is a privilege wrapper and the status is in that wrapper's failure set, return `PRIVILEGE_WRAPPER`. Check the snapshot's aliases for the first word too. Add table rows for `env sudo …`, `FOO=1 sudo …`, `true && sudo …` and `env pkexec …` (127). Today's tests cover only a wrapper in first position (`tests/test_failure_classes.py:123`, `:313-315`).

- NEEDS-HUMAN [human] — **Low**, `src/nl_shell/failure_classes.py:72-90`. Input: the confirmed command text. `run0` (systemd's sudo-like wrapper) is installed on this host (`/usr/bin/run0`). It is not in `WRAPPER_FAILURE_STATUS`/`WRAPPER_ALIASES`, so `run0 apt update` exiting 1 is classed `other`, with a correction offer and `to_reader=True`. run0's own failure status is not documented the way pkexec's is, so the builder can't just pick a number. A human should decide whether nl-shell treats run0 as a privilege wrapper. That decision also affects the gate's privileged class (#12), not only this table.

## Checked, no finding

- **Display of the not-found word** (`:227-242`, `:301-303`): only printable words of at most 64 characters reach `message`/`command_word`. ESC, BEL, U+202E, U+200B and U+2028 all give the plain "Command not found.". Tests pin this (`tests/test_failure_classes.py:250-263`). The wrapper message interpolates only names from the fixed tables (`:217-222`).
- **Package names from the database** (`:330-342`): `re.fullmatch` against the Debian rule, at most 5 names. Tests include `htop\n`, `htop; rm -rf ~` and `-htop` (`tests/test_failure_classes.py:364`).
- **SQL** (`:361-373`, `src/nl_shell/targets.py:213-231`): the query comes from the repo's `targets/<id>/target.toml` (loaded from `TARGETS_ROOT`, which is trusted). The command word is bound as a `?` parameter, so it can't inject SQL. The database is opened with `mode=ro` and a 1 s timeout, with no network. sqlite3's `execute` refuses multiple statements.
- **Session `$PATH` from the snapshot** (`:306-327`): an attacker-set `PATH` (direnv) can only switch the suggestion off, or name a package from the trusted local database. Nothing runs. The stat calls are the same lookups bash makes itself. Empty or relative entries count as "found", which is the safe side.
- **Stale status**: `ran=False` → `NOT_RUN` (`:207-208`), with a test (`tests/test_failure_classes.py:240`).
- **Gates**: C4 is red without the fix and green with it (103/103). T3 suite: 584 passed (`gate-logs/T3-suite.log`). T2 found no security-relevant path, which is right: the patch adds no new path for untrusted input.
