# Adversarial review — issue 62 / failure-classes-by-exit-code (iteration 3)

The red→green evidence holds. `gate-logs/C4-verify.log:10-17`: 103 passed with the fix, 103 of 103 failed with the production files reverted, and there were no import or collection errors. The tests call the real `nl_shell.failure_classes.classify` (`tests/test_failure_classes.py:87`) with real `CommandResult`/`Snapshot` objects. They are not a copy of the production code, and the fake lookup only stands in for the SQLite data. T3 is green (`gate-logs/T3-suite.log`, 584 passed). I could not re-run pytest myself (pytest is not installed in this sandbox). I checked the cases below by importing the patched module directly with plain Python, using the host's real `/var/lib/command-not-found/commands.db`.

The two carry-forward items from rounds 1 and 2 are fixed: the `ran`/NOT_RUN check, the `$PATH`/builtin/alias resolution check, `None` in the message, the `htop\n` row, the `sudo` key in the fake lookup, and the sudo-rs/sudoedit aliases. The holes below are new, and all but the last two are on the ADR-0006 path the privilege class exists to protect.

- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:215-218`: the wrapper check only looks at the literal first word, so a sudo run behind any prefix the module already treats as transparent loses its protection. Every one of these was checked with status 1 and returns `other`, `offer_correction=True`, `to_reader=True`: `FOO=1 sudo apt update`, `command sudo apt update`, `env sudo apt update`, `time sudo apt update`, `nice sudo apt update`, `nohup sudo apt`, `exec sudo apt update`. A failed sudo password then gets a correction offer and is sent to the reader, which breaks the ADR-0006 must-hold. The module already lists these exact prefixes in `_COMMAND_WRAPPERS` (`:95-99`) for the not-found path, but never skips them to find the privilege wrapper. `time sudo …` and `VAR=x sudo …` are common forms. Fix: skip leading assignments and the `env`/`command`/`exec`/`time`/`nice`/`nohup` words (plus their option words) before the wrapper lookup, and add table rows. This goes beyond the brief's literal "first word" rule, but in the safe direction, the same way round 2's alias fix did.
- NEEDS-HUMAN [human] — `src/nl_shell/failure_classes.py:72-90`: `run0` (systemd's sudo replacement) is installed on the reference host (`/usr/bin/run0`) and isn't in `WRAPPER_FAILURE_STATUS` or `WRAPPER_ALIASES`. `classify(status=1, "run0 apt update")` → `other`, `offer_correction=True`, `to_reader=True`. A failed or refused polkit (the desktop permission service) authentication under run0 is the same kind of password failure the class is for. This is a new program, not an alias of the four the brief names, and its own failure status is not checked here (I did not run it). So the human should decide whether it joins the list now (with an "unverified" note like the sudo-rs one) or goes to #24/#75.
- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:207` vs `:172-173`: `classify` still accepts a bare `pty_protocol.Done`, which has no `ran` field (`src/nl_shell/pty_protocol.py:51-56`). So the stale-`$?` problem fixed in round 1 comes back on that path: `classify(Done(1, 1, (1,)), "# note")` → `OTHER`, `to_reader=True`, and a stale 127 reads as "Command not found." `tests/test_failure_classes.py:226-233` treats classifying a bare `Done` as supported behavior. Either accept only `CommandResult` (the brief's "completion result"), or have a bare `Done` say in its result that "ran" is unknown. Don't silently treat it as "ran".
- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:277-280`: pkexec 127 shows "you are not authorized, or authentication failed." But pkexec(1) RETURN VALUE also gives 127 for "an error occurred" (for example, the program doesn't exist), and `pkexec sh -c frob` returns the inner 127. The class and flags are what the brief asks for, which is safe. The fixed message, though, tells the user something that may be false. Use wording like "pkexec did not run the command, or it was not found" so the template doesn't overclaim. Low.
- `src/nl_shell/failure_classes.py:292-298` (low, no tag needed): `_is_simple` doesn't treat shell expansions in the first word as uncertain. Checked: `(frobnicate)` → message "Command not found: (frobnicate).", where bash's not-found word is `frobnicate`. `$CMD args` would likewise show `$CMD`. I found no input where this gives a confident *wrong package*: the DB holds no words with `(`, `$`, `*` or `{`, so the lookup returns nothing. The only harm is a wrong word in the display.

Attempted and could not break: the `$`-anchor and suffix tricks on package names (`fullmatch` holds), ESC/bidi/over-long words reaching `message`, `\sudo`/`'sudo'`/`s\udo`/`/usr/bin/sudo` (the tokenizer unquotes them and the class is correct), `\htop` (bash also runs `htop`, so the suggestion is right), and a relative or empty `$PATH` entry (it counts as found, no suggestion). The C4 red leg is real (no import errors) and T3 is green.
