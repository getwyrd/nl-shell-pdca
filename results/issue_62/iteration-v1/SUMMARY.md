# Result — issue 62 / failure-classes-by-exit-code

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: A deterministic first pass that classifies a finished command's failure from trusted facts only — the exit status from the PTY session's done record and the command the user confirmed — into: not found (127), not executable (126), interrupted (130), killed by signal n (128+n), privilege-wrapper failure (sudo, su, pkexec, doas), and other. Each class carries its fixed response: what to tell the user, whether a correction may be offered, and whether the case goes to the quarantined reader. For "not found" it suggests the package that provides the command from local package data named by the active target.
- Success criterion: `python3 -m pytest tests/test_failure_classes.py` passes, with a table-driven test that covers each class: exit 0 → no failure · 127 for `htop` with a fake provider lookup that knows `htop` → not-found, suggests package `htop`, no reader · 127 for a command the lookup doesn't know → not-found without a suggestion, no reader · 127 for `cat f | htop`, `make && htop`, `true; htop`, `FOO=1 htop` and `env htop` (fake lookup knows `htop`, `cat`, `make`, `env`) → not-found with NO suggestion (the not-found word can't be told from the first token, see Scope (2)), no reader · 126 → not-executable ("permission or noexec"), no reader · 130 → interrupted, no correction offer and no message presented as an error · 137 → killed by `SIGKILL`, with the OOM-killer hint · 143 → `SIGTERM` · `sudo apt update` with status 1 → privilege-wrapper failure: a fixed message saying the password was wrong or the user may not use sudo, no correction offer, nothing that re-runs sudo, no reader · `pkexec …` with 126 and with 127 → privilege-wrapper failure (pkexec's own codes for a dismissed or refused authentication), not "not executable" / "not found" · `su -c …` with 1 → privilege-wrapper failure · 1, 2, 100, 128 and 255 for an ordinary command → other, and ONLY this class goes to the reader. Plus, each as its own assertion: passing a bare `int` instead of #10's done-record type raises `TypeError`; `inspect.signature` of the classify function has no parameter whose name contains `stderr` or `output`; the classifier module's source text (read from its `__file__`) contains none of `/var/`, `/usr/`, `commands.db`, `ubuntu` (the lookup is defined by the active target's `target.toml`); provider names `HTOP`, `htop; rm -rf ~`, `htop\nevil` and `-htop` from the fake lookup are each dropped (whole-string match, not prefix), while `libc6`, `g++` and `python3.12` are kept; the real `targets/ubuntu-26.04` lookup returns `htop` for `htop` when the local data exists on the host (skip that one test when it doesn't — the binding table uses the fake lookup).
- Repo + branch target: eduralph/nl-shell @ main (built in a later wave than #10 and #92: per `Depends on` the driver folds their accepted patches into the wave's integration branch and verifies against it via `$PDCA_VERIFY_BASE`, so #10's done-record type and #92's target loader exist when this bundle builds; if either is not accepted, this bundle is not scheduled. Use their names as they landed; do not invent stand-ins.)
- Scope (one logical fix) / out of scope: (1) A classifier module under `src/nl_shell/`: input = the session's completion result (#10) plus the confirmed command's parsed command word(s) and the command word that would have been not found; output = the class, the user-facing message (fixed templates, no model), `offer_correction` (false for interrupted and privilege-wrapper failures), `to_reader` (true only for "other"). Precedence: exit 0 → none; privilege wrapper (the confirmed command's first word is `sudo`, `su`, `pkexec` or `doas`) with that wrapper's own failure status (sudo/su/doas: 1; pkexec: 126, 127) → privilege-wrapper failure; then 127, 126, 130, 129–192 (128+n, n = 1…64) → signal n by name; everything else → other. Use the command's last pipeline status as the exit status (bash's `$?`), and keep `PIPESTATUS` available to callers. (2) The command word for the 127 lookup comes from the confirmed command text, never from stderr ("bash: x: command not found" is attacker-shaped text). Until the policy gate (#12) supplies a parse, take the first shell word of the confirmed command with the same no-raise tokenizer the router uses (`router.first_token`, `src/nl_shell/router.py:38-48`); note in a comment that #12's parse replaces it. Because `$?` is the *last* command's status, the first word is only the not-found word for a simple command: when the confirmed text contains `|`, `;`, `&`, a newline, or a backtick/`$(`, or its first word is a leading assignment (contains `=`, see `router.py:9-10`) or a wrapper (`env`, `nohup`, `time`, `nice`, `command`, `exec`, `xargs`), the result is not-found with no suggestion. A confident wrong package is worse than none. (3) A provider lookup defined per target: add a field to `targets/ubuntu-26.04/target.toml` describing the local source (on Ubuntu 26.04: the read-only SQLite database `/var/lib/command-not-found/commands.db`, tables `commands(command, pkgID)` and `packages(pkgID, name)` — checked at Plan on this host, `htop` → `htop`), open it read-only, no network (ADR-0003), and return nothing when the data is absent; extend #92's target loader to validate the field (the target loader only — #77 edits #92's separate `config.toml` unit in the same wave). Validate returned names against the Debian package-name rule with a whole-string match (`re.fullmatch(r"[a-z0-9][a-z0-9+.-]+", name)` — not `re.match`, and not a `$` anchor, which accepts a trailing newline). / out of scope: offering or running a correction (#17); `?why` (#14 route → later); calling the reader (#61); deciding "the gate's parse" (#12); real sudo/su/pkexec behaviour checks (M1 #24, the VM tests #75); localisation of messages (ADR-0022); wiring into the REPL; architecture doc 05 (one docs pass after the batch).

### Advisory — adversary

# Adversarial review — issue 62 / failure-classes-by-exit-code

**Evidence.** The red→green proof holds as far as it goes. `gate-logs/C4-verify.log` shows 59 of 59 tests failed pre-fix and all passed after. `gate-logs/T3-suite.log` shows 540 passed. Every red failure is `ModuleNotFoundError` or an `AttributeError` on the loader. So the red leg only proves the module was missing. It does not prove that each assertion can tell a right implementation from a wrong one. I checked the assertions by hand and found two that can't (below). The tests do call the production path (`nl_shell.failure_classes.classify`, `targets.load`), not a copy. I ran each case below against the patched tree at `$PDCA_TARGET` with the host's real `commands.db`.

- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:70` (`_COMMAND_WRAPPERS`) together with `:231` (`_is_simple`): a 127 that comes from a program that was found gives a confident wrong package. That is the exact case the brief calls "worse than none". Real output: `timeout 5 frobnicate` → "Command not found: timeout. It is provided by the packages coreutils-from-busybox, coreutils-from-gnu, …". timeout(1) returns 127 when *its* command is missing. The same happens for `stdbuf -oL frobnicate`, `chroot / frobnicate` and `setsid frobnicate` (util-linux), plus `bash -c frobnicate` → package `bash` and `ssh host frobnicate` → `openssh-client`. The seven-word list in the brief is not enough. Possible fixes: add the coreutils/util-linux exec-wrappers (`timeout`, `stdbuf`, `chroot`, `setsid`, `ionice`, `taskset`, `nsenter`, `unshare`, `flock`, `runuser`, `eval`, `bash`/`sh -c`, `ssh`). A sounder fix is to give no suggestion when the first word resolves on the session's `$PATH` (`Snapshot.path`) or is a builtin, function or alias (`Snapshot.functions` / `aliases`). If bash found the word, the word was not "not found".
- NEEDS-HUMAN [human] — `src/nl_shell/failure_classes.py:160-162`: the privilege-wrapper rule only looks at the first word. So a failed sudo authentication in any other position becomes `OTHER`, with `offer_correction=True` and `to_reader=True`. Confirmed: `cd /x && sudo apt update`, `time sudo apt update`, `FOO=1 sudo apt update` and `nohup sudo apt update`, each with status 1, all give `OTHER True True`. This follows the brief's literal rule. But it means sudo's stderr reaches the reader, and #17 may offer a correction for a sudo command. That is the ADR-0006/0015 must-hold the brief sets out to protect. The human should decide whether "sudo/su/pkexec/doas anywhere in the confirmed command" should be the rule. It would be the same conservative direction the Design section already accepts for `sudo grep`.
- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:135-140`: `classify` ignores `CommandResult.ran`. Protocol §4.1 (`docs/design/specs/pty-protocol/v1.md:370-372`) says `D` without `S` means nothing ran (an empty line, a comment, a syntax error). For an empty line or comment, `$?` is the *previous* command's status. Confirmed: `CommandResult(ran=False, status=1)` with command `"# a note"` or `""` gives `OTHER`, `to_reader=True`, `offer_correction=True`. A stale 127 from an earlier command would likewise show up as "Command not found." Fix: when `ran` is False, return `NONE` (or a "not run" class). Add a test row for it.
- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:171,177`: when the lookup returns packages but the word is non-printable or longer than 64 characters, `shown` is `None` and the message renders the literal text "None". Confirmed: `classify(Done(1,127,(127,)), "a"*65, lambda w: ["htop"])` gives "Command not found: None. It is provided by the package htop." The no-package branch handles `shown is None`, but the package branch doesn't. The same check should also skip the suggestion altogether.
- NEEDS-HUMAN [impl] — `tests/test_failure_classes.py:209`: the bad-name cases can't catch the `$`-anchor mistake the brief names. `re.compile(r"[a-z0-9][a-z0-9+.-]+$").match("htop\nevil")` is already False, because `$` only accepts a *trailing* newline. So the test passes with `re.match(...$)` as well as with `fullmatch`. Add `"htop\n"`: `$` accepts it and `fullmatch` rejects it. The brief's own case list has the same gap, but the builder can fix it.
- NEEDS-HUMAN [impl] — `tests/test_failure_classes.py:60` (`not-found-under-sudo`): the fake lookup doesn't know `sudo`. If you remove `| set(WRAPPER_FAILURE_STATUS)` from `_COMMAND_WRAPPERS` (`failure_classes.py:70-72`), every test still passes. On the real host, `sudo frobnicate` → 127 would then suggest `sudo, sudo-rs` (the real lookup returns `('sudo', 'sudo-rs')`). Add `"sudo": ["sudo"]` to `FAKE_PROVIDERS` so that row actually tests the exclusion.

**Tried and could not break.** Pipelines, `&&`/`;`/newline/backtick/`$(` lists. Quoted or backslash-escaped first words (`\sudo`, `'htop'`). The `/usr/bin/sudo` basename. pkexec 126/127. SIGRTMIN naming at 34–64. The bare-`int` `TypeError`. The read-only SQLite open: a writing query fails and is caught, and a multi-statement query raises `ProgrammingError`, which is a `sqlite3.Error`, so it is caught. The missing-database path. The loader checks for format, absolute path and a single `?`. The OS-name scan of the source. The `check-gates.json` C4/T3 PASS claims match their logs. The reviewer's main weak spot is reading the 59/59 red as proof that each assertion discriminates, when it only proves the module was missing.

### Advisory — security-review

# Security review (advisory) — issue 62, failure classes by exit code

**Attacker-reachable inputs this diff touches:** the confirmed command text (trusted as a user decision, but it can be a model proposal, threat-model item 5); the done record's exit status (trusted, though fd-3 records can be forged — known gap #135); and the package names read from the target's command-not-found SQLite file. It does **not** read stderr or PTY output (threat-model item 1). `inspect.signature`, the `CommandResult.output` row and the source text confirm this.

Rubric: `target/.oss-scanner/threat_model.md`, its severity scale. I followed `AGENTS.md`; it lists no deferrals that apply here.

## Findings

- NEEDS-HUMAN [human] — **Below Low on the scale (no must-hold broken today: there are no consumers yet). It weakens the brief's own sudo rule.** `src/nl_shell/failure_classes.py:160-162`. Input: the confirmed command text, which the model can shape (item 5). The privilege-wrapper class only fires when the *first* shell word is `sudo`/`su`/`pkexec`/`doas`. Any prefix the policy gate (the deterministic check that classes each command before it runs) still treats as privileged gets past it: a wrapper, an assignment, or a list. The failed authentication then comes out as `OTHER`, with `offer_correction=True` and `to_reader=True`. Once #17 is built, it would offer a correction (likely a sudo re-run) for a failed sudo auth, which is exactly what the brief and ADR-0006 rule out. I ran the patched module against `Done(status=1)`:
  `env sudo apt update`, `command sudo apt update`, `time sudo apt update`, `FOO=1 sudo apt update` and `true && sudo apt update` → all `OTHER True True`. Plain `sudo apt update` → `PRIVILEGE_WRAPPER False False`.
  The password itself is not exposed: passthrough stops capture (ADR-0015), so the reader never sees it. The brief chose "first word" on purpose, and #12's parse replaces it. So a human decides between two options. One: accept this until #12. Two: ask for the safe-side rule now ("a wrapper word anywhere in the command plus that wrapper's failure status → wrapper failure") plus test rows for the inputs above. The test table has no row for a wrapped or listed sudo.

- NEEDS-HUMAN [impl] — **Low.** `src/nl_shell/failure_classes.py:171`. Input: the not-found command word from the confirmed text. The display guard (`isprintable()`, at most 64 chars) does its job. `'\x1b[2Jfoo‮'` gives the message `"Command not found."` with no escape and no bidi character (bidi: invisible marks that flip the display direction of text). But no test covers it: every not-found row uses plain ASCII, so taking the guard out would keep the suite green. Add rows with an ESC byte, a bidi override (U+202E) and a 65-char word, and assert none of them reach `message`. Related: `Failure.command_word` (set right after line 177) keeps the raw word unfiltered. A later consumer (#17, `?why`) that prints it would skip this guard. A docstring line saying "not display-safe" or a test that pins the behaviour would make the contract clear.

- NEEDS-HUMAN [human] — **No severity (threat-model upkeep).** `targets/ubuntu-26.04/target.toml` `[command_provider]` and `src/nl_shell/failure_classes.py:278-280` add a new trusted local input: the root-owned `/var/lib/command-not-found/commands.db`, plus a SQL query taken from `target.toml`. The threat model's "Trusted" list doesn't name it. The T2 gate said "no security-relevant path touched" (`gate-logs/T2-threat-model.log`), so nothing pushed an update. The threat model says each change that lands code updates it. A human should decide whether to add this file under "Trusted" (similar to the dpkg-owned man pages) in this patch or in the docs pass the brief defers.

## Not a security finding (correctness, for code-review)

`failure_classes.py:171-177`: if the word fails the display guard but the lookup still returns packages, the message reads `"Command not found: None. It is provided by the package htop."`. I reproduced this with a 70-char word and a fake lookup. Nothing leaks; it is just a bad template.

## Checked, no finding

- **SQL injection:** none. The command word is a bound parameter (`:280`). The query text comes from the repo's `target.toml` (trusted config). Multi-statement queries fail inside `sqlite3`, and that error is caught.
- **Read-only / no network (ADR-0003):** `mode=ro` URI, 1 s timeout, all errors give `()`. The test shows an `INSERT … RETURNING` writes nothing, and a missing file is not created.
- **Package names reaching messages:** the `re.fullmatch` Debian-name rule drops `htop; rm -rf ~`, `htop\nevil`, `HTOP` and `-htop`, and keeps at most 5 names (`_packages`). Tests cover both good and bad names.
- **Wrapper name in messages:** it only comes from the fixed `WRAPPER_FAILURE_STATUS` keys, so no attacker text gets in.
- **Path traversal through target loading:** this diff doesn't change it. `command_provider.path` must be absolute and comes from trusted repo config.
- **Resource use:** `fetchall()` has no row cap, but the source is root-owned system data, not attacker-sized.
- **Forged exit status:** a command writing a fake `D` record on fd 3 could move a failure between classes. That is known gap #135, and this patch doesn't widen it.
- **Toolchain:** none missing. I ran the reproducers above on the patched source with the host's `python3`.
