# Adversarial review — issue 62 / failure-classes-by-exit-code

**Evidence.** The red→green proof holds as far as it goes. `gate-logs/C4-verify.log` shows 59 of 59 tests failed pre-fix and all passed after. `gate-logs/T3-suite.log` shows 540 passed. Every red failure is `ModuleNotFoundError` or an `AttributeError` on the loader. So the red leg only proves the module was missing. It does not prove that each assertion can tell a right implementation from a wrong one. I checked the assertions by hand and found two that can't (below). The tests do call the production path (`nl_shell.failure_classes.classify`, `targets.load`), not a copy. I ran each case below against the patched tree at `$PDCA_TARGET` with the host's real `commands.db`.

- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:70` (`_COMMAND_WRAPPERS`) together with `:231` (`_is_simple`): a 127 that comes from a program that was found gives a confident wrong package. That is the exact case the brief calls "worse than none". Real output: `timeout 5 frobnicate` → "Command not found: timeout. It is provided by the packages coreutils-from-busybox, coreutils-from-gnu, …". timeout(1) returns 127 when *its* command is missing. The same happens for `stdbuf -oL frobnicate`, `chroot / frobnicate` and `setsid frobnicate` (util-linux), plus `bash -c frobnicate` → package `bash` and `ssh host frobnicate` → `openssh-client`. The seven-word list in the brief is not enough. Possible fixes: add the coreutils/util-linux exec-wrappers (`timeout`, `stdbuf`, `chroot`, `setsid`, `ionice`, `taskset`, `nsenter`, `unshare`, `flock`, `runuser`, `eval`, `bash`/`sh -c`, `ssh`). A sounder fix is to give no suggestion when the first word resolves on the session's `$PATH` (`Snapshot.path`) or is a builtin, function or alias (`Snapshot.functions` / `aliases`). If bash found the word, the word was not "not found".
- NEEDS-HUMAN [human] — `src/nl_shell/failure_classes.py:160-162`: the privilege-wrapper rule only looks at the first word. So a failed sudo authentication in any other position becomes `OTHER`, with `offer_correction=True` and `to_reader=True`. Confirmed: `cd /x && sudo apt update`, `time sudo apt update`, `FOO=1 sudo apt update` and `nohup sudo apt update`, each with status 1, all give `OTHER True True`. This follows the brief's literal rule. But it means sudo's stderr reaches the reader, and #17 may offer a correction for a sudo command. That is the ADR-0006/0015 must-hold the brief sets out to protect. The human should decide whether "sudo/su/pkexec/doas anywhere in the confirmed command" should be the rule. It would be the same conservative direction the Design section already accepts for `sudo grep`.
- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:135-140`: `classify` ignores `CommandResult.ran`. Protocol §4.1 (`docs/design/specs/pty-protocol/v1.md:370-372`) says `D` without `S` means nothing ran (an empty line, a comment, a syntax error). For an empty line or comment, `$?` is the *previous* command's status. Confirmed: `CommandResult(ran=False, status=1)` with command `"# a note"` or `""` gives `OTHER`, `to_reader=True`, `offer_correction=True`. A stale 127 from an earlier command would likewise show up as "Command not found." Fix: when `ran` is False, return `NONE` (or a "not run" class). Add a test row for it.
- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:171,177`: when the lookup returns packages but the word is non-printable or longer than 64 characters, `shown` is `None` and the message renders the literal text "None". Confirmed: `classify(Done(1,127,(127,)), "a"*65, lambda w: ["htop"])` gives "Command not found: None. It is provided by the package htop." The no-package branch handles `shown is None`, but the package branch doesn't. The same check should also skip the suggestion altogether.
- NEEDS-HUMAN [impl] — `tests/test_failure_classes.py:209`: the bad-name cases can't catch the `$`-anchor mistake the brief names. `re.compile(r"[a-z0-9][a-z0-9+.-]+$").match("htop\nevil")` is already False, because `$` only accepts a *trailing* newline. So the test passes with `re.match(...$)` as well as with `fullmatch`. Add `"htop\n"`: `$` accepts it and `fullmatch` rejects it. The brief's own case list has the same gap, but the builder can fix it.
- NEEDS-HUMAN [impl] — `tests/test_failure_classes.py:60` (`not-found-under-sudo`): the fake lookup doesn't know `sudo`. If you remove `| set(WRAPPER_FAILURE_STATUS)` from `_COMMAND_WRAPPERS` (`failure_classes.py:70-72`), every test still passes. On the real host, `sudo frobnicate` → 127 would then suggest `sudo, sudo-rs` (the real lookup returns `('sudo', 'sudo-rs')`). Add `"sudo": ["sudo"]` to `FAKE_PROVIDERS` so that row actually tests the exclusion.

**Tried and could not break.** Pipelines, `&&`/`;`/newline/backtick/`$(` lists. Quoted or backslash-escaped first words (`\sudo`, `'htop'`). The `/usr/bin/sudo` basename. pkexec 126/127. SIGRTMIN naming at 34–64. The bare-`int` `TypeError`. The read-only SQLite open: a writing query fails and is caught, and a multi-statement query raises `ProgrammingError`, which is a `sqlite3.Error`, so it is caught. The missing-database path. The loader checks for format, absolute path and a single `?`. The OS-name scan of the source. The `check-gates.json` C4/T3 PASS claims match their logs. The reviewer's main weak spot is reading the 59/59 red as proof that each assertion discriminates, when it only proves the module was missing.
