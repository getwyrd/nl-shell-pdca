# Result — issue 62 / failure-classes-by-exit-code

## 1. Spec (from brief.md)              ← Check verifies against THIS
- Defect / goal: A deterministic first pass that classifies a finished command's failure from trusted facts only — the exit status from the PTY session's done record and the command the user confirmed — into: not found (127), not executable (126), interrupted (130), killed by signal n (128+n), privilege-wrapper failure (sudo, su, pkexec, doas), and other. Each class carries its fixed response: what to tell the user, whether a correction may be offered, and whether the case goes to the quarantined reader. For "not found" it suggests the package that provides the command from local package data named by the active target.
- Success criterion: `python3 -m pytest tests/test_failure_classes.py` passes, with a table-driven test that covers each class: exit 0 → no failure · 127 for `htop` with a fake provider lookup that knows `htop` → not-found, suggests package `htop`, no reader · 127 for a command the lookup doesn't know → not-found without a suggestion, no reader · 127 for `cat f | htop`, `make && htop`, `true; htop`, `FOO=1 htop` and `env htop` (fake lookup knows `htop`, `cat`, `make`, `env`) → not-found with NO suggestion (the not-found word can't be told from the first token, see Scope (2)), no reader · 126 → not-executable ("permission or noexec"), no reader · 130 → interrupted, no correction offer and no message presented as an error · 137 → killed by `SIGKILL`, with the OOM-killer hint · 143 → `SIGTERM` · `sudo apt update` with status 1 → privilege-wrapper failure: a fixed message saying the password was wrong or the user may not use sudo, no correction offer, nothing that re-runs sudo, no reader · `pkexec …` with 126 and with 127 → privilege-wrapper failure (pkexec's own codes for a dismissed or refused authentication), not "not executable" / "not found" · `su -c …` with 1 → privilege-wrapper failure · 1, 2, 100, 128 and 255 for an ordinary command → other, and ONLY this class goes to the reader. Plus, each as its own assertion: passing a bare `int` instead of #10's done-record type raises `TypeError`; `inspect.signature` of the classify function has no parameter whose name contains `stderr` or `output`; the classifier module's source text (read from its `__file__`) contains none of `/var/`, `/usr/`, `commands.db`, `ubuntu` (the lookup is defined by the active target's `target.toml`); provider names `HTOP`, `htop; rm -rf ~`, `htop\nevil` and `-htop` from the fake lookup are each dropped (whole-string match, not prefix), while `libc6`, `g++` and `python3.12` are kept; the real `targets/ubuntu-26.04` lookup returns `htop` for `htop` when the local data exists on the host (skip that one test when it doesn't — the binding table uses the fake lookup).
- Repo + branch target: eduralph/nl-shell @ main (built in a later wave than #10 and #92: per `Depends on` the driver folds their accepted patches into the wave's integration branch and verifies against it via `$PDCA_VERIFY_BASE`, so #10's done-record type and #92's target loader exist when this bundle builds; if either is not accepted, this bundle is not scheduled. Use their names as they landed; do not invent stand-ins.)
- Scope (one logical fix) / out of scope: (1) A classifier module under `src/nl_shell/`: input = the session's completion result (#10) plus the confirmed command's parsed command word(s) and the command word that would have been not found; output = the class, the user-facing message (fixed templates, no model), `offer_correction` (false for interrupted and privilege-wrapper failures), `to_reader` (true only for "other"). Precedence: exit 0 → none; privilege wrapper (the confirmed command's first word is `sudo`, `su`, `pkexec` or `doas`) with that wrapper's own failure status (sudo/su/doas: 1; pkexec: 126, 127) → privilege-wrapper failure; then 127, 126, 130, 129–192 (128+n, n = 1…64) → signal n by name; everything else → other. Use the command's last pipeline status as the exit status (bash's `$?`), and keep `PIPESTATUS` available to callers. (2) The command word for the 127 lookup comes from the confirmed command text, never from stderr ("bash: x: command not found" is attacker-shaped text). Until the policy gate (#12) supplies a parse, take the first shell word of the confirmed command with the same no-raise tokenizer the router uses (`router.first_token`, `src/nl_shell/router.py:38-48`); note in a comment that #12's parse replaces it. Because `$?` is the *last* command's status, the first word is only the not-found word for a simple command: when the confirmed text contains `|`, `;`, `&`, a newline, or a backtick/`$(`, or its first word is a leading assignment (contains `=`, see `router.py:9-10`) or a wrapper (`env`, `nohup`, `time`, `nice`, `command`, `exec`, `xargs`), the result is not-found with no suggestion. A confident wrong package is worse than none. (3) A provider lookup defined per target: add a field to `targets/ubuntu-26.04/target.toml` describing the local source (on Ubuntu 26.04: the read-only SQLite database `/var/lib/command-not-found/commands.db`, tables `commands(command, pkgID)` and `packages(pkgID, name)` — checked at Plan on this host, `htop` → `htop`), open it read-only, no network (ADR-0003), and return nothing when the data is absent; extend #92's target loader to validate the field (the target loader only — #77 edits #92's separate `config.toml` unit in the same wave). Validate returned names against the Debian package-name rule with a whole-string match (`re.fullmatch(r"[a-z0-9][a-z0-9+.-]+", name)` — not `re.match`, and not a `$` anchor, which accepts a trailing newline). / out of scope: offering or running a correction (#17); `?why` (#14 route → later); calling the reader (#61); deciding "the gate's parse" (#12); real sudo/su/pkexec behaviour checks (M1 #24, the VM tests #75); localisation of messages (ADR-0022); wiring into the REPL; architecture doc 05 (one docs pass after the batch).

# Adversarial review — issue 62 / failure-classes-by-exit-code

**Evidence.** pytest is not installed in this sandbox, so I could not re-run C4. I judged it from `gate-logs/C4-verify.log`: green 92/92, red 92/92 failed, all with `ModuleNotFoundError`/`AttributeError` from the in-function imports. That is a real red, not a collection error. The tests call the production `classify` with a hermetic temp `$PATH` (`tests/test_failure_classes.py:72-88`), not a copy. To probe the fix I imported `nl_shell.failure_classes` directly with `python3 -I` against `$PDCA_TARGET/src`, using the real ubuntu-26.04 lookup. All six carry-forward items from iteration 1 are addressed and have tests: the `_resolves` PATH check, `NOT_RUN`, the display guard, `"htop\n"`, `"sudo"` in `FAKE_PROVIDERS`, and the ESC/bidi/65-char rows (`tests/test_failure_classes.py:20-31,231,241`).

## Findings

- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:71-76` / `:200-201`: the wrapper check matches only the literal basenames `sudo|su|doas|pkexec`. The reference target's own sudo is reachable under other names. This host has `/usr/bin/sudo-rs`, `/usr/bin/sudoedit` and `/usr/bin/sudoedit-rs` (all point to sudo-rs, which `target.toml` names as the implementation), and `/usr/lib/cargo/bin/su`. Checked: `classify(CommandResult(status=1), "sudo-rs apt update")` → `other`, `to_reader=True`, `offer_correction=True`. `"sudoedit /etc/hosts"` gives the same. So a failed sudo-rs authentication gets a correction offer and goes to the reader, which breaks the ADR-0006 must-hold the class exists to protect. Fix: map `sudo-rs`, `sudoedit`, `sudoedit-rs` (and `su-rs` if it ships) to their wrapper's statuses, and add table rows. The brief's list of four names doesn't stop the builder from covering aliases of the same programs.
- NEEDS-HUMAN [human] — `src/nl_shell/failure_classes.py:199-201`: the brief's "first word is the wrapper" rule misses sudo whenever it is not the first word. Checked, all with status 1 → `other`, `to_reader=True`, `offer_correction=True`: `FOO=1 sudo apt update`, `time sudo apt update`, `env sudo apt update`, `cd /x && sudo apt update`. The worst case is `echo hunter2 | sudo -S apt update`. The confirmed text holds the password, and it becomes a correction candidate (#17) and goes to the reader. The code follows the brief as written, so whether to treat "sudo anywhere in the command" (or anything in `_COMMAND_WRAPPERS` that is followed by sudo) as a wrapper failure is a scope call for the human. `run0` (systemd's polkit wrapper, present at `/usr/bin/run0` on this host) has the same gap.
- NEEDS-HUMAN [human] — `src/nl_shell/failure_classes.py:191-192`: every `ran=False` record becomes `NOT_RUN`, with `is_error=False` and `offer_correction=False`. pty-protocol §4.1 says a *syntax error* also produces D without S. So `if then` or `echo "unterminated` (bash status 2) now gets "No command ran." and no fix offer, though a syntax error is the most fixable failure there is. This fixes the stale-`$?` bug from iteration 1, but it also drops a whole class of real errors. Whether to tell a syntax error apart from an empty line or comment (for example by the confirmed text being blank or `#`-only) is a product decision.
- `src/nl_shell/failure_classes.py:91` / `:271-277`: `(` is not in `_COMPOUND`. So `(htop)` with 127 gives the message `Command not found: (htop).` and `command_word="(htop)"`, which is a wrong word. No package is suggested, since no package is named `(htop)`, so the harm is cosmetic. Adding `(` and `)` to `_COMPOUND` would fix it. Low; not tagged for routing.
- `tests/test_failure_classes.py:454-467`: `test_real_lookup_with_session_path_skips_found_wrapper` passes trivially on a host without command-not-found data, because the lookup returns `()` anyway. It does not skip, so it reads as covered when it isn't. The binding table already covers this case with the fake lookup (`"timeout": ["coreutils"]`), so this is informational.

Things I tried and could not break: escaped or quoted sudo (`\sudo`, `'sudo'`, `/usr/bin/sudo`) is classed as a wrapper failure; `! htop` / `coproc htop` / `{ htop; }` give no suggestion; a tilde, empty or relative `$PATH` entry counts as found (the safe side); RT signals 162-192 get names; `sqlite` errors and missing data return `()`; the `fullmatch` name filter holds.

The C4 claim in `check-gates.json` ("red without the fix (92 of 92 failed), green with it") is supported by the log. I found no unwarranted claim in the gate verdict itself. The gaps above are in coverage, not in the evidence.

# Security review (advisory) — issue 62, failure classes by exit code

Attacker-reachable inputs this diff touches: **session state in the snapshot** (threat model item 4: `PATH`, aliases, functions, disabled builtins, read by `_resolves`). It also reads three inputs the threat model trusts: the exit status and `ran` flag from the control channel, the confirmed command text, and the repo-shipped `target.toml` plus the root-owned `commands.db`. It never reads command output (item 1). The test sets `output=b"bash: htop: command not found\n"` and the signature test pins that.

Rubric: `target/.oss-scanner/threat_model.md` (read in full). I followed `AGENTS.md`. The 12 deferred findings from iteration 1 (`deferred-findings.json`) are not in my inputs, so a finding below may repeat one of them.

## Findings

- NEEDS-HUMAN [human] — **Low** — `src/nl_shell/failure_classes.py:293-298`. **Input:** the confirmed command text (trusted), plus aliases from the session snapshot (item 4, which an attacker can shape through `~/.bashrc` or a sourced script). **Who controls it:** the user, or an attacker-shaped alias. **What goes wrong:** the privilege-wrapper rule looks only at the literal first word. A failed sudo, pkexec or doas run that a wrapper word, a leading assignment or an alias hides is classed `OTHER`: `offer_correction=True`, `to_reader=True`. That is the outcome ADR-0006/0015 and the brief's Motivation say must never happen for a failed authentication. **Seen, by running the patched module:** `env sudo apt update` → 1, `FOO=1 sudo apt update` → 1, `command sudo apt update` → 1 and `time sudo ls` → 1 all give `OTHER True True`. `s apt update` with snapshot alias `alias s='sudo'` gives `OTHER True True`. `nice pkexec x` → 126 gives `NOT_EXECUTABLE`, not a wrapper failure. **Why only Low:** no consumer is wired yet (#17, #61). Any later correction still goes through the gate and a confirm, and sudo passthrough stops capture, so the reader would not get the password. No "must hold" property breaks today. **Why [human]:** the brief defines the rule as "the confirmed command's first word", and #12's parse is meant to replace it. Someone has to decide between two options. (a) Widen it now: the module already has `_COMMAND_WRAPPERS`, the assignment check and the alias parse in `_resolves`, so it could skip leading assignments and wrapper words and expand a snapshot alias before testing for a wrapper (the safe side: it only removes offers). (b) Accept it until #12 and record it as a known gap. Test to add either way: the five commands above with status 1 (126 for pkexec), each expecting `PRIVILEGE_WRAPPER`.

## Checked, no finding

- **Snapshot `PATH` (item 4) → `_resolves`, `failure_classes.py:394-399`.** `word` cannot contain `/` (`_is_simple`, `:369`), so `os.path.join` cannot climb out of a `PATH` entry. Empty or relative entries count as found, which is the safe side. Cost: a 1.7 MB `PATH` of 200k entries took 0.32 s for one 127, and a real record is capped at 1 MiB (`pty_protocol.py:19`). The cost grows with input size, and only one `stat` runs per entry, so I don't count it as resource exhaustion. A crafted `PATH`, alias or function list can only *remove* a suggestion. It cannot change which package is named, because names come from the root-owned database and must pass `re.fullmatch` (`:411`).
- **Alias text injection** (`_ALIAS_LINE`, `:187`). An alias value with an embedded newline and `alias foo=` can make `foo` look like an alias. That only hides a suggestion (the safe side).
- **Display of the confirmed word** (`:301-316`). `isprintable()` rejects ESC, BEL, U+202E and zero-width (Cf, Unicode format characters) code points. The 64-character limit is applied before the word reaches `message` or `command_word`. Tests cover this: `tests/test_failure_classes.py`, `test_unsafe_word_reaches_no_message` (escape, bidi, 65 characters, bell). The `"None"` rendering bug from iteration 1 is fixed: an unsafe word now takes the "not certain" branch.
- **Package names** (`:403-415`). Whole-string match, at most 5 names, no duplicates. `"htop\n"` is now in the bad-name list, so the test can tell `fullmatch` from a `$` anchor.
- **The SQL lookup** (`:427-448`, `targets.py:495-513`). `target.toml` is shipped in the repo and trusted. The path must be absolute, the query must have exactly one `?`, and the word is bound as a parameter, so it cannot inject SQL. The database is opened `mode=ro` with a 1 s timeout and no network (ADR-0003). `test_provider_lookup_reads_sqlite_read_only` shows that a writing query fails. A missing file is never created (`test_provider_lookup_without_data_returns_nothing`).
- **Stale `$?`** (`:285-286`). `ran=False` now gives `NOT_RUN` before any status is read, so a stale 127 or 1 from an earlier command can no longer produce "not found" or a reader send. Covered by `test_nothing_ran_is_not_classed`.
- **First word under sudo** (`:175-177`). `sudo frobnicate` → 127 gives no suggestion, and `FAKE_PROVIDERS` now knows `sudo`, so the test would catch the exclusion being removed.
- **Gates.** C4 shows red without the fix (92 of 92 failed) and green with it. T3: 573 passed. T2 says no security-relevant path was touched. That fits: the module is not wired into the REPL, the gate or passthrough.

Nothing else found. The one finding is advisory and Low.
