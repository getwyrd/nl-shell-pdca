# Security review (advisory) — issue 62, failure classes by exit code

Attacker-reachable inputs this diff touches: **session state in the snapshot** (threat model item 4: `PATH`, aliases, functions, disabled builtins, read by `_resolves`). It also reads three inputs the threat model trusts: the exit status and `ran` flag from the control channel, the confirmed command text, and the repo-shipped `target.toml` plus the root-owned `commands.db`. It never reads command output (item 1). The test sets `output=b"bash: htop: command not found\n"` and the signature test pins that.

Rubric: `target/.oss-scanner/threat_model.md` (read in full). I followed `AGENTS.md`. The 12 deferred findings from iteration 1 (`deferred-findings.json`) are not in my inputs, so a finding below may repeat one of them.

## Findings

- NEEDS-HUMAN [human] — **Low** — `src/nl_shell/failure_classes.py:293-298`. **Input:** the confirmed command text (trusted), plus aliases from the session snapshot (item 4, which an attacker can shape through `~/.bashrc` or a sourced script). **Who controls it:** the user, or an attacker-shaped alias. **What goes wrong:** the privilege-wrapper rule looks only at the literal first word. A failed sudo, pkexec or doas run that a wrapper word, a leading assignment or an alias hides is classed `OTHER`: `offer_correction=True`, `to_reader=True`. That is the outcome ADR-0006/0015 and the brief's Motivation say must never happen for a failed authentication. **Seen, by running the patched module:** `env sudo apt update` → 1, `FOO=1 sudo apt update` → 1, `command sudo apt update` → 1 and `time sudo ls` → 1 all give `OTHER True True`. `s apt update` with snapshot alias `alias s='sudo'` gives `OTHER True True`. `nice pkexec x` → 126 gives `NOT_EXECUTABLE`, not a wrapper failure. **Why only Low:** no consumer is wired yet (#17, #61). Any later correction still goes through the gate and a confirm, and sudo passthrough stops capture, so the reader would not get the password. No "must hold" property breaks today. **Why [human]:** the brief defines the rule as "the confirmed command's first word", and #12's parse is meant to replace it. Someone has to decide between two options. (a) Widen it now: the module already has `_COMMAND_WRAPPERS`, the assignment check and the alias parse in `_resolves`, so it could skip leading assignments and wrapper words and expand a snapshot alias before testing for a wrapper (the safe side: it only removes offers). (b) Accept it until #12 and record it as a known gap. Test to add either way: the five commands above with status 1 (126 for pkexec), each expecting `PRIVILEGE_WRAPPER`.

## Checked, no finding

- **Snapshot `PATH` (item 4) → `_resolves`, `failure_classes.py:394-399`.** `word` cannot contain `/` (`_is_simple`, `:369`), so `os.path.join` cannot climb out of a `PATH` entry. Empty or relative entries count as found, which is the safe side. Cost: a 1.7 MB `PATH` of 200k entries took 0.32 s for one 127, and a real record is capped at 1 MiB (`pty_protocol.py:19`). The cost grows with input size, and only one `stat` runs per entry, so I don't count it as resource exhaustion. A crafted `PATH`, alias or function list can only *remove* a suggestion. It cannot change which package is named, because names come from the root-owned database and must pass `re.fullmatch` (`:411`).
- **Alias text injection** (`_ALIAS_LINE`, `:187`). An alias value with an embedded newline and `alias foo=` can make `foo` look like an alias. That only hides a suggestion (the safe side).
- **Display of the confirmed word** (`:301-316`). `isprintable()` rejects ESC, BEL, U+202E and zero-width (Cf, Unicode format characters) code points. The 64-character limit is applied before the word reaches `message` or `command_word`. Tests cover this: `tests/test_failure_classes.py`, `test_unsafe_word_reaches_no_message` (escape, bidi, 65 characters, bell). The `"None"` rendering bug from iteration 1 is fixed: an unsafe word now takes the "not certain" branch.
- **Package names** (`:403-415`). Whole-string match, at most 5 names, no duplicates. `"htop\n"` is now in the bad-name list, so the test can tell `fullmatch` from a `$` anchor.
- **The SQL lookup** (`:427-448`, `targets.py:495-513`). `target.toml` is shipped in the repo and trusted. The path must be absolute, the query must have exactly one `?`, and the word is bound as a parameter, so it cannot inject SQL. The database is opened `mode=ro` with a 1 s timeout and no network (ADR-0003). `test_provider_lookup_reads_sqlite_read_only` shows that a writing query fails. A missing file is never created (`test_provider_lookup_without_data_returns_nothing`).
- **Stale `$?`** (`:285-286`). `ran=False` now gives `NOT_RUN` before any status is read, so a stale 127 or 1 from an earlier command can no longer produce "not found" or a reader send. Covered by `test_nothing_ran_is_not_classed`.
- **First word under sudo** (`:175-177`). `sudo frobnicate` → 127 gives no suggestion, and `FAKE_PROVIDERS` now knows `sudo`, so the test would catch the exclusion being removed.
- **Gates.** C4 shows red without the fix (92 of 92 failed) and green with it. T3: 573 passed. T2 says no security-relevant path was touched. That fits: the module is not wired into the REPL, the gate or passthrough.

Nothing else found. The one finding is advisory and Low.
