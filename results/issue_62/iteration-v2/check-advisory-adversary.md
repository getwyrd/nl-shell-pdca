# Adversarial review — issue 62 / failure-classes-by-exit-code

**Evidence.** pytest is not installed in this sandbox, so I could not re-run C4. I judged it from `gate-logs/C4-verify.log`: green 92/92, red 92/92 failed, all with `ModuleNotFoundError`/`AttributeError` from the in-function imports. That is a real red, not a collection error. The tests call the production `classify` with a hermetic temp `$PATH` (`tests/test_failure_classes.py:72-88`), not a copy. To probe the fix I imported `nl_shell.failure_classes` directly with `python3 -I` against `$PDCA_TARGET/src`, using the real ubuntu-26.04 lookup. All six carry-forward items from iteration 1 are addressed and have tests: the `_resolves` PATH check, `NOT_RUN`, the display guard, `"htop\n"`, `"sudo"` in `FAKE_PROVIDERS`, and the ESC/bidi/65-char rows (`tests/test_failure_classes.py:20-31,231,241`).

## Findings

- NEEDS-HUMAN [impl] — `src/nl_shell/failure_classes.py:71-76` / `:200-201`: the wrapper check matches only the literal basenames `sudo|su|doas|pkexec`. The reference target's own sudo is reachable under other names. This host has `/usr/bin/sudo-rs`, `/usr/bin/sudoedit` and `/usr/bin/sudoedit-rs` (all point to sudo-rs, which `target.toml` names as the implementation), and `/usr/lib/cargo/bin/su`. Checked: `classify(CommandResult(status=1), "sudo-rs apt update")` → `other`, `to_reader=True`, `offer_correction=True`. `"sudoedit /etc/hosts"` gives the same. So a failed sudo-rs authentication gets a correction offer and goes to the reader, which breaks the ADR-0006 must-hold the class exists to protect. Fix: map `sudo-rs`, `sudoedit`, `sudoedit-rs` (and `su-rs` if it ships) to their wrapper's statuses, and add table rows. The brief's list of four names doesn't stop the builder from covering aliases of the same programs.
- NEEDS-HUMAN [human] — `src/nl_shell/failure_classes.py:199-201`: the brief's "first word is the wrapper" rule misses sudo whenever it is not the first word. Checked, all with status 1 → `other`, `to_reader=True`, `offer_correction=True`: `FOO=1 sudo apt update`, `time sudo apt update`, `env sudo apt update`, `cd /x && sudo apt update`. The worst case is `echo hunter2 | sudo -S apt update`. The confirmed text holds the password, and it becomes a correction candidate (#17) and goes to the reader. The code follows the brief as written, so whether to treat "sudo anywhere in the command" (or anything in `_COMMAND_WRAPPERS` that is followed by sudo) as a wrapper failure is a scope call for the human. `run0` (systemd's polkit wrapper, present at `/usr/bin/run0` on this host) has the same gap.
- NEEDS-HUMAN [human] — `src/nl_shell/failure_classes.py:191-192`: every `ran=False` record becomes `NOT_RUN`, with `is_error=False` and `offer_correction=False`. pty-protocol §4.1 says a *syntax error* also produces D without S. So `if then` or `echo "unterminated` (bash status 2) now gets "No command ran." and no fix offer, though a syntax error is the most fixable failure there is. This fixes the stale-`$?` bug from iteration 1, but it also drops a whole class of real errors. Whether to tell a syntax error apart from an empty line or comment (for example by the confirmed text being blank or `#`-only) is a product decision.
- `src/nl_shell/failure_classes.py:91` / `:271-277`: `(` is not in `_COMPOUND`. So `(htop)` with 127 gives the message `Command not found: (htop).` and `command_word="(htop)"`, which is a wrong word. No package is suggested, since no package is named `(htop)`, so the harm is cosmetic. Adding `(` and `)` to `_COMPOUND` would fix it. Low; not tagged for routing.
- `tests/test_failure_classes.py:454-467`: `test_real_lookup_with_session_path_skips_found_wrapper` passes trivially on a host without command-not-found data, because the lookup returns `()` anyway. It does not skip, so it reads as covered when it isn't. The binding table already covers this case with the fake lookup (`"timeout": ["coreutils"]`), so this is informational.

Things I tried and could not break: escaped or quoted sudo (`\sudo`, `'sudo'`, `/usr/bin/sudo`) is classed as a wrapper failure; `! htop` / `coproc htop` / `{ htop; }` give no suggestion; a tilde, empty or relative `$PATH` entry counts as found (the safe side); RT signals 162-192 get names; `sqlite` errors and missing data return `()`; the `fullmatch` name filter holds.

The C4 claim in `check-gates.json` ("red without the fix (92 of 92 failed), green with it") is supported by the log. I found no unwarranted claim in the gate verdict itself. The gaps above are in coverage, not in the evidence.
