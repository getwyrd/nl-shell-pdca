# Security review (advisory): persistent-bash-session-core

Attacker-reachable inputs this diff touches: **session state** (threat model "Where untrusted input enters" item 4: key bindings, shell options, traps set by `~/.bashrc`, raw `\cmd` input or a confirmed `source` of a repository script), **command output** on the PTY (item 1), and **the model's proposal as the bytes pasted** (item 5, through `check_command`).

All three findings below are live reproductions against the patched tree. I ran them on host bash 5.3.9 with the system `ptyprocess`, a temporary HOME and `Session.start(env=…)`. Each one needs one earlier confirmed session-altering step. That makes it close to the Known gap "Confirmed code can subvert the session's hooks on purpose". But that bullet lists what nl-shell does detect, and none of these three mechanisms is on the list or in `H`. In each case the session stays **healthy** while what runs or what is reported is wrong. So this patch reaches past the gap; it does not just sit inside it.

- NEEDS-HUMAN [impl] — **Medium** (scale: "the session doesn't enter degraded mode when its hooks were changed"; it enables the **Critical** "the command that runs differs from the one the user confirmed"). `src/nl_shell/session.py:120-123` (the `H` record) covers only the bracketed-paste *variable* (`bind -v`), not the key *bindings* readline (bash's line editor) uses to accept the pasted line. `session.py:410` ends every paste with `CR`, so whatever `\r` is bound to runs after the confirmed bytes. Who controls it: anyone who gets one `bind` line into the session (a sourced repository script, `~/.inputrc`, `~/.bashrc`). Reproducer: `run(r'''bind '"\r": " ; touch MARK_CR\n"' ''')`, then `run("echo hello")` → the result is `ran True, status 0, output 'hello\n'`, the session is **not degraded**, and `MARK_CR` exists. The snapshot has no field for bindings either, so the later policy gate (#12) can't see this change. A related case: binding `"\e[200~"` (the paste-start sequence) to a macro runs the macro, and the session degrades only *after* the injected command has run. Fix: add to `H` the bindings §5 depends on, for example `builtin bind -q accept-line`, `builtin bind -q bracketed-paste-begin`, plus `bind -s`/`bind -X` output, or at least the lines for `\r`, `\n` and `\e[200~`. Then add both reproducers as tests. If the human instead decides this belongs in the Known gap, the gap bullet should name key bindings explicitly.

- NEEDS-HUMAN [impl] — **Medium** (same rule, and the same Critical effect: what runs differs from what was confirmed). `session.py:82` turns history expansion off once (`set +H`), but neither `H` (`session.py:115-123`) nor any other record checks that it stays off. The threat model's "What must hold" names "no history expansion" as part of byte-for-byte execution. Who controls it: a confirmed `set -H` or a sourced script, which can also plant entries with `history -s` (`HISTFILE` is unset, but in-memory history is still on). Reproducer: `run("history -s 'touch MARK_H'; set -H")`, then `run('echo "x!t"')` → bash runs `echo "xtouch MARK_H"` (the expanded line shows up in the output), with status 0 and the session healthy. Any later confirmed command containing `!!`, `!$` or `!word` gets rewritten silently. Fix: add `[[ $- == *H* ]]` (or `builtin set -o | …histexpand`) to the `H` text, and add the reproducer as a test.

- NEEDS-HUMAN [impl] — **Medium** (scale: "the session doesn't enter degraded mode when its hooks were changed"). The decision-5 path (`pty_protocol.py:241-244`, `session.py:485-489`) reports "nothing ran" with the output thrown away whenever `S` is missing. Last round's fix added `__nls_ps0` to `H` (`session.py:115`). But `__nls_done` unsets `__nls_ps0` *before* it builds `H` (`session.py:103`), so code that runs after the snapshot can set it again and stay invisible. A DEBUG trap does this: it fires before `__nls_started=1` in `PROMPT_COMMAND`, after `E`. Reproducer: `run("trap '__nls_ps0=$__nls_seq' DEBUG")`, `run("true")`, then `run("touch …/ran_marker; echo printed; (exit 7)")` → `ran False, status 7, output '', degraded False`, and the marker file exists. A command that ran is reported as not run, with its output (attacker-controlled text that the taint logic, #11, will need to see) hidden. The session stays healthy. A user hook in `__nls_user_pc` that calls a function a later `source` redefines gets the same result. The existing test `tests/test_session.py:325-343` only covers a DEBUG trap that *cuts the snapshot short*, which already fails closed. Fix options: (a) add `builtin trap -p DEBUG` to `H`; (b) have the `PS0` check compare against a value no post-`E` code can predict, rather than a variable the user can assign; or (c) degrade when `D` without `S` arrives for a command whose text isn't blank, a comment, or a syntax error. (c) can't be decided without parsing, so (a) or (b) is the realistic fix. Add the reproducer as a test.

## Checked, no finding

- `check_command` (`pty_protocol.py:139-153`): ESC, C0 except TAB/LF, and `ESC [201~` are refused before anything is written (`session.py:397` runs before any write). DEL and C1 characters encoded as UTF-8 pass, but inside a bracketed paste readline inserts them as text, so no finding.
- Printed text forging records: fd 3 is a pipe that only bash and its children hold. A child writing to it is a Known gap. Records with `\r`, bad escapes, oversized records (`MAX_RECORD`) and over-long numbers (`\d{1,18}`) degrade instead of raising.
- PTY output delimiting (`session.py:192-227`): the `ESC[?2004l` search runs only before the line is accepted, and the echoed paste can't contain ESC, so command output can't move the start of the capture window. Capture is bounded (`MAX_OUTPUT`).
- Resource exhaustion: I tried four background `yes` floods (`for i in 1 2 3 4; do yes … & done; sleep 0.5`). The run returned in 0.5 s with output capped at 1 MiB, and the next `true` returned in 0.2 s. No hang or unbounded growth.
- Secrets: nothing is logged. The rcfile is written to a fresh temporary directory (created with mode 0700) and removed after start-up.
- No other finding.
