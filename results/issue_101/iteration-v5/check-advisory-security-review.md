# Security review (advisory): issue 101 / persistent-bash-session-core

**Attacker-reachable inputs this diff touches:** session state (threat model "Where untrusted input enters" item 4: traps, aliases, functions, builtins and hooks set by a confirmed command, a sourced script or `~/.bashrc`) and programs the session runs (Table B: terminal settings, fds, signals). Command output (item 1) reaches only the output capture (`_Output`). The confirmed command text is trusted, but whether it runs byte for byte (I1) is the property under test.

Grounding: `$PDCA_TARGET` is checked out at `8c95e05` (the stale stack-base). `src/nl_shell/session.py` and `src/nl_shell/pty_protocol.py` do not exist there, so the `path:line` references below point into the patch's new files (post-image line numbers). I took the two new modules out of `patch.diff` into this sandbox and ran them against the host's bash 5.3.9 with the system `ptyprocess`. Both findings below reproduce live. The scripts are `scripts/r2.py` and `scripts/r3.py` in this run's sandbox.

## Findings

- NEEDS-HUMAN [impl] — **Critical on the threat model's scale (the command that runs differs from the one confirmed). It also breaks I1 and the Table A row "Traps DEBUG/RETURN: detect, in H".** `src/nl_shell/session.py:211` (PROMPT_COMMAND passes `"$(\builtin trap -p DEBUG RETURN)"` with stderr not captured) and `session.py:188` (`traps %s` in H). **Input:** a confirmed command (or a script it sources) that sets session state. **What goes wrong:** `enable -n trap` makes `builtin trap -p` fail ("not a shell builtin"). Its error goes to the PTY, not into H, so `$2` is empty and H's `traps ` line matches the baseline. A DEBUG trap set in the same command stays installed and runs before every simple command of every later confirmed command, and the session stays healthy. T is also reported as `''`. **Reproducer (ran live):** `run("trap 'builtin printf \"%s\\n\" \"$BASH_COMMAND\" >> LOG' DEBUG; enable -n trap")` then `run("echo hello; rm -f /nonexistent-demo")`. Both return `ran=True`, `degraded=False`, and LOG contains `echo hello` and `rm -f /nonexistent-demo`, so the payload ran before each confirmed word. No `extdebug` or `functrace` is needed. **Fix direction:** the trap text H depends on must fail closed. Capture stderr into the argument (`"$(\builtin trap -p DEBUG RETURN 2>&1)"`, likewise for T). Or put the enabled/disabled state of every builtin the hooks call (`trap`, `printf`, `read`, `declare`, `bind`, `shopt`, `compgen`, `alias`, `jobs`, `enable`, `eval`, `set`) into H. Add a test that runs `enable -n trap` together with a marker-touching DEBUG trap; `tests/test_session.py` has no `enable -n` case at all, so the patch's tests only cover the direct `trap ':' DEBUG` path.

- NEEDS-HUMAN [human] — **High on the threat model's scale ("a session change (alias, function, hook) goes undetected by the gate"), deferred to the gate.** `session.py:164-172` (`F` from `compgen`, `L` from `alias -p`, `J` from `jobs -ps`, all with stderr not captured). **Input:** a confirmed command or sourced script. **What goes wrong:** disabling the builtin a snapshot field is built from turns that field into an empty, healthy-looking value. Aliases and functions defined before the disable still work. **Reproducer (ran live):** `run("alias ls='touch MARK2 #'; enable -n alias")` gives `L == ''`, `B == 'enable -n alias'`, not degraded. The next `run("ls")` creates MARK2. `evil(){ :; }; enable -n compgen` likewise gives `F == ()`. A gate that resolves `ls` against L would class it read-only and run it without a confirm. B does show the disabled builtin, and Table A puts disabled builtins in "reported for the gate (#12), not a session degrade". So a human should decide whether "B is honest" is enough, or whether the session must make F/L/T/J fail loudly (the same `2>&1` change as above, or degrade). The brief's (l) says the snapshot must stay "honest", and today an empty L is not.

- NEEDS-HUMAN [impl] — **Docs accuracy, no severity of its own.** Patched `.oss-scanner/threat_model.md:182-189`, the new Known-gaps bullet. It says a DEBUG trap that gets around the hooks "needs `extdebug` and `functrace`", and that nl-shell detects "accidental and indirect changes … not every deliberate way around them". The first finding shows a hidden DEBUG trap that needs neither. The closing sentence is also wider than brief decision 2 allows ("code comments must not claim more than these": `enable -f` and functions named `builtin`/`command`/`local`/`return`). Either fix the code (preferred) or name `enable -n` here explicitly. A broad catch-all sentence should not quietly cover it.

## Checked, no finding

- **Paste filtering** (`pty_protocol.py:147-161`): refuses ESC, `ESC [201~` and every C0 byte except TAB/LF, before anything is written (`session.py:595`). DEL and bytes ≥ 0x80 go into the paste, where readline inserts them literally, and `convert-meta` is in H through `bind -v`. No finding.
- **Record parser** (`pty_protocol.py:123-144`, `204-222`): bounded at 1 MiB, numeric fields capped at 18 digits, CR rejected, unknown types ignored, any parse error degrades. No hang or crash reachable from fd 3 beyond the existing fd-3 Known gap (#135).
- **Disabling other hook builtins** (`printf`, `read`, `declare`, `bind`, `shopt`): each ends in degraded mode, either through the prompt rule, the check point at `session.py:747-750`, or error text captured inside H's `2>&1` at `session.py:203`. Only `trap` (H) and `compgen`/`alias`/`jobs` (gate fields) fall outside that capture.
- **End-marker token** (`session.py:227-233`, `_Output`): a command can learn it from `declare -f __nls_done` and end its own captured output early. That only hides the attacker's own output from capture. Status still comes from fd 3. No finding.
- **Outside checks against a racing background program** (`session.py:605-608`, `758-770`): the termios check is a single sample taken just before the `os.write`. A background job that ignores SIGTTOU, or one in its own session that reopens `/dev/pts/N`, could flip `stty intr '['` on and off and hope the paste lands in the gap. For example, `[ -e keep ] || rm -rf cache` would then run as `-e keep ] || rm -rf cache`. I could not show the window is wide enough to matter and did not reproduce it. It is built into the sampled-check design of decision 8, and code that stays running after its command ends sits close to the threat model's "code already running as the user" exclusion. I note it here rather than file it.
- **Not checked:** I did not run `tests/test_session.py`. C4 failed on the worktree mismatch (the patch was applied to the stale `8c95e05`, not `c47c5c2`). That is the gate's problem, not a security finding.
