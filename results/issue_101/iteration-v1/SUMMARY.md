# Adversarial review: persistent-bash-session-core

**Evidence.** The red→green proof holds up. `gate-logs/C4-verify.log` shows 55 of 55 tests failing with the fix reverted (`ModuleNotFoundError` in each test, because the session module is imported inside each test as the brief requires) and all passing with it. T3 has the full suite green (232 passed). The tests drive the real `Session` against real bash 5.3.9, not a copy of it. I could not re-run pytest here (it is not installed in this sandbox), so I drove `nl_shell.session.Session` directly with python3 + ptyprocess 0.7.0 + bash 5.3.9. Every probe below is a live run against the patched tree in `$PDCA_TARGET`.

**What I tried and could not break:** the ESC / C0 / `ESC [201~` refusal (`src/nl_shell/pty_protocol.py:139-153` runs before any write, `session.py:368`); printed fake `D` records; losing output in the gap between the PTY and the `D` record (300 × `echo hiN` plus outputs of 5 KB, 70 KB and 300 KB were all captured exactly); `PS0=` hidden as not-run; and how `set -e` is handled (it degrades with "the shell exited", which is correct).

- NEEDS-HUMAN [impl] — `src/nl_shell/session.py:425`: the back-at-a-prompt check only runs while `done is None`. If the snapshot is cut off after `D`, nothing degrades, and `run()` with its default `timeout=None` (`session.py:361`) **hangs forever**. Concrete case: `run("set -u; unset PATH")`. The control channel delivers `S 1, D 1, F, L, T, B, X`, then bash aborts `PROMPT_COMMAND` on `"$PATH"` (`session.py:103`, rcfile `__nls_enc P "$PATH"`) under nounset. No `P/J/H/V/E` ever arrives, bash goes back to its prompt, and the call never returns (confirmed: killed by `timeout 15`; with `timeout=4` it gives `SessionTimeout`, and the records stop after `X`). Spec §4.2 trigger 1 ("a record is missing") is not enforced for snapshot records. Fix: keep the foreground-group timer running until `E`, not just until `D`, and make the rcfile safe under `set -u` (`${PATH-}`). Add a test for `set -u; unset PATH`. The suite misses this because every test passes an explicit timeout (`tests/test_session.py:82`).
- NEEDS-HUMAN [impl] — `src/nl_shell/session.py:125,189-198`: the command's output is found only by looking for readline's `ESC[?2004l` on the PTY. A confirmed command can turn that marker off, and every later result then has `output == b""` while the session still reports healthy. Concrete cases (live): `bind 'set enable-bracketed-paste off'` then `echo hello` → `ran True, status 0, output ''`. Same with `TERM=dumb` then `echo hello`. The rcfile only forces bracketed paste on once, after `~/.bashrc` (`session.py:76`), and the test (h) only covers the `.bashrc` case. Output silently disappearing without a degrade goes against "never from printed text… output between S and D". Either degrade when `S` arrives but the marker never shows up, or capture from `S` onward.
- NEEDS-HUMAN [human] — `src/nl_shell/session.py:381`: after `set +o emacs` (readline off), bash no longer treats the bracketed-paste markers as markers, so they become part of the command text. Live: `set +o emacs` then `echo hello` → `status 127, output ''`, session not degraded. Bash ran `\e[200~echo hello\e[201~`, not the confirmed bytes, and that breaks the brief's "sends exactly the confirmed bytes" (§5). For a multi-line paste, the second and later lines run as typed while the first line is mangled. Nothing in `H`/`X` watches the line-editing state. Deciding whether this is a §4.2 trigger (add `set -o` / `bind -v` state to `H`) or a Known gap is a spec/scope call.
- NEEDS-HUMAN [impl] — `src/nl_shell/session.py:355-359`: `interrupt()` writes `\x03` whatever state the session is in. Ctrl-C at an idle prompt makes bash run `PROMPT_COMMAND` again, which sends a stray `D`, and the session is degraded for good. Live: `interrupt()` while idle → `control record 'D' arrived out of order (while no command was running)`. The same race happens if Ctrl-C lands just after a command finishes. Test (b) vector 10 (`tests/test_session.py:188-212`) only presses Ctrl-C 0.3 s into `sleep 5`, so this case is never exercised. child-2 will forward real keystrokes, so either refuse or ignore `interrupt()` when no command is in flight, or document it as a fail-closed limit.
- Minor (not NEEDS-HUMAN) — `src/nl_shell/session.py:199-203`: after `stty -echo`, `echo hello` captures `'\nhello\n'`. The single-CR skip assumes readline's echo layout, so `output` can pick up an extra leading newline when echo is off.
- Reviewer claim I'd question: the C4/T3 "pass" rows prove the tested behaviour. They do not back up a reading that the session is "fail-closed on every §4.2 trigger". The first bullet above shows a §4.2 "record missing" case that neither degrades nor returns.

# Advisory security review — persistent-bash-session-core

Attacker-reachable inputs this diff touches: the command bytes sent to the PTY (threat model "Where untrusted input enters" item 5, the model's proposal, after confirm), session state (item 4: termios, variables, aliases, functions set by `~/.bashrc` or a confirmed `source`), and PTY output (item 1), which `_Output` captures.

Both findings below were reproduced on the host (bash 5.3.9, system `ptyprocess`) by driving the patched `Session` with small scripts in this sandbox (`probe/p2.py`, `probe/p3.py`).

- NEEDS-HUMAN [human] — **Critical (the command that runs differs from the one the user confirmed), but only after an earlier confirmed termios change** — `src/nl_shell/pty_protocol.py:148-153`, `src/nl_shell/session.py:381`. The §5 guard only refuses ESC, C0 controls and `ESC [201~`. It assumes the PTY's termios special characters (termios: the terminal's line settings; e.g. the interrupt key) are still their C0 defaults. Readline leaves ISIG (the terminal turning keys into signals) on. So once the session has run `stty intr '|'` (typed, from a cloned repo's `~/.bashrc` or env script that the user confirmed `source`-ing, or a confirmed proposal), every `|` in a later confirmed command reaches the line discipline as SIGINT, not as text. Readline drops the line typed so far, and whatever follows the last `|` runs. Reproducer: `run("stty intr '|'")`, then `run("true || touch never_confirmed_to_run")`. The confirmed command can never create a file. In the probe it created `never_confirmed_to_run~` (the trailing `~` is the leftover from `ESC [201~` once the paste was cut). It was reported `ran=True, status=0`, and the session stayed healthy. Nothing in the snapshot (§3) records termios, so neither H nor V changes. The same flaw makes `interrupt()` (`session.py:359`) silently do nothing after `stty intr` moves away from `^C`. Fix options: before each write, read the line settings with `os.tcgetattr` on the master and refuse (or degrade) if any active VINTR/VQUIT/VSUSP character (or VLNEXT/VDISCARD under IEXTEN, the extended-input flag) appears in the command; or record those settings in the baseline and degrade when they change. Either one widens spec §5.2 or §3 beyond what the brief settled, so a human should pick which. Add the reproducer above as a test.

- NEEDS-HUMAN [impl] — **Medium (the session doesn't enter degraded mode when its hooks were changed)** — `src/nl_shell/session.py:83,95,107-109`. H covers PS0, PROMPT_COMMAND, `__nls_user_pc` and the hook functions, but not the hook's state variables `__nls_ps0`, `__nls_seq`, `__nls_started` and `__nls_once`. Making one of them readonly breaks the "S once per command" logic without changing H. Reproducer: `run("readonly __nls_ps0=2")`, `run("true")`, then `run("touch m3; echo printed; (exit 7)")`. The third command ran (`m3` exists) but came back as `ran=False` ("nothing ran", §4.1), with status 7, `output=b''` (its output thrown away by `session.py:445`), and the session not degraded. The hook even prints `cannot unset: readonly variable` on every prompt, and nothing acts on it. This sits next to the Known gap "confirmed code can subvert the session's hooks on purpose". But the patch adds the "D without S = healthy not-run" path (decision 5), and this lets a command that did run be reported as not run, which brief item (f) set out to stop for `PS0=`. A cheap fix the builder can make: add `builtin declare -p __nls_seq __nls_started __nls_ps0 __nls_once` (or just their attributes) to H, and/or have `__nls_done` emit a malformed record when `builtin unset __nls_ps0` fails. Add the reproducer as a test.

- NEEDS-HUMAN [impl] — **Low (comment claims more than the code does; brief decision 2 says comments must not)** — `src/nl_shell/session.py:64-65` says the hooks "call builtins through `builtin`, so … a function named like a builtin they use does not change them". But `local` (`:86`, `:93`) and `return` (`:84`, `:114`) are called bare, so a function named `local` or `return` changes how the hooks behave. In the cases I tried, the damage was a malformed `D` record, which fails closed. Either route those calls through `builtin` where bash allows it, or reword the comment to name the exceptions.

Checked, no finding:
- Printed text can't forge records. Records come only from fd 3 (`session.py:288-311`). Brief vectors 4–5 are covered by tests, and C4/T3 pass in `gate-logs/`.
- `parse_record` rejects CR, records over 1 MiB, bad escapes and numbers longer than 18 digits, and degrades instead of raising (`pty_protocol.py:117-136`, `:217-221`).
- Captured output is capped (`session.py:205-208`).
- The rcfile is in a `mkdtemp` (0700) directory and is removed after the baseline (`session.py:284`, `:324`).
- `HISTFILE` is unset and history expansion is off (`set +H`) in the rcfile (`:74-75`).
- The `ESC [?2004l` output boundary can't be shifted by the command's own bytes, because ESC is refused.
- DEL (0x7f) and non-ASCII bytes pass inside the paste unchanged, as long as termios is at its defaults. The first finding covers the case where it isn't.
- Test coverage: the forbidden-byte tests are on the attacker-reachable path. Neither reproducer above is covered.
