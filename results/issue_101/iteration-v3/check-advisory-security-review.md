# Security review (advisory): persistent-bash-session-core, iteration 3

Attacker-reachable inputs this diff touches: **session state** (threat model input 4: aliases, functions, traps, `PS0`/`PS1`/`PROMPT_COMMAND`, readline bindings and settings, set by `~/.bashrc`, raw `\cmd` or a confirmed `source` from a cloned repo) and **command output** (input 1: PTY bytes and anything a command writes, including fake control records). The confirmed command bytes are trusted, but the §5 refusal check on them is security-relevant.

Every finding below was reproduced on the host (bash 5.3.9, system `ptyprocess`) by driving `nl_shell.session.Session` from `$PDCA_TARGET/src`. The scripts are in this sandbox under `scratch/`.

## Findings

- NEEDS-HUMAN [human] — **Medium** ("the session doesn't enter degraded mode when its hooks were changed"). It also hides command output from the later taint logic (#11). `src/nl_shell/session.py:98`, `:143`, `:121-124`; `src/nl_shell/pty_protocol.py:241-244`; `src/nl_shell/session.py:501`. This round fixed the DEBUG-trap and user-hook versions of last round's finding: `__nls_ps0=` is now the last command of `PROMPT_COMMAND` (`session.py:143`), and I confirmed the DEBUG-trap reproducer now gives `ran True` with its output. But `PS1` is expanded *after* `PROMPT_COMMAND`, and with `promptvars` on (forced at `session.py:93`), an array subscript in `PS1` is evaluated in the shell itself. That is the same trick `PS0` uses at `:98`. So `PS1` can set `__nls_ps0` again after the reset. `H` keeps only the attributes of `__nls_ps0`, not its value (`:122-124`), and `PS1` is in no record, so nothing changes in any snapshot.
  - **Who controls it:** anyone who can put one `PS1=` line into the session: a sourced repo script, `~/.bashrc`, or a confirmed command. `PS1` changes are common (venv `activate` sets one), so the gate is unlikely to treat this line as special.
  - **Reproducer:** `run(r"""PS1='${__a[__nls_ps0=__nls_seq]-}\$ '""")`, then `run("true")`, then `run("touch …/marker_PS1; echo printed; (exit 7)")`. The last call returned `ran False, status 7, output '', degraded False`, and the marker file exists. Every later command is reported as "nothing ran" (§4.1), with its output thrown away, and the session stays healthy.
  - **Why this needs a human:** the threat model's new Known-gaps bullet (`.oss-scanner/threat_model.md:177`) names "a `PS1` that runs code" but says "`H` shows it only at that command's snapshot". For this case that is false: `H` never shows it. Code in `PS1` can read and write anything `PS0` can, so no in-shell variable check can stop it. A human has to pick one of three: (a) put `PS1` (and `PS2`) in `H`, which degrades on every venv activate; (b) treat it as deliberate subversion and fix the Known-gaps text and the `session.py:58-61` comment so they don't claim `H` catches it (brief decision 2: comments must not claim more); or (c) move the "did a command start" signal out of shell variables, for example by having the Python side tell bash's foreground process group apart, or by a `D` field that `PS1` can't predict. If (b), the builder can do the wording as an [impl] follow-up.

## What I checked and found holding

- **The iteration-2 findings are fixed and tested.** Rebinding `\C-m` or `\e[200~` (`tests/test_session.py:524-529`) degrades the session. I also tried prefix bindings (`"\e[2"`, `"\e["`, `"\e"`, `"\e[20"` bound to macros): the paste still arrived intact, nothing injected ran (no marker file), and the session stayed healthy. An `emacs-meta` rebinding of `[200~` degrades through `H`. `set -H` with planted history is detected (`:562`). The DEBUG-trap and user-hook reset of `__nls_ps0` now reports `ran True` with its output (`:501-515`).
- **§5 refusal** (`pty_protocol.py:139-153`): ESC, `ESC [201~` and every C0 byte except TAB/LF are refused before anything is written (`session.py:410` runs before any write). DEL (0x7f) and C1 code points pass through, and they arrived byte for byte inside the paste (`echo p6 \x7f` → `p6 \x7f`). Readline is in non-canonical mode, so the TTY driver does not act on them.
- **The "nothing ran" path cannot hide a multi-line command.** `"# x\ntouch m1"`, `"\ntouch m2"`, `"fi\ntouch m3"`, `"true\n\ntouch m4"` and `"echo a \\\n; touch m5"` all came back as `ran True` with their output. None was misreported as not run.
- **Forged records from output:** status and completion come only from fd 3 (`session.py:445-460`), and output capture starts only after readline's `ESC[?2004l`. The echoed command can't contain ESC, so its echo can't fake that marker. If the marker never arrives, the session now degrades instead of returning empty output (`:451-458`).
- **Parser robustness** (`pty_protocol.py:27-41`, `:115-136`, `:204-205`): digits are capped at 18 and records at 1 MiB, CR is rejected, and bad escapes degrade the session instead of raising. I found no way for attacker-sized input to crash it or make it hang.
- **`interrupt()`** writes only in `Phase.RUNNING` (`session.py:398-400`). A Ctrl-C that races the end of a command fails closed, and the Known gaps bullet says so.
- **Tests:** the patch's tests cover the hostile cases from earlier rounds, not just the normal path. The only hostile case missing is the `PS1` one above.
