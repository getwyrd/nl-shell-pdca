# Adversarial review — persistent-bash-session-core (round 3)

Red→green evidence: `gate-logs/C4-verify.log` shows 76 of 76 failing with the production files reverted (ModuleNotFoundError, since the imports sit inside each test) and 76 passing with them. That proves the tests depend on the new modules. It does not prove they would catch a wrong implementation. I could not re-run pytest here (no pytest outside the gate venv), but `ptyprocess` and bash 5.3.9 are on the host, so I drove `nl_shell.session.Session` directly with scripts in my scratch dir under a temporary HOME. The results below come from those live runs.

- NEEDS-HUMAN [impl] — `src/nl_shell/session.py:98,143` with the claim at `session.py:57-61`: the decision-5 hole is still open, now through `PS1`. The rcfile comment says `__nls_ps0` "is cleared by the last command of PROMPT_COMMAND … so [code] that sets it after `E` is overwritten before the next command is read". That is false. Bash expands `PS1` *after* `PROMPT_COMMAND` (with `promptvars` on, which the rcfile forces at `:93`), and `PS1` is not in `H` (`:121-136`). Live reproducer: `run(r"PS1='${__nls_once[__nls_ps0=__nls_seq]-}\$ '")`, then `run("true")`, then `run("touch MARK; echo printed; (exit 7)")` → `ran False, status 7, output '', degraded False`, and `MARK` exists. Every later command (`echo again`, `true`) also comes back `ran False` with its output thrown away, and the session never degrades. This is the same failure brief item (f) and both earlier rounds' findings were meant to stop: a command that ran is reported as "nothing ran" (§4.1), with its output hidden. The Known-gaps bullet (`.oss-scanner/threat_model.md:176-179`) says a `PS1` change "shows [in `H`] only at that command's snapshot", but here `H` never shows it. The tests at `tests/test_session.py:500-517` cover only the DEBUG-trap and user-hook writers, which the clear-last ordering does beat. Putting `PS1` into `H` would degrade on every virtualenv `activate`, so the fix should remove the shell-side guard instead. For example: emit `S n` on every `PS0` expansion and have the tracker accept repeated `S n` for the same `n`. Or have `__nls_done` check the guard against something post-`E` code cannot set. Add the reproducer as a test.
- NEEDS-HUMAN [impl] — `src/nl_shell/session.py:121-136` (the `H` record) together with `:143`: a DEBUG trap that acts only on the last `PROMPT_COMMAND` command changes `H`-covered state *after* the snapshot. The confirmed command that follows then runs altered before anything degrades. Live: `run(r'''trap '[[ $BASH_COMMAND == __nls_started* ]] && bind '"'"'"\r": " ; touch MARK\n"'"'"' 2>/dev/null' DEBUG''')` → healthy (`ran True, degraded False`). Then `run("true")` → `MARK` is created, and only *then* does the session degrade on `H`. The same trap with `set -H` (after `history -s 'touch MARK'`) turns the next confirmed `echo "x!t"` into `echo "xtouch MARK"` before degrading (the `SessionDegraded.result` output shows the rewritten line). So "the bytes run are the bytes confirmed" (§5) fails for one command. The Known-gaps bullet names the user's `PROMPT_COMMAND`, a function it calls, and `PS1` as post-snapshot code, but not a bare confirmed `trap … DEBUG`, which needs no `source` and no pre-existing hook. Round 2 already suggested the cheap fix: add `builtin trap -p DEBUG` (and `RETURN`, plus `shopt -p extdebug`/`set -o functrace` if those matter) to `H`. Then any DEBUG trap degrades at the snapshot of the command that set it. The other option is to name DEBUG traps explicitly in the Known gap. Either way, add the reproducer.
- NEEDS-HUMAN [human] — `.oss-scanner/threat_model.md:176-179`: the patch now accepts in writing that code running after the snapshot (user `PROMPT_COMMAND`, `PS1`, and per the item above a DEBUG trap) can rebind CR or turn on history expansion so that the *next* confirmed command runs something other than what was confirmed, with `H` catching it only afterwards. The threat model scores "a confirm that shows something other than what runs" as in scope (`threat_model.md:161-162`). Whether one-command-late detection is acceptable for v1, or whether `H` must also be checked just before the paste is sent (for example a fresh check record that `run()` waits for before writing), is a scope call for the human, not the builder.
- Attempted and could not refute: Ctrl-C at idle (`session.py:398` now refuses when not `RUNNING`); `set -u; unset PATH` cutting the snapshot short (`${PATH-}` at `:117`, and the timer runs until `E` at `:477`); output silently empty after bracketed paste is turned off (`:451-458` degrades); a DEBUG trap writing `__nls_ps0` (overwritten by the last `PROMPT_COMMAND` command at `:143`, live-confirmed); a DEBUG trap acting before `__nls_done` (caught in the same snapshot's `H`, live-confirmed). The `check_command` rule (`pty_protocol.py:148-152`) matches §5 as briefed.
