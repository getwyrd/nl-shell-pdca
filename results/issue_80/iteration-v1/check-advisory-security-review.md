# Security review — issue 80 / pinned-tldr-snapshot

**Attacker-reachable inputs touched:** one, the vendored tldr corpus (`data/tldr/pages.jsonl` + `source.json`). The threat model counts this as a supply-chain input: it feeds the #23 harvest and the shipped training data (threat model "Where untrusted input enters" item 10, and the Supply chain attacker row). The `--root` argument is set by the build operator, not an attacker. The README acquisition recipe reads an upstream git archive, which is also supply chain. No runtime path is touched: nothing in `src/` reads tldr, and no command, confirm, sudo or state-block path changes.

Rated on the scale in `.oss-scanner/threat_model.md:338-371`. None of the findings reaches Critical, High or Medium. The reader has no consumer yet.

## Findings

- NEEDS-HUMAN [impl] — **Low (hardening)**, `scripts/tldr_snapshot.py:67`. The input is the corpus records, which a supply-chain editor (or anyone handing over a `--root` snapshot) controls. The export is `dict(record, revision=…, language="en", provenance="local-reference")`, so any extra key in a JSONL record is passed through to the harvest-facing output. The fixed inventory anchor covers only `path` + `content`. `corpus_sha256` (`:38`) is checked against `source.json` in the same directory, so it only shows the two files agree with each other, not that they are the real upstream data. An edited snapshot therefore passes every reader check while carrying fields the future #23 consumer may trust. Example: add `,"trusted":true` (or `"taint":"trusted"`, `"source":"man"`) to one record in a copy of `pages.jsonl`, recompute `corpus_sha256` in the copied `source.json`, then run `python3 scripts/tldr_snapshot.py export --root <copy>`. It exits 0 and emits the extra key. `provenance` itself is correctly overwritten. The shipped-corpus test catches this only for the tracked corpus (`tests/test_tldr_snapshot.py:74`). The reader does not enforce it, and no corruption case at `tests/test_tldr_snapshot.py:106` covers it. Fix: reject any record whose keys are not exactly `{"path","content"}`, require both to be `str`, and add that mutation to the corruption test.

- NEEDS-HUMAN [impl] — **Low (doc accuracy)**, `.oss-scanner/threat_model.md:101`. The old bullet ended "…and the vendored tldr snapshot (local-reference, ADR-0016)". The brief read that label as covering the man pages and `--help` output as well ("already annotating them local-reference"). The patch removes the label together with the tldr clause. Dpkg man pages and `--help` output now appear in the Trusted list with no local-reference label, even though `docs/design/adr/0016-taint-model-v2.md:43` labels them local-reference. The brief asked to keep the man/help wording, not to drop its label. No code depends on this today, but the threat model is the rubric reviewers use, and "untrusted text labelled trusted" is a High outcome on its scale. Fix: keep "(local-reference, ADR-0016)" on the man-page bullet, or say in the new paragraph that the same label applies to it. The new tldr paragraph (`:110-112`) matches ADR-0016:43 and the brief.

- NEEDS-HUMAN [impl] — **Context, not a security defect by itself**, `data/tldr/` (patch). `pages.jsonl`, `source.json` and the upstream `LICENSE.md` are not in the patch. C4 and T3 fail on exactly this (`gate-logs/C4-verify.log`: `No such file or directory: …/data/tldr/source.json`; "real pinned corpus must be shipped"). As a result, the new threat-model text "verified before offline consumption" (`.oss-scanner/threat_model.md:110-111`) refers to a snapshot that does not exist yet, and I could not check the anchor against real bytes. Ship the generated corpus, metadata and license.

## Checked, no finding

- **Integrity anchor:** `INVENTORY`, `LICENSE_BLOB`, the page count and the byte total are hardcoded in the script and again in the test. Both recompute Git blob IDs from the shipped content, not from the manifest's claims. To swap in a forged corpus, an attacker would also have to change the constants in two reviewed files, and that change would be visible in review. All validation finishes before the first output line (`scripts/tldr_snapshot.py:81`), so a bad snapshot prints nothing.
- **Path handling:** paths are never opened or written. The prefix, `.md`, three-part and `..` checks (`:51-54`) are extra hardening. The README's rebuild recipe uses `tarfile.extractfile` only, never `extract`/`extractall`, so there is no path traversal (writing outside the target directory). The upstream archive is pinned to a full commit hash and checked against the fixed anchor before anything is written.
- **No network or process use:** the script imports only `argparse`, `hashlib`, `json`, `pathlib` and `sys`. There is no `ctypes`, `subprocess`, `socket`, `os.system` or dynamic import. The audit-hook test (`tests/test_tldr_snapshot.py`, `WRAPPER`) covers the brief's event list. Its positive controls show the hook fires for both network and process events. Page text with `sudo apt` in it stays as data in the export and is never run.
- **Malformed JSON:** `UnicodeDecodeError`/`JSONDecodeError` are caught as `ValueError`. A record with a non-string `path`/`content` raises an uncaught `AttributeError`. That gives a traceback and exit 1 with no stdout, so it fails closed. This is cosmetic, and the type check suggested in the first finding fixes it too.
- **Resource use:** the reader loads about 4–6 MiB into memory, in proportion to the input. That is fine for a build-time tool.
