# Security review — issue 80 / pinned-tldr-snapshot (round 2)

Attacker-reachable inputs this diff touches: **none.** The patch adds only `tests/test_tldr_snapshot.py`. It ships no `data/tldr/` corpus, no `scripts/tldr_snapshot.py` reader and no `.oss-scanner/threat_model.md` edit (`ls $PDCA_TARGET/data/tldr` → no such directory; `$PDCA_TARGET/scripts/` holds only `build_bash.py`, `docs_checks.py`, `gen_unicode_tables.py`). The one input in the threat model this work would touch is item 10, supply-chain build data (`.oss-scanner/threat_model.md:90-92`), meaning the vendored tldr pages. That input does not exist in this round, so no production code reads attacker-controlled data.

What I checked: the patch's file list (one file); the gate evidence (`gate-logs/C4-verify.log`: "no behavioral production change to revert (test-only or docs-only patch)"; `gate-logs/T3-suite.log`: both new tests fail on assertions, 1331 pass); and the test's own subprocess and audit wrapper. The wrapper runs `sys.executable -c <fixed string> <repo path>`, has no shell and no outside input, and is not a risk. No severity-rated finding exists, because no production path changed.

The bullets below are about the test's value as a **security guard** for the reader that has not shipped yet. The brief asks the test to prove "zero network or process-execution attempts" and to prove that corrupt data is rejected. As written, the test can't prove either.

- NEEDS-HUMAN [impl] — `tests/test_tldr_snapshot.py:56-102` (patch). The brief's audit **positive controls** are gone. The brief (lines 50-52) requires separate children that try a loopback `socket.connect` and a harmless process launch, and show the hook records and blocks both, "so an uninstalled/inactive hook cannot give a vacuous pass". The previous round had `test_audit_positive_controls`; this patch drops it. Without it, the hook could silently stop working and `assert result.stderr == b"[]\n"` would still pass: for example, if an event name were misspelled, or if the reader did its network work through an event outside the set. The concrete check: add a child that runs the same `audit` function and then `socket.create_connection(("127.0.0.1", 9))` and `subprocess.run(["true"])`, and assert that `attempts` holds `socket.connect` and `subprocess.Popen` and that neither call went through.
- NEEDS-HUMAN [impl] — `tests/test_tldr_snapshot.py` (whole file). The test never feeds **corrupt or fabricated data to the reader**. The brief (lines 6-7, 44) requires that corrupt temporary copies are rejected, and that "a fabricated corpus with a recomputed manifest still fails that anchor". `test_real_pinned_snapshot` recomputes the anchor only over the tracked corpus, inside the test. Nothing calls `scripts/tldr_snapshot.py export --root <tmp copy>` on a changed copy and asserts a non-zero exit. A reader with no checks at all would pass this file. Concrete cases to add, each on a `tmp_path` copy and each expecting rejection: (a) change one page's `content`, then recompute that page's manifest entry and the corpus digest in `source.json` (the anchor must still reject it); (b) add an extra key such as `"trusted": true` to one record, then recompute the manifest (the reader must reject any key set other than `{path, content}`, or the future #23 harvest could receive a planted trust label: "untrusted text is labelled trusted" is **High** at `.oss-scanner/threat_model.md:347`); (c) duplicate or drop a path; (d) change `LICENSE.md`.
- NEEDS-HUMAN [impl] — `tests/test_tldr_snapshot.py:61-66` (patch). Minor: the audited event set leaves out `os.fork` and `os.forkpty` (the events `pty.fork` and a bare `os.fork` raise). The brief lists the set with "where emitted", so this is a small hardening step, not a hole the brief demands be closed. Add both to the set, or state in a comment why fork without exec is out of scope.
- NEEDS-HUMAN [impl] — the corpus, reader and threat-model change are **still missing**. This repeats round 1's main finding. C4 is "unverifiable" because no production hunk exists, and T3 fails on `real pinned source must be shipped` and `production export entry point must be shipped`. Until `pages.jsonl`, `source.json`, `LICENSE.md`, `NOTICE.md` and `scripts/tldr_snapshot.py` ship, I can't check the real security questions: does the reader verify before it emits, is the anchor checked against real bytes, and does the reader reject extra keys. If Do had no GitHub HTTPS access to get the pinned revision (brief line 17), a human has to provide that access. If so, re-tag this bullet [human].

No other finding. With no production code in the diff, the round-1 hardening note on `scripts/tldr_snapshot.py:67` (extra keys passed through) and the doc note on the threat model (`.oss-scanner/threat_model.md:101-102`, which is unchanged in this round) do not apply.
