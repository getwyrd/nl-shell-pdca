# Plan advisory — plan-reviewer (issue 80 / pinned-tldr-snapshot)

The problem framing matches the thread. notes.json says: "no issue vendors it … **Done when:** a pinned tldr snapshot is in the repo … with its license and attribution recorded, and the harvest (#23) can include it". The target agrees: Grep finds no `data/tldr` path and no tldr reader, and `scripts/` holds only `build_bash.py`, `gen_unicode_tables.py` and `docs_checks.py`. The target is `getwyrd/nl-shell @ main`, and `Depends on` is empty, which is consistent with the thread. No `sources/` directory or `dependency-state.json` was present. Faults found:

- NEEDS-HUMAN — **The main success clause can't be checked offline, so a fake corpus would pass it.** The brief says the test "verifies a nonempty vendored … snapshot against its recorded immutable upstream revision and content hashes". The patch writes both the revision and the hashes. An offline test can therefore only check that the corpus agrees with its own manifest. It can't check that the content really is tldr-pages@`eacda70…`. A made-up or locally edited corpus with hashes recomputed to match would turn green. The only real check against upstream is moved to "record a real upstream acquisition/integrity comparison in Do's evidence" (Design ¶3), and no gate runs that. Fix: say plainly that the gated check is self-consistency only. Then either pin an external anchor the test can check offline and that Do cannot choose, such as the upstream git tree/blob SHA-1s for `pages/common/tar.md` and `pages/linux/apt.md` (and ideally the `pages/` tree hash) written into the brief now from the Plan-time API check, or name the reviewer step that re-runs the refresh/verify command against GitHub.
- NEEDS-HUMAN — **No mechanism is given to prove the code "neither accesses the network nor executes page examples".** The brief requires this in the success criterion and the repro, but never says how a test would show it. Nothing in `pyproject.toml:34-44` blocks network access (no plugin, no marker). If no mechanism is named, Do can write an assertion that passes no matter what the code does. Name one, for example: run the subprocess with a `sitecustomize`/`sys.addaudithook` that fails on `socket.connect`, `subprocess.Popen` and `os.system`/`exec*`, and add a positive control showing the hook trips.
- NEEDS-HUMAN — **The brief says "never trusted", but the threat model lists the snapshot under "Trusted:".** Brief line 8 says "vendored tldr is local-reference, never trusted". The target's `.oss-scanner/threat_model.md:97-102` puts "the vendored tldr snapshot (local-reference, ADR-0016)" under the **Trusted:** heading. ADR-0016:43 labels it `local-reference`, which is a separate class from `trusted` (:41). Design ¶4 says the brief will "Update the threat model to describe … reference text is data, not executable code or trusted instructions". That edit either reclassifies the snapshot in a security document or contradicts its current wording. That is a security-model decision hidden inside a data-vendoring slice. The brief should either quote the current lines and say exactly what changes (for example, moving it out of "Trusted:" or adding a "local-reference" heading), or leave that edit out.
- NEEDS-HUMAN — **The scope covers four deliverables, not one.** The thread asks only for a pinned snapshot plus license/attribution that #23 "can include". The brief also commits Do to (1) the corpus and metadata, (2) a reader/export CLI with an acquisition/refresh command (`scripts/tldr_snapshot.py`, Design ¶3), (3) a new design proposal `docs/design/proposals/draft/0002-pinned-tldr-snapshot.md` with an index row, and (4) the threat-model edit above. `docs/design/proposals/README.md:9` reserves proposals for "larger changes and milestone plans". A proposal shipped together with its own implementation is a second deliverable, and it adds `docs_checks.py` immutability/status surface. The refresh/acquisition code path is network code, and no gated test can run it offline. Consider dropping the proposal, or making it the only deliverable, and splitting refresh tooling from the read/export path.
- NEEDS-HUMAN — **The brief cites a frozen document as its invariant.** "Invariant to restore" and "Citations expected" rely on `docs/plan.md:21–27,94–99,268`. But `docs/plan.md:3-8` says: "**Historical — frozen on 2026-10-14.** … no longer maintained and already differs from the decisions … The live design is in design/". The live statement of the same invariant is ADR-0003 (`docs/design/adr/0003-locally-complete.md:22-23`), and the brief never cites it. That ADR also says local reference is "harvested at install time", and `docs/plan.md:99` says harvested reference docs "need not be redistributed". So the brief should say why redistributing tldr in-repo (rather than fetching it reproducibly, which the thread also allows) is consistent with ADR-0003, instead of resting on the frozen plan.
- NEEDS-HUMAN — **The patch would be too large to review, and that clashes with the contribution gate.** All English `pages/common` + `pages/linux` pages is several thousand pages, roughly megabytes of text, in one JSONL file plus per-page hashes. The brief notes T4 contribution is gating ("Verification contract") but never sizes the diff or says how a reviewer or the reverted C4 leg handles a multi-MB hunk. State the expected page count and byte size, and say whether `.gitattributes` (absent in the target) should mark the file `-diff`/`linguist-vendored`, so the review surface is a known quantity and not a surprise at Check.
- NEEDS-HUMAN — **The milestone citation doesn't resolve in the target.** The brief says "issue slice M1.4; proposal 0001 §M1". `docs/design/proposals/draft/0001-implementation-arc.md:62-72` (§M1) never mentions tldr or an M1.4 slice. M1's "Done when" covers the VM, harvest and sudo-rs. Training-data license checks belong to M2 (:78-79). "M1.4" exists only in the issue title. This is minor, but don't cite it as proposal authority. Also, `pdca.toml` and `engine/scripts/run-verify.sh` (cited under "Verification contract") don't exist in the target, so those claims can't be checked from here.
